# 探索方向：网站导航图与路径规划（Site Navigation Graph）

## 文档状态

**状态：新提出的探索方向，尚未验证，不是已确定的产品路线。**

> 版本：v0.1 · 2026-09-03  
> 来源：与项目外部评审讨论中提出  
> 前置必读：`探索方向-复杂网页任务地形信息.md`（本方向是地形信息方向的激进延伸）

本方向讨论一个根本性问题：

> **AI 操作网站，到底需不需要每次都从零探索？还是可以把"按钮通向哪里"这类内在逻辑预先构建出来，让 AI 在任务开始前就知道走哪条路径？**

---

## 一、问题背景：当前的探索成本从哪里来

当前 AI 操作网页的核心成本，不是"找不到按钮"，而是**不知道这条路走完了是不是想要的结果**——因此不得不反复试错：

```
打开页面
  → 扫描结构（world_map / world_guide）
  → 猜测"这个按钮大概去哪里"
  → 点击
  → 看结果（对了继续，错了回退重来）
  → 再猜下一步
  → ...
```

在一个多层网站（比如电商后台、开发者控制台、SaaS 管理界面）里，完成一个 5 步任务可能需要 20-40 次工具调用，因为每一步都要"到了才知道"。

**核心问题**：AI 对网站的理解是**局部的、即时的、不可复用的**。每次打开同一个网站，都从零开始理解。

---

## 二、核心设想：构建可查询的网站导航图

把网站的内在跳转逻辑，预先构建成一张**有向图**：

```
【节点】= 页面或页面状态
【边】  = 操作（点击/提交/跳转）
【权重】= 步骤数、前置条件、成功率

查询接口：
  给定当前位置 + 目标 → 返回最短/最可靠路径
  给定一个按钮 → 返回"点击后通常去哪里"
  给定目标页面 → 返回"从当前页面如何到达"
```

有了这张图，AI 在任务开始前就能"看穿"多层结构：

```
示例：任务是"修改账户密码"

没有导航图：
  打开首页 → 扫描 → 猜测点"用户头像" → 进入菜单 →
  扫描菜单 → 猜测点"账户设置" → 进入设置页 →
  扫描设置页 → 找到"安全设置" → 点击 → 找到"修改密码"
  （7步探索，实际有效操作只有4步）

有导航图：
  查图：首页 → 用户头像[el_12] → 账户设置 → 安全设置 → 修改密码
  直接执行4步，跳过探索
```

## 三、三种构建模式

### 模式A：被动积累（增量式，零额外成本）

每次 AI 完成一次操作，自动记录：
```
"我在页面 P（URL + 页面指纹），点击了元素 E（稳定指纹），
 到达了页面 Q（URL + 页面指纹），用时 T 秒"
```

随着 AI 使用次数增加，图自动变得越来越完整。不需要主动爬取，零额外成本。

**适合**：重复任务、固定流程的工作场景。

### 模式B：主动探测（任务前预热）

在执行真正任务之前，先快速"探一探"目标路径涉及的页面，只探测任务相关的子图，不爬整个网站。

```
任务：提交一个工单

预热：
  打开工单列表页 → 记录"新建工单"入口
  打开新建工单表单 → 记录字段和提交流程
  （2次额外工具调用换来后续路径清晰）
```

**适合**：首次访问陌生网站、任务路径未知的场景。

### 模式C：语义推断（不走就猜）

对于没有走过的路径，根据页面语义推断可能的跳转目标：
- 按钮文字叫"结算" → 大概率去支付页面
- 链接在"我的账户"菜单里 → 大概率是账户相关功能
- 表单有"提交"按钮 → 成功后大概率跳转到结果页

这不是精确的，但可以作为"路径候选"，引导 AI 优先尝试最可能正确的路径。

**适合**：图不完整时的降级兜底。

## 四、与已有能力的关系

当前项目已经有几块能力，可以作为导航图的基础：

| 已有能力 | 对导航图的贡献 |
|---|---|
| `fingerprint`（稳定元素指纹） | 图的"边"可以用指纹而不是坐标表示，跨会话稳定 |
| `world_map`（页面区域地图） | 图的"节点"内部结构，描述一个页面有哪些区域和入口 |
| `world_guide`（任务导览） | 图上的"路径建议"，目前是基于单页面的，可以扩展为跨页面 |
| `world_changes`（页面变化流） | 导航发生时（URL 变化）的信号，可以触发图的边更新 |
| `world_state.page.url`（当前 URL） | 图中当前节点的定位依据 |
| `page_outcome`（操作后果卡） | 图的边的"结果"——这次操作到底去了哪里 |

**缺的是**：把上面这些数据**连接成图并持久化存储**，以及一个**路径查询接口**。

## 五、导航图的数据结构（概念版）

```json
{
  "site": "github.com",
  "nodes": {
    "node_001": {
      "url_pattern": "github.com/:owner/:repo",
      "title_pattern": ":repo at :owner",
      "fingerprint": "sha256:abc123",
      "regions": ["header", "code-tab", "sidebar"],
      "exits": ["edge_001", "edge_002", "edge_003"]
    },
    "node_002": {
      "url_pattern": "github.com/:owner/:repo/pulls",
      "fingerprint": "sha256:def456"
    }
  },
  "edges": {
    "edge_001": {
      "from": "node_001",
      "to": "node_002",
      "action": {
        "kind": "click",
        "element_fingerprint": "fp:nav-pulls-tab",
        "element_name": "tab.Pull requests"
      },
      "preconditions": [],
      "observed_count": 3,
      "success_rate": 1.0,
      "avg_steps": 1
    }
  }
}
```

关键设计原则：
- **URL 用模式**（`pattern`）而不是精确 URL，一个模式覆盖同类页面（如所有 GitHub 仓库页面）
- **元素用指纹**而不是 `el_42` 编号，编号每次会变，指纹跨会话稳定
- **记录观测次数和成功率**，区分"走过一次"和"走过多次都成功"的可靠程度
- **记录前置条件**（如"需要登录"、"需要有管理员权限"），避免走到一半发现路被堵

## 六、路径规划的查询接口

新增工具 `world_path`（概念设计）：

```python
world_path(
    world_id,
    goal="找到密码修改入口",        # 自然语言目标
    goal_url_pattern=None,          # 或者精确 URL 模式
    goal_element_name="input.新密码" # 或者目标元素名
)

# 返回：
{
  "path_found": true,
  "confidence": "high",           # high / medium / low / speculative
  "steps": [
    {"action": "click", "target_fingerprint": "fp:user-avatar", "hint": "点击用户头像"},
    {"action": "click", "target_fingerprint": "fp:account-settings", "hint": "进入账户设置"},
    {"action": "click", "target_fingerprint": "fp:security-tab", "hint": "切换到安全设置"},
    {"action": "find", "target_name": "input.新密码", "hint": "找到密码输入框"}
  ],
  "total_steps": 4,
  "preconditions": ["auth.loggedIn == true"],
  "fallback": "如果路径失效，使用 world_guide(task_hint='修改密码') 重新探索"
}
```

## 七、最核心的难题：图的失效问题

这是整个方向最大的风险，必须正视：

### 7.1 失效场景

| 失效原因 | 发生频率 | 危害程度 |
|---|---|---|
| 网站改版（按钮改位置/改文字） | 月级 | 高（走错路） |
| A/B 测试（同用户不同时点看到不同 UI） | 实时 | 中（偶发） |
| 权限变化（原来能进的页面现在没权限） | 不定期 | 中 |
| 登录状态变化（进入后被踢出） | 任务中随机 | 高 |
| 动态路由（同一按钮根据状态去不同页面） | 高频 | 高 |

### 7.2 失效保护机制（必须先于图的使用落地）

**原则：实时事实永远优先于图中的先验。图只是建议，不是命令。**

```
使用图中路径前：
  1. 验证当前节点的"关键指纹"是否还存在（快速探针，<100ms）
  2. 如果指纹命中：按图走
  3. 如果指纹未命中：
     a. 标记该节点/边为"疑似过期"
     b. 降级为实时探索（world_guide）
     c. 如果探索成功：用新路径更新图
     d. 如果探索失败：标记为"已失效"，人工确认后删除

走图中路径时：
  每一步都验证 page_outcome，如果结果与预期不符：
     → 立即停止按图走
     → 降级为实时探索
     → 不要强行继续
```

## 八、与"地形信息"方向的关系

本方向是`探索方向-复杂网页任务地形信息.md`的**激进延伸**：

```
地形信息（已有方向）：
  "给 AI 一张当前页面的区域地图"
  → 静态的、单页面的、描述性的

导航图（本方向）：
  "给 AI 一张整个网站的跳转关系图"
  → 动态的、跨页面的、可规划的
```

地形信息解决的是"当前页面里该往哪走"，导航图解决的是"整个任务应该经过哪些页面"。

两者可以共存：导航图告诉 AI 宏观路线，地形信息帮助 AI 在每个节点内部精确定位。

## 九、与地图公地方向的关系

`探索方向-地图公地与小票标准.md`讨论过"跨用户共享地图"并将其封存（原因：过期先验危害大、第一轮实验未证明增益）。

导航图和地图公地的区别：

| 维度 | 地图公地（封存） | 导航图（本方向） |
|---|---|---|
| 共享范围 | 跨用户（多人共享一张图） | 单用户本地（只复用自己走过的路） |
| 数据内容 | 页面区域和入口的静态描述 | 操作→跳转的动态因果关系 |
| 失效处理 | 依赖版本戳（难以自动检测失效） | 实时指纹验证（每步都检查） |
| 初始增益来源 | 别人走过的路，自己用 | 自己走过的路，再次用 |

因此本方向不受地图公地封存结论的约束，但地图公地方向总结的**"过期先验危害教训"**必须在本方向的失效保护机制中贯彻。

## 十、待验证假设

### H1：探索成本主要来自"路径不确定性"而非"元素定位"

**支持**：E3 实验显示定位均值 43ms（极快），open 占总时间 57.8%（固定开销）。真正浪费在多轮 world_guide + 失败重试上。  
**质疑**：是否真的是路径不确定导致的，还是工具调用链本身的延迟？需要对一个已知路径和未知路径的同类任务做时间对比。

### H2：被动积累的图，在 N 次使用后能显著减少路径探索成本

**支持**：直觉上成立，类似 GPS 有了已知路网就能规划路线。  
**质疑**：N 是多少？如果需要 20 次才能积累出有用的图，大多数使用场景（一次性任务）根本用不到。

### H3：指纹验证（<100ms）能可靠检测图节点是否失效

**支持**：稳定指纹已经在测试中验证过跨会话可认路（命中率 80-92%）。  
**质疑**：8-20% 的失效率在路径验证场景里可接受吗？如果路径有 5 步，每步 90% 命中率，整条路径的成功概率只有 59%。

### H4：URL Pattern 能有效聚合"同类页面"，使节点数可控

**支持**：GitHub 所有仓库页面 URL 都是 `github.com/:owner/:repo`，一个节点可以代表数百万个具体 URL。  
**质疑**：有些 SPA 的 URL 根本不变化（靠状态区分），URL Pattern 在这类网站上完全失效。

## 十一、最小验证方案

**目标**：回答一个最小问题——"预先走过的路径，第二次走能省多少？"

**方案**：

```
Step 1：选一个有 3-4 步导航的固定任务（不涉及登录、不涉及提交）
  候选：GitHub 仓库首页 → Issues → 筛选 Open → 按时间排序

Step 2：第一次执行，记录：
  - 工具调用次数
  - 总时间
  - world_guide 调用次数（探索成本）
  同时，手动记录路径（哪些元素、哪些 URL）

Step 3：第二次执行，使用记录的路径（不调 world_guide，直接按指纹找元素）：
  - 工具调用次数
  - 总时间
  - 失败次数（指纹未命中）

Step 4：比较两次结果
  - 如果 Step 3 的调用次数和时间显著低于 Step 2，H2 初步成立
  - 如果指纹未命中率超过 20%，H3 需要重新评估
  - 如果节省的不显著（类似地图公地实验的结论），重新评估方向价值
```

**不做**：不构建完整的图存储系统，不实现 `world_path` 工具，不跨会话持久化——这些都是最小验证通过后才做的事。

---

## 十二、停止条件

出现以下情况之一，暂停本方向：

- 最小验证显示第二次执行的效率没有显著提升（工具调用次数下降 <30%）
- 指纹失效率导致整条路径成功率 <70%（单步 90% × 5步 = 59%，不可接受）
- 失效保护机制的开销（每步指纹验证）抵消了图带来的路径规划收益
- 大多数目标网站是 SPA，URL Pattern 无法有效区分节点

## 十三、如果验证成功，下一步

按阶段推进，每阶段需要上一阶段验证通过后才能开始：

```
阶段0（最小验证，当前）：
  手动记录路径 → 第二次手动复用 → 测量收益
       ↓ 通过
阶段1（被动积累）：
  world_act 每次自动记录（from_node, action, to_node）
  存本地文件，不做查询接口
       ↓ 验证积累的图覆盖了哪些路径、覆盖率多高
阶段2（路径查询）：
  实现 world_path(goal) 接口
  从本地图中查询最短/最可靠路径
  指纹验证 + 降级机制必须同步上线
       ↓ 验证 world_path 的实际使用准确率
阶段3（语义推断兜底）：
  对图中没有记录的路径，用语义推断生成候选路径
  "这个按钮叫'结算' → 大概率去支付页面"
```

## 十四、与其他探索方向的优先级关系

本方向**不与以下方向竞争资源**，可以并行：

- `SKILL-executor` 决策树（SKILL 层，不影响工具层）
- 扩展 E3 benchmark（测试体系，独立）

本方向**依赖以下前置**：

- `E1` 实验（指纹跨会话增益量化）——如果 E1 显示指纹本身就不稳定，本方向的基础就动摇了
- 稳定指纹的 `export/import` 落盘版本（T0）——图需要指纹持久化

**在 E1 完成之前，本方向的最小验证（十一节）可以手动进行，不依赖指纹系统。**

## 十五、开放问题（讨论用）

1. **节点的定义**：一个"节点"应该是 URL（静态网站友好）、页面指纹（SPA 友好）、还是"URL + 关键元素组合"（兼顾两者）？

2. **图的粒度**：图应该细到"每一个可点击元素的出口"，还是粗到"每一个区域（region）的出口"？细了维护成本高，粗了路径规划精度低。

3. **用户隐私**：图中记录了用户访问过哪些页面、做了哪些操作——这些数据存在本地还是可以分享？分享（跨用户）能带来更快的图积累，但引入了隐私问题。

4. **与 WebMCP 的关系**：WebMCP 的工具本质上是网站主动提供的"图"——精确、无歧义。本方向是"AI 自己爬出来的图"——可能不准确、会过期。如果 WebMCP 普及，本方向的图是替代品还是补充（用于验证 WebMCP 工具执行的结果）？

5. **多用户任务竞争**：如果图记录了"提交表单后去了成功页面"，下次是否意味着同样的表单一定能成功？表单内容不同，结果可能不同——图只记录了路径，不记录表单内容。如何处理"路径相同但前置状态不同"的情况？
