# 核心命题：反馈闭环是第一杠杆

> **状态**：已确认的项目定位陈述（**不是**探索提案）。本文是方向判据，不是待办清单。
> **替代**：本文取代原 4 篇「探索方向」文档（已归档至 `docs/archive/`）作为方向依据。
> **用法**：任何新功能、新文档、新实验，先回答一个问题——**它是在造传感器，还是在造 Runtime？**

---

## 0. 一句话

> 智能体完成任务的过程本质是**开环控制**：发出动作 → 假设环境按预期改变 → 继续。
> 它的误差不是随机的，而是**系统性偏乐观**——训练目标奖励「完成任务」，
> 在没有反向信号时，模型的默认假设是**成功**。
> 因此，**让智能体不再猜**，比提升模型能力更直接。

这不是「让 AI 更聪明」，而是「让 AI 知道自己做没做到」。

### 0.1 定位修正（2026-09-08）

**不是「放弃感知，全力做验证」**，而是：

```text
感知层      →  降级为可替换的传感器（sensor）
证据 / 因果 / 验证 / 信任 / 恢复  →  升级为核心 Runtime
```

传感器是可替换的：截图、DOM、无障碍树、Canvas scene model、未来的原生工具声明——
哪个准用哪个，哪个被模型能力吃掉就换掉，**它们不构成护城河**。

Runtime 不是可替换的：它负责把「传感器看到的东西」变成「可信的事实」，
并在事实不足时**承认不足**而不是猜测。这是本项目的长期价值所在。

> **Agent-Native Web 的长期价值，不是帮助 Agent 看见，而是让 Agent 不必猜。**

## 1. 问题：开环控制 + 系统性乐观偏差

### 1.1 开环控制在有扰动时必然发散

控制论里，开环系统不观测输出、只按预设输入执行。只要环境有扰动，误差就会累积且无法修正。网页环境恰恰是扰动密集的：

```text
异步渲染 · 网络延迟 · 请求竞态 · 局部刷新 · 反爬拦截 · 弹窗遮挡 · 受控组件重置
```

### 1.2 模型的失败模式不是「做错」，是「以为做对了」

这是本命题的关键起点。常见的 agent 失败不是选错了按钮，而是：

- 点击后页面没反应 → 认为「应该生效了」→ 继续下一步；
- 表单提交返回 422 → 没有观察到 DOM 变化 → 认为「提交成功」；
- 登录墙拦截 → 没识别 → 继续在错误页面上操作；
- 页面已跳转但目标区域无变化 → 判定「失败」→ 重复硬点。

**为什么模型会这样？** 因为它的训练目标是完成任务，不是承认不知道。观察不到反向信号时，它的先验是成功。

### 1.2.1 实验修正：这个失败模式**可以被提示缓解**（2026-09-08）

[三问实验](三问实验-缺失事实能否被推理.md) 的对照结果推翻了一个隐含假设：

| 组 | 正确率 |
|---|---|
| N 无事实（默认处境） | 17% |
| **C 提示组**（加一句「不确定就说不确定」） | **0%** |
| F 有事实（注入缺失事实） | 100% |

提示**确实让模型不再乱猜**（从"猜成功"变成"不确定"），但**没有让它变正确**——正确率 0%。

**所以本命题的价值主张必须改写**：

| 旧表述（数据不支持） | 新表述（数据支持） |
|---|---|
| 防止模型把「没生效」当「成功」 | **提供模型无法推理出来的事实** |
| 卖的是「防止错误」 | 卖的是「提供答案」 |
| 价值随模型变谨慎而下降 | 价值随事实不可得而**不下降** |

诚实说：提示能让模型知道「我不知道」，**只有事实能让它知道答案**。
前者是 prompt 能做的事，后者才是 Runtime 的领地。

**这个结论已通过 P2 的证伪测试（2026-09-08）**：换成强推理模型 glm-5.3（每组每场景 10 次）
与 kimi-k3 重测，提示组仍为 **0%（0/20）**，与无事实组无差异（p=1.0），有事实组 20/20。
→ [P2 实验](P2实验-换强模型提示组能否答对.md)。
**这一层不会被 scaling 吃掉**——它不取决于模型强弱，取决于事实是否可得。

（诚实标注：干净证据主要来自 ledger 场景——自由作答、真相 ¥0 与页面显示 ¥100 相反。
async 场景因二选一 + 真相等于保守默认答案，本轮不可用于判定。）

### 1.3 推论：最值钱的不是「成功」，是「模型推不出来的事实」

| 状态 | 模型能否自行推断 | 价值 |
|---|---|---|
| 生效了（`progressed`） | **能**——观察到变化即可 | 低（模型本来就会猜对） |
| 没生效（`unchanged`） | **不能**——它需要外部权威反驳它 | **高** |
| 不知道（`uncertain`） | **不能**——默认会被塌缩成「成功」 | **最高** |

> 这是本项目的真正价值主张，比「原生网页世界」准确得多：**让智能体不再猜**。
>
> 但要按 §1.2.1 的修正读：**提示能让模型说出「不确定」，只有事实能让它给出正确答案。**
> 「让它不再猜」的正确含义是「给它答案」，不是「让它闭嘴」。

### 1.4 表述订正与分层判据（2026-09-08）

「让智能体不再猜」这个说法把**两件成本完全不同的事**混在一起了：

| | 旧说法 | 落在哪一层 | 提示能不能做 | 价值 | 可防御性 |
|---|---|---|---|---|---|
| ① | 让 agent 别自信地做错 | **Intent**（提示） | **能**（实测 27%→2%） | **有** | ❌ 低（谁都能抄） |
| ② | 让 agent 拿到它推不出来的事实 | **Environment**（内核） | 不能 | 有 | ✅ 高 |

> **订正（2026-09-08）**：早先写成"凡是提示能做到的，都不构成护城河"——**这话太绝对**。
> 它混淆了**价值**与**可防御性**两件事。提示确实有价值（27%→2% 是实测），只是**难以防御**。
> 判据应该拆成两问：**「有没有用？」和「别人能不能轻易抄走？」**

**分层的判据来自 Claude Code 那套 harness/environment 工程实践**，它把"围绕模型的一切"分成三层
（[参考](https://hidekazu-konishi.com/entry/claude_code_harness_and_environment_engineering_guide.html)）：

```text
Intent       告诉 agent 该做什么（CLAUDE.md / system prompt）→ 只影响意图，无强制力
Harness      进程内强制（权限、hooks、工具面）→ 拦得住"派发"，拦不住"派发之后"
Environment  进程外边界（沙箱、OS 权限、网络）→ 内核级，绕不过去
```

**三层价值光谱**（不是"有/无"的二元判断）：

| 层 | 形态 | 例子 | 价值 | 可防御性 |
|---|---|---|---|---|
| **自由提示** | Intent，无契约 | 「不确定就说不确定」 | 有（实测 27%→2%） | ❌ 免费、可抄，会被上下文截断/自信幻觉压过 |
| **站点声明的提示** | **接口契约的一部分** | 站点声明「本动作异步，轮询 `/orders/<id>` 直到终态」 | 有 | ✅ **需站点参与，Runtime 要会兑现** |
| **环境证据** | Environment，内核级 | HTTP 状态码、跨信源复验 | 有 | ✅ 模型绕不过去 |

> **中间那一层是"有意识提示"的空间，值得单独记一笔**（用户 2026-09-08 提出，备用点）：
> 如果项目的终局是**网页主动暴露接口**（agent-native web），那么"提示"就不再只是
> 工程师写给模型的自由文本，而可以是**站点主动声明的、有版本的、属于接口契约的**验证提示。
> 它和"自由提示"的本质区别是：**前者是单方面加的一句话，后者是双方约定的一个面。**
> 这一层如果成立，它是有防御性的——因为需要站点参与，且 Runtime 必须能识别并兑现它。
>
> 但**这不是当前重点**：它依赖站点改造，而 Runtime 对"连声明都没有"的站点的价值才是主战场。
> 记为备用方向，不投入。

据此，本项目的表述订正为：

> ❌ 旧：让智能体不再猜（Intent 层，提示就能做一半）
>
> ✅ 新：**把网页环境里不可信的表象，转成 Environment 层的可信证据**
> —— 在事实不足时**停下来确认**，而不是在不确定状态下自信地继续

**为什么网页比代码仓库更需要这一层**：代码仓库的真值来自**执行**（编译过没过、测试红不红），
天然权威、不可辩驳；而网页的"环境"**本身就在撒谎**（页面显示 `✅ 成功`、后端 422）。
同一个 harness 思想，在网页上必须更重——因为它的 Environment 层不可信。

## 2. 关键区分：感知层 vs 验证层（以及验证层内部的再切分）

### 2.1 第一刀：感知 vs 验证

| | **感知层** | **验证层** |
|---|---|---|
| 问题 | 按钮在哪、页面结构是什么、目标元素是哪个 | 这个动作到底生效了没有 |
| 本质 | 信息**存在**，但编码对模型不友好 | 需要**缺失的外部事实** |
| 角色 | **可替换的传感器** | **核心 Runtime** |
| 会被模型能力吃掉吗 | **会，而且很快**（视觉 / 长上下文 / computer use 都在进步） | **部分会，部分永远不会**（见 2.2） |
| 典型失败 | 定位慢、选错元素、读不完页面 | 重复提交、以为登录了其实没登、以为下单了其实 422 |
| 项目对应资产 | 编号 / 语义名 / 导览图 / 地图 / 区域钻取 | 后果卡 / `evidence_seq` / `sources` / 静默失败归因 |

### 2.2 第二刀（关键修正）：验证层内部仍要再切一刀

**不能说「验证瓶颈不会被模型能力吃掉」——这个说法过于绝对。** 验证层里有两类东西：

| | **可被模型能力改善的部分** | **不可能靠模型 scaling 解决的部分** |
|---|---|---|
| 内容 | 从已有观察中做更准的判断 | 缺失的外部证据、权威状态、因果关系、来源身份 |
| 例子 | 截图里清楚写着 `Success` / `Payment complete`，更强视觉模型判得更准 | 见下方五个反例 |
| 结论 | 会被吃掉，**不要在这里建护城河** | **逻辑上不可能**，是 observability 问题 |

**五个反例（模型再强也推不出来）**：

```text
① 页面显示成功，后台请求其实 422
② 按钮变灰，但请求后来 rollback
③ POST 返回 202，后台任务 30 秒后失败
④ DOM 显示 $100，真正账本仍然是 $0
⑤ 页面发生变化，但这是 websocket 后台刷新，不是刚才这个 click 引发的
```

这些信息**不存在于任何观察里**。模型再聪明也无法从不存在的信息中可靠推出事实。
**这不是 intelligence problem，是 observability / evidence problem。**

所以精确的表述是：

> **验证中需要「缺失的外部证据、权威状态、因果关系和来源身份」的部分，
> 不可能靠单纯模型 scaling 凭空解决。**

而 Runtime 的职责正是补上这四样：**证据**（evidence）、**权威状态**（authoritative state）、
**因果关系**（causality）、**来源身份**（provenance）——并在补不上时明确报 `uncertain`。

### 2.3 由此得出的资源分配原则

```text
感知层（编号/导览/地图/地形）      →  可替换传感器  →  降级为实验，不投入主线
验证层·可判断部分（更强视觉判读）  →  会被模型吃掉  →  不建护城河
验证层·外部事实部分（证据/权威/因果/身份）→  逻辑不可能  →  核心 Runtime，最高优先级
```

**反过来说**：凡是「模型看一眼就能知道」的能力，做深了也会被下一代模型抹平。
凡是「环境才知道、观察里没有」的事实，做深了会随模型变强而更值钱。

### 2.4 补充：模型可进步的部分也在变，但边界不变

随着模型变强，2.2 左栏（可判断部分）的边界会外移——今天需要外部证据的，明天可能看一眼就够。
但右栏的四类东西**不会**外移，因为它们缺的是信息本身，不是推理能力。

**这意味着 Runtime 的设计必须能容忍传感器被替换**：当某个传感器（比如截图判读）变得足够强时，
Runtime 应该能把它当输入源之一接进来，而不是把它当竞争对手。

## 3. 机制：验证闭环由三层组成

### 3.1 因果窗口绑定——把动作和后果锁在一起

单看 DOM 变化无法判断因果（页面自己也在动）。必须把 `action` 生命周期、网络事件、DOM 变化放进同一条有序时间线，用**窗口**归属：

```text
seq=10 action    world_click start(el_79)
seq=11 request   github.com/git/git/pulls
seq=12 response  200 text/html          ← 归因到 seq=10 的动作
```

没有这一步，「页面变了」和「我的动作生效了」无法区分。

### 3.2 信任分层——决定「这句话能不能当指令」

`sources` 四类标注是本项目**最被低估的设计**，它解决的不是生效性，而是安全边界：

| 类别 | 内容 | 可信度 |
|---|---|---|
| `fact` | URL / 编号 / 坐标 / 指纹 / 序号 | 可信 |
| `evidence` | 动作前后差分 | 可信 |
| `inference` | 导览 / 处方 / 建议 | 仅参考 |
| `untrusted` | 页面自由文本（name / text / aria-label / placeholder） | **绝不当指令执行** |

五态解决**正确性**（生效了吗），四类解决**信任性**（这句能不能信）。后者更难抄——它需要整条管道自洽（`evidence_seq`、`world_epoch` 失效、IPI 过滤），不是加个字段就有。

### 3.3 五态出口——给模型一个「说不知道」的合法选项

```text
progressed  确定生效
challenged  被拦住（明确转人工）
errored     明确失败（带结构化原因）
uncertain   有变化但不知道有没有生效   ← 核心：把「未知」从两端拆出来
unchanged   确实没生效
```

默认 agent 的行为是二值的：观察到变化 → 成功；没观察到 → 失败（或更糟，假设成功）。歧义全部塌缩到两端。**`uncertain` 是把「未知」显式化的那一态，也是别的方案没有的一态。**

## 4. 边界：这个命题只在两个条件下成立

必须写死，否则会被反例打穿。

### 4.1 成立条件

```text
高环境不确定性  ×  高假成功代价
```

- **高环境不确定性**：异步状态、多步表单、有副作用的提交、跨页面流程；
- **高假成功代价**：重复提交、重复下单、误以为已授权、误以为已保存。

### 4.2 不成立（或增益趋零）的场景

- 静态信息检索：读文档、抽表格、单页问答——模型看一遍就够，反馈层增益 ≈ 0；
- 低代价动作：搜索页点错链接，代价为零；
- 有明确 API / WebMCP 原生工具的场景——网站已经提供了权威反馈，不需要重建。

> 项目自己的 A/B 数据已印证：任务图复用**没有提速**（66.9s vs 70.0s，慢 4.6%）。
> 增益只在高不确定性任务上出现，且必须实测，不能假设。

### 4.3 「完整」是个危险的词

反馈的目标**不是完整，是充分且可信**。完整 = 上下文洪水，等于把「整页信息洪水」复制成多个版本。

准确措辞是：**及时、准确、可判定、带信任级别**。没有「完整」。

（项目自己的时间线 A/B 已得出正确结论：**价值在「信息」不在「工具」**——由 harness 每步自动注入压缩摘要，而不是让模型主动调工具。）

## 5. 可证伪的预测

本命题必须可测，否则只是信念。

| # | 预测 | 证伪条件 |
|---|---|---|
| P1 | 同一模型，验证层开/关，增益在**高环境不确定性任务**上显著，在静态阅读任务上不显著 | 若两类任务增益无差异 → 命题不成立 |
| P2 | 增益随模型能力提升，在**感知维度**与**验证层的可判断部分**衰减，在**验证层的外部事实部分**不衰减 | 若外部事实部分的增益也随模型变强而消失 → 该部分也会被吃掉，需重写命题 |
| P3 | `unchanged` / `uncertain` 出现率下降 ⇒ 重复动作率下降 ⇒ 假成功率下降（三者强相关） | 若三者不相关 → 卡没有真正改变行为 |

**P2 最关键**，也是最需要小心的一条：它必须**分层测**，不能笼统测"验证维度"。

做法：构造两组任务——
- **A 组（可判断）**：成功信号在观察里可见（截图写着 Success），预期强模型不需要外部证据也能判对；
- **B 组（外部事实）**：成功信号不在观察里（显示成功但后端 422、202 后异步失败、DOM 值 ≠ 账本值、变化非本动作引起）。

若 A 组增益随模型变强衰减、B 组不衰减 → 命题成立，且给出了 Runtime 的精确边界。

### 5.1 现有实验的轴选错了

`mcp/experiments/astra_canvas_phase1/`（issue #16）的 A/B/C 测的是「结构化接口 vs 视觉」——**那是感知维度**，正好是被模型能力吃掉的那一半，而且用最强模型去测，等于主动选了一个会输的战场。

**应该测的轴**：同一模型，**验证层开 / 关**，并按上文的 A 组 / B 组任务分层。

## 6. 决策判据

新增任何功能 / 文档 / 实验前，按顺序回答：

```text
1. 它是在造传感器，还是在造 Runtime？
     传感器（感知层） → 可替换，降级为实验，不进主线，不写规格
     Runtime（证据/因果/验证/信任/恢复） → 优先级最高，必须配测试与守护

2. 它需要的信息，模型自己能不能推出来？
     能推出来（观察里已有） → 会被下一代模型抹平，不值得长期投入
     推不出来（观察里没有） → 属 observability 问题，随模型变强更值钱

3. 它属于验证层的哪一半？
     可判断部分（更强视觉/推理能解决） → 不建护城河，但要能当输入源接进来
     外部事实部分（证据/权威/因果/身份） → 核心 Runtime

4. 它有没有可证伪的判据？
     没有 → 不许写成规格文档，只能进 docs/archive/ 或实验目录

5. 它是否只在高不确定性 × 高代价场景有效？
     是 → 明写边界，不许宣称通用
```

## 7. Runtime 的四个职责（对应四类缺失事实）

| 职责 | 补的是什么缺失 | 现有对应资产 |
|---|---|---|
| **证据（evidence）** | 页面之外的动作后果（网络状态码、控制台错误、异步结果） | 静默失败归因、因果窗口 |
| **权威状态（authoritative state）** | 观察里没有的真值（账本、后端状态、任务是否真完成） | 待建：外部权威接入点 |
| **因果关系（causality）** | 「变化是我的动作引起的」还是「后台自己动的」 | 统一时间线、`evidence_seq` |
| **来源身份（provenance）** | 这句话是事实、证据、推断，还是不可信文本 | `sources` 四类标注 |
| **恢复（recovery）** | 事实不足时怎么办，而不是猜 | `uncertain` + 预算铁律 + `handoff` |

> 前四类决定「能不能知道」，第五类决定「不知道时会不会乱来」。
> 五态里的 `uncertain` 正是第五类的具体形式。

## 7.5 反馈不完整时如何验证（七条思路，2026-09-08）

**这是本命题最棘手的一层**：它直接决定「自主执行」能不能被信任。
反馈不完整的本质是**部分可观测性**——模型看到的状态与世界的真实状态之间有缺口，
而这个缺口正是错误累积、幻觉延续、任务偏离的主要来源。

**核心思路一句话**：当模型自身的语言理解无法保证验证可靠性时，
**把验证下沉到 harness 层的结构化、确定性检查**，而不是让模型对不完整信息做自由推断。
反馈不完整不可能被完全消除，能做的是让系统在不确定时倾向于**停下来确认**，
而不是**自信地继续**。

下表把七条思路与项目现有资产对齐（✅ 已有 / 🟡 部分 / ❌ 待建）：

| # | 思路 | 要点 | 项目现状 |
|---|---|---|---|
| 1 | **不信任单一通道，交叉验证** | 工具返回"成功"≠目标达成（exit 0 ≠ 逻辑对；HTTP 200 ≠ 业务生效）。动作后主动去**独立信源**核实 | 🟡 `sources` 四类已做信任分层；但"独立复核"未实现 |
| 2 | **可检验的后置条件替代语义反馈** | 别让模型"解读"模糊日志，预先为动作定义结构化、可编程检查的 postcondition | ❌ 待建（最有潜力的一条） |
| 3 | **主动探测而非被动等待** | 插入只用于确认状态、不产生业务效果的验证步骤（"观察工具"而非只有"动作工具"） | 🟡 `world_outcome(since)` / `world_wait` 是雏形 |
| 4 | **置信度分级 + 分层响应** | 高置信→推进；中置信→额外核实；低/矛盾/缺失→停下或转人工 | ✅ `confidence` 三档 + `handoff` 已具备骨架 |
| 5 | **fail-closed 而非 fail-open** | 反馈不完整时默认假设失败，宁可多确认一次，不在错误状态上继续构建 | 🟡 `uncertain` 是保守默认，但**无强制策略** |
| 6 | **幂等 + 检查点分解** | 长任务拆成有明确可验证边界的短步骤，每步幂等可重试 | ❌ 待建 |
| 7 | **保留可回放轨迹，验证延后** | 当下判不了就完整记录（调用参数 + 环境快照），事后异步审计/人工回溯 | 🟡 `evidence_seq` / 时间线 / runtime_traces 是雏形 |

**第 5 条是七条里最反直觉、也最容易被做错的一条**（见 §7.6）。

### 7.6 fail-closed 的代价：保守不是免费的

「反馈不完整时默认失败」听起来安全，但有个直接的副作用：
**它会制造假阴性（把成功的动作判成失败），进而引发重复动作。**

这正是项目自己五态里的 `unchanged` 困境：
- 判 `unchanged` → 模型重试 → **重复提交/重复下单**（正是我们要防的）；
- 判 `progressed` → 万一没生效 → 假成功。

所以 fail-closed **不能是无条件的**。正确的形态是**按代价分级**：

| 动作代价 | 反馈不完整时的默认 | 理由 |
|---|---|---|
| 可逆 / 低代价（读页面、搜索） | fail-open，继续 | 多确认一次的代价 > 做错一次的代价 |
| 不可逆 / 高代价（提交、下单、删除、授权） | **fail-closed，停下确认** | 重复动作的代价 > 停下来的代价 |

**判据：fail-closed 只在高代价动作上成立；把它无条件推广到所有动作，会退化成"什么都不敢做"。**

这条也给出了第 4 条（置信度分级）与第 5 条的正确组合方式：
**置信度决定"要不要核实"，动作代价决定"核实不了时该不该继续"。两者正交，不能混为一谈。**

完整的二维决策矩阵（2026-09-08 推演，用户提出并修正）：

| | **可核实**（后置条件满足/不满足） | **不可核实**（反馈缺失/矛盾） |
|---|---|---|
| **可逆 / 低代价** | 按结果推进 | fail-open，继续 |
| **不可逆 / 高代价** | 按结果推进 | **fail-closed，停下** |

> 踩过的坑（`unchanged` → 重试 → 重复下单）本质是**在高代价格子里套用了低代价格子的策略**。

### 7.7 锚点问题：交叉验证需要"这条资源就是那一次提交"的证据

第 1 条（交叉验证）与第 2 条（后置条件）是**一体两面**，交点是一个**锚点**。

三种候选后置条件各自的缺陷：

| 候选 | 缺陷 |
|---|---|
| HTTP 状态码 | 只反映"请求被受理"，不反映"业务状态落地"（202 之后完全可能失败） |
| DOM 文案 | 不可信（前端 catch 块写死 toast、乐观更新不回滚） |
| 独立信源读回 | 最接近真值，但有隐藏前提——**你怎么知道读到的这条，就是刚才那次提交产生的**？ |

第三点是核心矛盾，也是"重复下单"的根源：
- 查到 → 分不清"这次提交成功的"还是"上次重试遗留的"
- 没查到 → 分不清"真的失败了"还是"后端异步还没写完，读早了"

**幂等键（idempotency key）能同时消解这两个歧义**，因为它把"验证"和"防重复"绑在同一个客户端生成的 token 上：

```text
提交前：harness 生成 key = uuid()，写入本地待确认队列
提交时：请求携带该 key
验证时：查 EXISTS(resource WHERE client_key == our_key)
        而不是查"订单列表里有没有新订单"
```

后置条件谓词因此可以写成：

```text
P(success)       = EXISTS(resource WHERE client_key == our_key AND status ∈ {confirmed,…})
P(failure)       = EXISTS(resource WHERE client_key == our_key AND status ∈ {failed,rejected})
P(indeterminate) = NOT EXISTS(resource WHERE client_key == our_key)
   → 只有到这一步,才轮到 fail-closed / fail-open 分级介入
```

**DOM 在这个结构里的正确位置**：降级为**弱信源，仅用于矛盾检测**。
「独立信源说 confirmed，但页面还在转圈/显示错误」——这个矛盾本身是**触发人工确认的信号**，
而不是直接采信任一边。**撒谎的信源依然有情报价值，只是不能当仲裁者。**

**幂等键同时解决防重复**：若后端支持幂等语义（Stripe 等支付 API 普遍支持），
即便 harness 因反馈缺失而重试，后端会返回同一笔已存在资源，而不是创建第二笔。
**验证机制与防重复机制共用同一套基础设施**——这就是"1 和 2 是一体两面"的具体含义：
交叉验证需要一个跨信源的连接键，而这个连接键天然具备幂等语义。

### 7.8 锚点降级：面对不配合的第三方网站

上面这套有个前提：应用方愿意暴露"按 client key 查询"的读接口，或后端本身实现幂等。
但 Runtime 面对的大概率是**没有这层配合的第三方网站**——它们的 API 不会认识你塞进去的 key。

锚点只能退而求其次，用**网络层的关联手段**去凑：

| 手段 | 性质 | 风险 |
|---|---|---|
| 拦截提交请求的 request/response | 这一跳的响应可信 | 可能只到 202/500 粒度 |
| 提交后轮询资源列表 + **时间窗 + 内容近似匹配** | **概率性证据** | 必须在谓词里显式标注置信度，不能当确定性判断 |
| harness 本地状态锁（动作在途，禁止二次发起） | 确定性（不依赖后端） | 把防重复的责任从后端移到 harness 自己 |

**最后一条是第三方场景下的主要依靠**：harness 在收到明确 P(success)/P(failure) 之前，
本地维护"该逻辑动作已在途中"的锁，阻止自己对同一逻辑动作发起第二次请求。

### 7.9 待展开：置信度如何量化（下一节）

当锚点从"业务层幂等键"降级到"网络层弱关联"时，需要回答：

1. **置信度怎么量化？**（时间窗命中？内容匹配度？多信源一致数？）
2. **阈值多少才允许从 indeterminate 转出**（转向 success，或转向"允许重试"）？
3. 这**大概率不能用全局阈值**，要按 resource 类型（订单 / 表单提交 / 权限授予）分别标定——
   因为误判代价差异巨大。

**这是 §7.6 之后需要单独展开的一节。**

### 7.10 一个必须先解决的实现前提（2026-09-08 核查）

**上述设计全部依赖"能读到网络层的响应内容"，而项目当前做不到。**

| 事实 | 位置 |
|---|---|
| 普通响应**不读 body**（仅 ≥400 截 200 字符） | `mcp/server.py:710` 注释 |
| 时间线**不存响应体**（隐私/体积），URL 归一化去 query | `mcp/aw_timeline.py:173` |
| 响应事件只记 `url / status / rtype / ctype` | `mcp/server.py:710-712` |

**这意味着**：
- 幂等键即使塞进请求，也**读不回来**（响应体不存）；
- "按 client key 查询资源"需要一次**额外的 GET**，而 GET 的响应体同样不被保留；
- 网络层弱关联（时间窗 + 内容匹配）需要**响应体内容**做匹配，同样缺料。

**所以 §7.7-7.9 的前置条件是：先决定"是否、以及如何在隐私边界内保留结构化响应体"。**
这是一个安全/隐私取舍，不是纯技术问题——需要单独定案（可能形态：只存**结构化字段的白名单子集**
而非原始 body，且**本地、不落盘、世界关闭即销毁**）。

**在这一点定案之前，§7.7-7.9 属于设计推演，不可作为实现依据。**

### 7.11 不需要读响应体的独立信源：刷新后读 DOM（2026-09-08 推演）

上面 §7.10 的隐私约束不必推翻——**存在一条不碰响应体、只看"人能看到的东西"的验证路径**，
而且它与项目"只看人类可见内容"的设计哲学同构。

**核心观察**：读响应体 = 拦截页面本不打算给观察者看的原始通道（可能夹带他人数据、token）；
读**刷新后的 DOM** = 只看页面主动渲染、打算给任何查看者看的内容，
与人类"打开新标签页去核实"是同一个访问模型。**这不是妥协，是本来就该走的路。**

但它的可行性**不是均匀的**，由两个正交轴决定：

| | **有 canonical view**（该资源有确定的展示位置：订单详情页、账户设置页） | **无 canonical view**（fire-and-forget：点赞、埋点、204 无 body 的 webhook） |
|---|---|---|
| **SSR / 刷新即诚实**（刷新拿到的是服务端刚查库生成的 HTML） | ✅ **选项 1 成立**：强制刷新 + 读 DOM = 免费、可靠的独立信源 | ❌ 无法验证——没地方可看 |
| **CSR / 乐观状态持久化**（成功状态写进 localStorage/IndexedDB，刷新时先读本地缓存） | 🟡 **半成立**：需"强制绕过缓存的重新拉取"才能恢复成选项 1，否则退化 | ❌ 选项 3：结构性不可验证 |

**"有 canonical view × SSR-诚实"这个象限，就是 §7.10 里说的"合法观察"。**

**CSR×有 view 能否救回选项 1**：理论上可以（hard reload / 清缓存后导航，强迫新网络往返），
但这依赖应用没有把"乐观成功"写进比 HTTP cache 更底层的地方
（localStorage / IndexedDB / Service Worker 拦截 fetch 直接返回缓存值）。
若应用做到这一步，就不是缓存问题，而是**架构上主动选择"本地状态优先于服务端状态"**——
这类站点不读 body 基本戳不穿，属选项 3 的边界情况（估计是少数，但需实测分布）。

**三个隐性成本（不是免费的）**：

| 成本 | 说明 | 应对 |
|---|---|---|
| **时序 / 最终一致性** | 刷新后立刻读可能仍是旧数据（异步写入、读写分离副本延迟）→ **假阴性**（不是失败，是读早了） | retry-with-backoff，而非刷新一次就下判断 |
| **可能被判定为异常行为** | 动作后高频刷新不像人类行为，部分站点有节流/风控 | 节流、退避 |
| **对当前会话的干扰** | 刷新可能丢失页面上其他未提交状态（另一个 tab 填了一半的表单） | **验证动作自己也要过 §7.6 的代价分级表**，不能当免费操作 |

**最后一条尤其重要**：**验证动作本身是一个动作，它也有代价，也必须被纳入二维矩阵。**
「刷新核实」在高代价格子上不是无副作用的——如果刷新会破坏用户会话状态，
那它的代价可能高于"停下来问用户"。

### 7.12 实证盲点：现有实验夹具全部落在最坏象限（2026-09-08 核查）

**这是个必须记下的问题**：我们一直在推演"刷新后读 DOM"这条路，
但**项目现有的两个夹具，恰好都在最坏象限**——

| 夹具 | canonical view | 刷新是否诚实 | 落在哪 |
|---|---|---|---|
| `fact_ledger.html` | 有（余额就在页面上） | ❌ **不诚实**：余额是硬编码静态值，刷新还是 ¥100 | CSR/乐观（退化格） |
| `fact_async.html` | 有（任务状态面板） | ❌ **不诚实**：状态面板写死"排队中"，**从不轮询** | CSR/乐观（退化格） |

**所以 P2 实验里 C 组"刷新也读不到真相"不是意外，是夹具设计决定的。**
这意味着：

1. **现有实验无法验证"刷新后读 DOM"这条路径**——它在最坏象限，天然测不出；
2. **要继续这条路线，必须先有落在"SSR × 有 canonical view"象限的夹具**；
3. 这恰好是个**可证伪的预测**：如果新夹具下"刷新 + 读 DOM"能拿到真值，
   则 §7.11 的最优象限成立；如果连新夹具都拿不到，说明这条路整体不成立。

**建议的新夹具形态**：服务端渲染的订单/任务详情页——
提交后页面是服务端查库生成的（刷新即诚实），且该资源有确定的 URL 展示位置。
`fact_async.html` 的"从不轮询"恰好是要修掉的反面教材。

### 7.13 SSR 复验实测结果（2026-09-08，子代理盲跑，零外部 API 成本）

**新夹具**：服务端渲染订单页（`/checkout` → POST → 302 → `/orders/<id>`）。
订单状态 3 秒后由"处理中"变为"已确认"并生成**随机确认码**。
确认码不可猜、生成前页面上不存在——避开 P2 的"真相等于先验"坑。

**三条假设全部成立**：

| 假设 | 结果 | 证据 |
|---|---|---|
| **H1** 最优象限成立（刷新能拿到真值） | ✅ | 首读"处理中"，重开页面后读到"已确认 + 确认码" |
| **H2** 刷新幂等（确认码稳定） | ✅ | 连续两次刷新，确认码一致 |
| **H3** 时序成本（读早了是假阴性） | ✅ | 所有运行首读均为"处理中"，无一例外 |

**但最重要的发现是一个否命题**：

| 组 | 结果 |
|---|---|
| 页面**带**"请稍后重新打开本页查看结果"提示 | **6/6 正确**（6/6 都刷新了） |
| 页面**无**该提示（真盲） | **2/3 正确**（2/3 刷新了） |

> 注：n=3，Fisher 精确检验 p≈0.33，**不显著**。机制清楚但比率定不下来。

**失败那一次的原文值得记下**（真盲 T2）：

> "页面全部可见元素（共 7 个）：`订单详情` / `订单号:ORD-508268` / `状态:处理中`，无其它文本……
> **我不会用订单号冒充确认码。**"

**它的推理完全正确，结论完全错误**——它只观察了一次，而真相那时候还没到。
这是**假阴性**：把"还没来"当成了"不存在"。

**小结**：

1. **"刷新后读 DOM"这条路成立**（H1 ✅）；
2. **但"agent 会主动去做复验"不成立**——真盲组仅 2/3 自发刷新，失败方式是静默的；
3. **这一层当前取决于页面有没有给提示**（6/6 vs 2/3）——靠提示生效的东西**难以防御**（注意：是"难防御"，不等于"没价值"）。

**→ 正确形态不是"给 agent 一个刷新工具等它自己用"，而是把复验做成 harness 的自动行为。**
**但"自动行为是否真的必要"必须先实测**——见 §7.14。

### 7.14 提示 vs harness 的根本区分，与测试设计订正（2026-09-08）

**先撤回一个措辞**：早先写的"凡是提示能做到的，都不构成护城河"**太绝对**。
它把两件事混成了一件：

| 问题 | 答案 |
|---|---|
| **有没有用？** | 提示**有用**（实测 27%→2%，6/6 复验） |
| **别人能不能轻易抄走？** | 提示**容易**（免费、可抄、无强制力） |

**根本区分不是"提示 vs 无提示"，而是"是否依赖模型当下的注意力"**：

| | 机制生效的条件 | 上下文变长时 |
|---|---|---|
| **提示** | 模型**当下注意到并愿意遵守** | **注意力被稀释**，可靠性下降 |
| **Harness** | 执行路径本身触发，**不依赖模型注意** | 不受影响 |

**项目自己的数据已支持这一点**（[统一时间线 A/B](archive/评估报告-统一时间线真实任务AB.md)）：
- 「模型 15 轮只用 1 次 `world_assume`」——工具摆在那儿，模型不主动用；
- 「B 臂仍有注入内容充足却失败的轮次（注入 1772 字符仍用旧价）——**注入不保证模型理会**」。

也就是说：**连"harness 主动注入"这种强提示，都可能被忽略。**

#### harness 侧也分两级（重要区分）

| 级别 | 形态 | 是否依赖模型注意 |
|---|---|---|
| **C1 信息级** | harness 复验后，把**已核实的结论放在调用点**（工具返回值里） | 🟡 仍需模型读，但信息在**使用现场**，不在 20k tokens 之前 |
| **C2 执行级** | harness 直接按复验结果**行动**（阻断推进 / 重试 / 升级人工） | ✅ 完全不依赖 |

> 项目现有的**统一后果卡五态**就是 C1（判定结果直接进工具返回）。
> 缺的是**对"延迟到达的结果"也做 C1**（轮询 canonical view 到终态），以及高代价动作的 C2。

#### 测试设计订正：必须把"上下文长度"作为第二轴

**原设计的缺陷**：只在短任务上测 B（提示）vs C（harness）。
而**短上下文里提示的权重最高、最容易生效**——这会系统性偏向 B，
跑出一个"提示就够了，别建 C"的假结论。**这与本项目一直在抓的设计缺陷同类。**

**订正后的设计**：

| | 短上下文（约 3-5 步） | 长上下文（约 20-40 步，真实累积） |
|---|---|---|
| **B 提示** | 预期 ≈100% | **★ 关键格：衰减多少？** |
| **C1 信息级** | 预期 ≈100% | **★ 关键格：是否保持？** |
| **A 基线** | 参照 | 参照 |

关键动作放在**长流程末尾**（如：先浏览多页、加购、再提交），
使验证发生在上下文已充分膨胀之后。记录**累计上下文规模**（工具返回字节数）作为自变量。

**判据**：

- **若 B 在长上下文下保持** → 提示足够可靠，**C 是过度工程，应撤回建议**；
- **若 B 衰减而 C 保持** → 这就是"必须下沉到 harness"的**直接证据**；
- **若 C1 也衰减** → 说明"信息级"不够，需要 C2；这是下一层结论。

**必须承认的边界**：
- 多数客户端**每轮都会重发 system prompt**，所以衰减机制主要是**注意力稀释**，
  不是"提示消失"；极端长上下文下才会被压缩/截断掉——这一层机制无法在单个实验里完全分离；
- 真盲组 n=3，统计上不显著，机制清楚但比率未定。

### 7.15 「结果未知」的重复副作用：延迟窗口实验（2026-09-11）

**问题**：上一节的画布床测不了最关键的失败——**重复副作用**（写入是幂等的集合操作）。
本节换成一个**非幂等**装置：每次 `POST /orders` 都真的创建新订单，
而**第一个 POST 的响应在服务端执行后被丢弃**（客户端只见 `RemoteDisconnected`）。
唯一自变量是 `/orders` 的**可见性延迟**：写入成功，但列表在一段时间内仍读不到。

**为什么这是"未知伪装成已知"的最小形态**：

```
POST → 连接断开（结果未知，但副作用已发生）
立即 GET /orders → 返回 []         ← 看起来是"否证"
```

`[]` 不是"没有创建"的证据，只是"还没可见"。**它把未知伪装成了已知的否定。**

#### 剂量-反应：延迟越长，重复越多

| 延迟 | 发生第二次提交 | 产生重复订单 |
|---|---|---|
| 0.5 s | **0/3** | 0/3 |
| 5 s | **0/3** | 0/3 |
| 30 s | **1/3** | 1/3 |
| 120 s | **2/3** | 2/3 |

单调上升。但**延迟单独并不决定结果**——30 s 档里有两个 agent 安全、一个重复。

#### 真正的自变量：延迟 vs 该 agent 自己的耐心

对每个 agent 测出"它在下结论前等了多久"（`patience`），与延迟比较：

| 判据 | 结果 |
|---|---|
| 重试 **且** patience < delay（预测重复） | `d120_1` `d120_3` `d30_2`（3） |
| 未重试 **且** patience ≥ delay（预测安全） | 其余 9 个 |
| 违规：等够了还重试 | **无** |
| 违规：没等够却不重试 | **无** |

> **12/12 完全分离。规则是：当且仅当「该 agent 的耐心 < 延迟窗口」时会重复下单。**

各 agent 的 patience 分布：**min 3.1 s / median 51.2 s / max 234.5 s**。
所以「把延迟调到某个安全值」不是可用的设计规则——**阈值取决于 agent，不取决于系统**。

#### 关键行为分解：看到假阴性 ≠ 会行动

11/12 的 agent 都观察到了那个误导性的空列表（`0.5s` 档 3/3 也观察到了），
但只有 3 个据此重试。**区别在于是否在行动前解开了这个假阴性。**

失败者的推理链高度一致（`d30_2` 原文）：

> "我按 README 的要求去 `GET /orders` 对账，**返回的是空列表**。
> 我据此认定'没有产生副作用'，于是又提交了一次。"

**这不是没读警告，而是读懂了警告后用错误的证据满足了它。**
C 臂 README 明写"结果未知时不要再提交"——该条件式提示的前提是
**agent 能正确判断自己是否处于"未知"状态**，而这正是本装置攻击的能力。

#### 失败是静默的

重复订单不会让 agent 察觉任务失败——`d120_1` 创建了 **4 张订单**，
它的自述是"采购成功"。它甚至**正确识别了读取端点不可靠**
（"一个本该列出订单的接口在返回 201 之后仍然为空，本身就是读取不可靠的信号"），
**但仍然继续提交了三次**。三个失败者最终都主动披露了重复（值得记一笔），
但**没有任何机制保证披露**——需求方无法从结果中发现损失。

#### C2 强制闸门：与 agent 行为无关

上一轮的 runtime 闸门（pending 期间禁止再提交）在本床压力测试：

| 场景 | 订单数 |
|---|---|
| 立即重试（失败者的路径） | 1 |
| 先解决未知再重试 | 1 |
| **连续五次盲重试** | **1** |

**不管 agent 怎么试、是否理解状态、是否记得提示，副作用都只发生一次。**

#### 必须承认的缺陷

1. **我引入了污染**：目录名泄漏了自变量——`d05`/`d30`/`d120`，以及 `aw_lag`。
   `d120_2` 的原文明确说："**The room is named `aw_lag`** — 'lag' may mean the
   side effect lands *after* the client gives up." 它因此延长了轮询。
   下一轮必须用不透明的房间名。
2. **n=3/档，单一模型**，统计上不足以估比率，只能说**机制存在且可复现**。
3. **故障只有一种形态**（响应丢失 + 读取延迟）。超时、202 异步、部分提交未测。
4. 判分依赖订单数这一外部真值，而**真实网页上通常没有这个真值**——
   这正好是 §7.12 的边界：能测"客户端是否重复提交"，不能证明"业务终态"。

| 资产 | 归属 | 处置 |
|---|---|---|

| 编号 / 语义名 / 导览图 / 地图 / 地形 | 传感器 | 保留，但**降级为实验**，不再写新规格 |
| 任务图 / 业务运行时 / 站点适配器 | 传感器（且已实测无增益） | 冻结，见治理台账 |
| IPI 伪隐藏过滤 | 安全 | 保留，边界已声明 |

## 9. 一句话总结

> **「原生网页世界」是实现方式，「让智能体不必猜」是问题。**
> 把问题当第一性陈述，项目立刻变得可判断、可取舍、可证伪。
> 把实现方式当第一性陈述，就会堆出 40 个工具，没有一个是可删的。

> **不是帮助 Agent 看见，而是让 Agent 不必猜。**

**但「不必猜」要按 §1.4 分层读**：让 agent「别自信地做错」是 Intent 层的事（提示就能做，免费）；
让 agent「拿到推不出来的事实」才是 Environment 层的事（本项目的护城河）。

> **护城河判据：凡是写在提示里也有效的东西，都不构成护城河。**
