# 核心命题：反馈闭环是第一杠杆

> **状态**：已确认的项目定位陈述（**不是**探索提案）。本文是方向判据，不是待办清单。
> **替代**：本文取代原 4 篇「探索方向」文档（已归档至 `docs/archive/`）作为方向依据。
> **用法**：任何新功能、新文档、新实验，先回答一个问题——**它是在造传感器，还是在造 Runtime？**

---

## 0. 一句话

> 智能体完成任务的过程本质是**开环控制**：发出动作 → 假设环境按预期改变 → 继续。
> 它的误差不是随机的，而是**系统性偏乐观**——训练目标奖励「完成任务」，
> 在没有反向信号时，模型的默认假设是**成功**。
> 因此，**让智能体不再猜**，比提升模型能力更直接。

这不是「让 AI 更聪明」，而是「让 AI 知道自己做没做到」。

### 0.1 定位修正（2026-09-08）

**不是「放弃感知，全力做验证」**，而是：

```text
感知层      →  降级为可替换的传感器（sensor）
证据 / 因果 / 验证 / 信任 / 恢复  →  升级为核心 Runtime
```

传感器是可替换的：截图、DOM、无障碍树、Canvas scene model、未来的原生工具声明——
哪个准用哪个，哪个被模型能力吃掉就换掉，**它们不构成护城河**。

Runtime 不是可替换的：它负责把「传感器看到的东西」变成「可信的事实」，
并在事实不足时**承认不足**而不是猜测。这是本项目的长期价值所在。

> **Agent-Native Web 的长期价值，不是帮助 Agent 看见，而是让 Agent 不必猜。**

## 1. 问题：开环控制 + 系统性乐观偏差

### 1.1 开环控制在有扰动时必然发散

控制论里，开环系统不观测输出、只按预设输入执行。只要环境有扰动，误差就会累积且无法修正。网页环境恰恰是扰动密集的：

```text
异步渲染 · 网络延迟 · 请求竞态 · 局部刷新 · 反爬拦截 · 弹窗遮挡 · 受控组件重置
```

### 1.2 模型的失败模式不是「做错」，是「以为做对了」

这是本命题最关键的一点。常见的 agent 失败不是选错了按钮，而是：

- 点击后页面没反应 → 认为「应该生效了」→ 继续下一步；
- 表单提交返回 422 → 没有观察到 DOM 变化 → 认为「提交成功」；
- 登录墙拦截 → 没识别 → 继续在错误页面上操作；
- 页面已跳转但目标区域无变化 → 判定「失败」→ 重复硬点。

**为什么模型会这样？** 因为它的训练目标是完成任务，不是承认不知道。观察不到反向信号时，它的先验是成功。所以它不是在「猜」，是在**押注自己赢**。

### 1.3 推论：最值钱的不是「成功」，是「失败」

| 状态 | 模型能否自行推断 | 价值 |
|---|---|---|
| 生效了（`progressed`） | **能**——观察到变化即可 | 低（模型本来就会猜对） |
| 没生效（`unchanged`） | **不能**——它需要外部权威反驳它 | **高** |
| 不知道（`uncertain`） | **不能**——默认会被塌缩成「成功」 | **最高** |

> 这是本项目的真正价值主张，比「原生网页世界」准确得多：**让智能体不再猜**。

## 2. 关键区分：感知层 vs 验证层（以及验证层内部的再切分）

### 2.1 第一刀：感知 vs 验证

| | **感知层** | **验证层** |
|---|---|---|
| 问题 | 按钮在哪、页面结构是什么、目标元素是哪个 | 这个动作到底生效了没有 |
| 本质 | 信息**存在**，但编码对模型不友好 | 需要**缺失的外部事实** |
| 角色 | **可替换的传感器** | **核心 Runtime** |
| 会被模型能力吃掉吗 | **会，而且很快**（视觉 / 长上下文 / computer use 都在进步） | **部分会，部分永远不会**（见 2.2） |
| 典型失败 | 定位慢、选错元素、读不完页面 | 重复提交、以为登录了其实没登、以为下单了其实 422 |
| 项目对应资产 | 编号 / 语义名 / 导览图 / 地图 / 区域钻取 | 后果卡 / `evidence_seq` / `sources` / 静默失败归因 |

### 2.2 第二刀（关键修正）：验证层内部仍要再切一刀

**不能说「验证瓶颈不会被模型能力吃掉」——这个说法过于绝对。** 验证层里有两类东西：

| | **可被模型能力改善的部分** | **不可能靠模型 scaling 解决的部分** |
|---|---|---|
| 内容 | 从已有观察中做更准的判断 | 缺失的外部证据、权威状态、因果关系、来源身份 |
| 例子 | 截图里清楚写着 `Success` / `Payment complete`，更强视觉模型判得更准 | 见下方五个反例 |
| 结论 | 会被吃掉，**不要在这里建护城河** | **逻辑上不可能**，是 observability 问题 |

**五个反例（模型再强也推不出来）**：

```text
① 页面显示成功，后台请求其实 422
② 按钮变灰，但请求后来 rollback
③ POST 返回 202，后台任务 30 秒后失败
④ DOM 显示 $100，真正账本仍然是 $0
⑤ 页面发生变化，但这是 websocket 后台刷新，不是刚才这个 click 引发的
```

这些信息**不存在于任何观察里**。模型再聪明也无法从不存在的信息中可靠推出事实。
**这不是 intelligence problem，是 observability / evidence problem。**

所以精确的表述是：

> **验证中需要「缺失的外部证据、权威状态、因果关系和来源身份」的部分，
> 不可能靠单纯模型 scaling 凭空解决。**

而 Runtime 的职责正是补上这四样：**证据**（evidence）、**权威状态**（authoritative state）、
**因果关系**（causality）、**来源身份**（provenance）——并在补不上时明确报 `uncertain`。

### 2.3 由此得出的资源分配原则

```text
感知层（编号/导览/地图/地形）      →  可替换传感器  →  降级为实验，不投入主线
验证层·可判断部分（更强视觉判读）  →  会被模型吃掉  →  不建护城河
验证层·外部事实部分（证据/权威/因果/身份）→  逻辑不可能  →  核心 Runtime，最高优先级
```

**反过来说**：凡是「模型看一眼就能知道」的能力，做深了也会被下一代模型抹平。
凡是「环境才知道、观察里没有」的事实，做深了会随模型变强而更值钱。

### 2.4 补充：模型可进步的部分也在变，但边界不变

随着模型变强，2.2 左栏（可判断部分）的边界会外移——今天需要外部证据的，明天可能看一眼就够。
但右栏的四类东西**不会**外移，因为它们缺的是信息本身，不是推理能力。

**这意味着 Runtime 的设计必须能容忍传感器被替换**：当某个传感器（比如截图判读）变得足够强时，
Runtime 应该能把它当输入源之一接进来，而不是把它当竞争对手。

## 3. 机制：验证闭环由三层组成

### 3.1 因果窗口绑定——把动作和后果锁在一起

单看 DOM 变化无法判断因果（页面自己也在动）。必须把 `action` 生命周期、网络事件、DOM 变化放进同一条有序时间线，用**窗口**归属：

```text
seq=10 action    world_click start(el_79)
seq=11 request   github.com/git/git/pulls
seq=12 response  200 text/html          ← 归因到 seq=10 的动作
```

没有这一步，「页面变了」和「我的动作生效了」无法区分。

### 3.2 信任分层——决定「这句话能不能当指令」

`sources` 四类标注是本项目**最被低估的设计**，它解决的不是生效性，而是安全边界：

| 类别 | 内容 | 可信度 |
|---|---|---|
| `fact` | URL / 编号 / 坐标 / 指纹 / 序号 | 可信 |
| `evidence` | 动作前后差分 | 可信 |
| `inference` | 导览 / 处方 / 建议 | 仅参考 |
| `untrusted` | 页面自由文本（name / text / aria-label / placeholder） | **绝不当指令执行** |

五态解决**正确性**（生效了吗），四类解决**信任性**（这句能不能信）。后者更难抄——它需要整条管道自洽（`evidence_seq`、`world_epoch` 失效、IPI 过滤），不是加个字段就有。

### 3.3 五态出口——给模型一个「说不知道」的合法选项

```text
progressed  确定生效
challenged  被拦住（明确转人工）
errored     明确失败（带结构化原因）
uncertain   有变化但不知道有没有生效   ← 核心：把「未知」从两端拆出来
unchanged   确实没生效
```

默认 agent 的行为是二值的：观察到变化 → 成功；没观察到 → 失败（或更糟，假设成功）。歧义全部塌缩到两端。**`uncertain` 是把「未知」显式化的那一态，也是别的方案没有的一态。**

## 4. 边界：这个命题只在两个条件下成立

必须写死，否则会被反例打穿。

### 4.1 成立条件

```text
高环境不确定性  ×  高假成功代价
```

- **高环境不确定性**：异步状态、多步表单、有副作用的提交、跨页面流程；
- **高假成功代价**：重复提交、重复下单、误以为已授权、误以为已保存。

### 4.2 不成立（或增益趋零）的场景

- 静态信息检索：读文档、抽表格、单页问答——模型看一遍就够，反馈层增益 ≈ 0；
- 低代价动作：搜索页点错链接，代价为零；
- 有明确 API / WebMCP 原生工具的场景——网站已经提供了权威反馈，不需要重建。

> 项目自己的 A/B 数据已印证：任务图复用**没有提速**（66.9s vs 70.0s，慢 4.6%）。
> 增益只在高不确定性任务上出现，且必须实测，不能假设。

### 4.3 「完整」是个危险的词

反馈的目标**不是完整，是充分且可信**。完整 = 上下文洪水，等于把「整页信息洪水」复制成多个版本。

准确措辞是：**及时、准确、可判定、带信任级别**。没有「完整」。

（项目自己的时间线 A/B 已得出正确结论：**价值在「信息」不在「工具」**——由 harness 每步自动注入压缩摘要，而不是让模型主动调工具。）

## 5. 可证伪的预测

本命题必须可测，否则只是信念。

| # | 预测 | 证伪条件 |
|---|---|---|
| P1 | 同一模型，验证层开/关，增益在**高环境不确定性任务**上显著，在静态阅读任务上不显著 | 若两类任务增益无差异 → 命题不成立 |
| P2 | 增益随模型能力提升，在**感知维度**与**验证层的可判断部分**衰减，在**验证层的外部事实部分**不衰减 | 若外部事实部分的增益也随模型变强而消失 → 该部分也会被吃掉，需重写命题 |
| P3 | `unchanged` / `uncertain` 出现率下降 ⇒ 重复动作率下降 ⇒ 假成功率下降（三者强相关） | 若三者不相关 → 卡没有真正改变行为 |

**P2 最关键**，也是最需要小心的一条：它必须**分层测**，不能笼统测"验证维度"。

做法：构造两组任务——
- **A 组（可判断）**：成功信号在观察里可见（截图写着 Success），预期强模型不需要外部证据也能判对；
- **B 组（外部事实）**：成功信号不在观察里（显示成功但后端 422、202 后异步失败、DOM 值 ≠ 账本值、变化非本动作引起）。

若 A 组增益随模型变强衰减、B 组不衰减 → 命题成立，且给出了 Runtime 的精确边界。

### 5.1 现有实验的轴选错了

`mcp/experiments/astra_canvas_phase1/`（issue #16）的 A/B/C 测的是「结构化接口 vs 视觉」——**那是感知维度**，正好是被模型能力吃掉的那一半，而且用最强模型去测，等于主动选了一个会输的战场。

**应该测的轴**：同一模型，**验证层开 / 关**，并按上文的 A 组 / B 组任务分层。

## 6. 决策判据

新增任何功能 / 文档 / 实验前，按顺序回答：

```text
1. 它是在造传感器，还是在造 Runtime？
     传感器（感知层） → 可替换，降级为实验，不进主线，不写规格
     Runtime（证据/因果/验证/信任/恢复） → 优先级最高，必须配测试与守护

2. 它需要的信息，模型自己能不能推出来？
     能推出来（观察里已有） → 会被下一代模型抹平，不值得长期投入
     推不出来（观察里没有） → 属 observability 问题，随模型变强更值钱

3. 它属于验证层的哪一半？
     可判断部分（更强视觉/推理能解决） → 不建护城河，但要能当输入源接进来
     外部事实部分（证据/权威/因果/身份） → 核心 Runtime

4. 它有没有可证伪的判据？
     没有 → 不许写成规格文档，只能进 docs/archive/ 或实验目录

5. 它是否只在高不确定性 × 高代价场景有效？
     是 → 明写边界，不许宣称通用
```

## 7. Runtime 的四个职责（对应四类缺失事实）

| 职责 | 补的是什么缺失 | 现有对应资产 |
|---|---|---|
| **证据（evidence）** | 页面之外的动作后果（网络状态码、控制台错误、异步结果） | 静默失败归因、因果窗口 |
| **权威状态（authoritative state）** | 观察里没有的真值（账本、后端状态、任务是否真完成） | 待建：外部权威接入点 |
| **因果关系（causality）** | 「变化是我的动作引起的」还是「后台自己动的」 | 统一时间线、`evidence_seq` |
| **来源身份（provenance）** | 这句话是事实、证据、推断，还是不可信文本 | `sources` 四类标注 |
| **恢复（recovery）** | 事实不足时怎么办，而不是猜 | `uncertain` + 预算铁律 + `handoff` |

> 前四类决定「能不能知道」，第五类决定「不知道时会不会乱来」。
> 五态里的 `uncertain` 正是第五类的具体形式。

## 8. 与项目现有资产的关系

| 资产 | 归属 | 处置 |
|---|---|---|
| 统一后果卡 `page_outcome` 五态 | Runtime | **核心**，最高优先级，必须被测试守护 |
| `sources` 四类信任标注 | Runtime + 安全 | **核心**，被低估，应对外主张 |
| `evidence_seq` / `changes_seq` 对账 | Runtime | 核心，需外部消费者 |
| 因果窗口 / 统一时间线 | Runtime | 核心（信息注入，非工具） |
| 静默失败归因（4xx/5xx/console） | Runtime | 核心 |
| 编号 / 语义名 / 导览图 / 地图 / 地形 | 传感器 | 保留，但**降级为实验**，不再写新规格 |
| 任务图 / 业务运行时 / 站点适配器 | 传感器（且已实测无增益） | 冻结，见治理台账 |
| IPI 伪隐藏过滤 | 安全 | 保留，边界已声明 |

## 9. 一句话总结

> **「原生网页世界」是实现方式，「让智能体不再猜」是问题。**
> 把问题当第一性陈述，项目立刻变得可判断、可取舍、可证伪。
> 把实现方式当第一性陈述，就会堆出 40 个工具，没有一个是可删的。

> **不是帮助 Agent 看见，而是让 Agent 不必猜。**
