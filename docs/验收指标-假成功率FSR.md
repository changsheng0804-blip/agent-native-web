# 验收指标：假成功率 FSR

> 状态：提案 · 2026-09-29 · 纯文档，不改动代码

## 一、这份文档要解决什么问题

本仓库的核心主张是：感知（DOM、无障碍树、截图）是可替换的传感器，真正的内核是证据、因果、验证、信任与恢复。`world_act` 的五态回执 `page_outcome`（`progressed` / `challenged` / `errored` / `uncertain` / `unchanged`）就是这个主张的落点：它回答"这次动作到底发生了什么"，而不是"页面现在长什么样"。

现有门禁已经把假阳性当成零容忍的否决项。但门禁只能回答一个问题：有没有退步。它回答不了另外两个：

1. **现在到底有多好？** 全绿只说明没踩已知的坑，没有任何数值。
2. **外部的人怎么引用？** 他们不会读代码，也不会跑测试，需要一个可复算、可挑战的数字。

所以缺的不是更多功能，是一个数字。这份文档定义那个数字：**当运行时说"这一步做完了"，这句话有多大概率是假的。**

## 二、为什么盯"假成功"，而不是笼统的准确率

两个方向的错，代价完全不对称。

- **假成功**（实际没生效，却报成功）：用户在不知情的情况下承担后果。最典型的是以为付款没成功而再付一次。
- **假失败**（实际已生效，却报失败）：用户多确认一句，或者多问一次。

所以主指标只盯一个方向，否决权也只给这个方向。假失败单独记录、跟踪趋势，但不拦车。这和仓库现有的假阳性否决取向是一致的，只是把定性的"不许有"换成了定量的"等于 0"。

## 三、与现有设计的关系

| 现有的东西 | 本指标怎么用它 |
|---|---|
| `page_outcome` 五态 | 直接作为输入，不新增状态 |
| 小票标准 `page_receipt` | 在回执上新增两个字段：证据强度分数、证据等级 |
| `run_quality.py` 门禁 | 新增一个 scope `fsr`，并加一条否决规则 |
| 假阳性零容忍 | 由定性否决变成一个可复算的数值门槛 |

## 四、三个数字，其中只有一个是主指标

| 指标 | 定义 | 目标 |
|---|---|---|
| **FSR@C**（假成功率） | 在覆盖率被校准到 C 时，判定为 `progressed` 但后端实际未生效的动作，占全部 `progressed` 判定的比例 | 等于 0 |
| **FNR@C**（假失败率） | 后端实际已生效，却被判定为 `errored` 或 `unchanged` 的比例。它是重复下单、重复付款的来源 | 记录并跟踪，不作否决 |
| **Coverage**（覆盖率） | 运行时给出确定判定的比例，等于 1 减去 `uncertain` 的占比 | 报告实测值，比较时固定在 80% |

## 五、覆盖率必须固定，否则这个指标可以被刷满分

任何系统只要对每一次动作都回答 `uncertain`，假成功率立刻变成 0，但它同时什么都没做成。所以单独报 FSR 没有意义，必须在同一覆盖率下比较。

做法：让运行时为每次判定额外输出一个**证据强度分数**（取值 0 到 1），扫描阈值得到一条"覆盖率对假成功率"的曲线，取覆盖率等于 80% 那一点作为 FSR@80，同时把整条曲线附在报告里。

这是运行时唯一需要新增的判断性字段，其余全部复用现有回执。建议同时标注**证据等级**：页面内观测为二级，带外核对（确认邮件、扣款流水、回到订单历史重读）为一级。原因是页面推导出的回执本质上还是商家用自己的话在自证，页面没有义务说实话；最硬的证据在带外。

## 六、真值由夹具自带，不靠人工标注

每个夹具由两部分组成：一个本地页面，和一个本地后端。页面负责制造各种"看起来成功"的假象，后端负责如实记录这次动作到底有没有落库。测试跑完直接读后端，就是真值。

这一条决定了这套指标能不能天天跑：一旦需要人去标注，它就只会跑一次。

## 七、夹具按失败模式分类，不按网站分类

按网站分类会跟着网站改版腐烂；按失败模式分类才稳定。十类模式覆盖了绝大多数假成功的来源。每类至少 20 次动作，真成功与真失败的比例固定在 6 比 4，总量不少于 200 次。

| # | 失败模式 | 正确的判定 |
|---|---|---|
| 1 | 静默拒收：前端看起来填进去了，后端没收到 | 不得判 `progressed` |
| 2 | 遮挡拦截：提交按钮被浮层盖住，点击落在别的元素上 | `errored` 或 `unchanged` |
| 3 | 请求失败无提示：点击后接口返回 500，页面毫无变化 | `errored` |
| 4 | 页面说谎：显示"提交成功"，后端没有记录 | `uncertain` 或 `errored`，绝不能 `progressed` |
| 5 | 慢落库：3 到 10 秒后才写入，过早观测会误判 | `uncertain`，或等待后判 `progressed` |
| 6 | 重复提交诱导：第一次其实已成功但页面无反馈 | 必须判出已生效，这条专测假失败 |
| 7 | 路由变化无状态变化：SPA 换了地址，数据没动 | `unchanged` |
| 8 | 挑战页：验证码或二次验证拦截 | `challenged` |
| 9 | 正常成功（对照组） | `progressed` |
| 10 | 正常失败（对照组） | `errored` |

第 9、10 类是对照组，用来确认系统不是靠"一律保守"换来的低假成功率。

## 八、报告只有一页，最值钱的是失败样本本身

报告分四块：

1. 主表：FSR@80、FNR@80、实测覆盖率、样本量
2. 按失败模式分解的表
3. 每一个假成功案例的完整证据卡快照
4. 与上一次基线的差异

第三块才是这份报告真正的价值。一个数字只告诉你好坏，一张证据卡才告诉你为什么错。

## 九、通过门槛

**FSR@80 等于 0 才算绿。** 假失败进趋势图，恶化时告警但不否决。覆盖率同时报出，若覆盖率跌破 60%，即便 FSR 为 0 也要标注，因为那说明系统是靠大量"我不确定"换来的。

## 十、落地六步

1. 在回执上新增两个字段：**证据强度分数**（0 到 1），以及本次结论用到的**证据等级**（页面内观测为二级，带外核对为一级）。
2. 按第七节的表建十类夹具，每类一个页面加一个记录真值的本地后端，统一暴露一个读真值的接口。
3. 写一个跑批脚本：依次执行全部动作，记录每次的判定、证据强度、耗时，再从后端读回真值。
4. 按阈值扫描生成覆盖率与假成功率的曲线，取覆盖率 80% 处的值作为 FSR@80 与 FNR@80。
5. 输出 `metrics.json`（结构见下），并渲染成一页 Markdown 报告，假成功案例逐条附上证据卡原文。
6. 挂进 `run_quality.py` 作为新 scope `fsr`，并在门禁里加一条：FSR@80 大于 0 直接否决。

## 十一、一句话总结

把"这个运行时很谨慎"换成一个别人可以复算的数字。只要 FSR@80 长期为 0 而覆盖率不塌，这个方向就不再是理念，而是一条可被引用、可被复现、也可以被别人挑战的结论。
