# 验收指标：假成功率 FSR

> 状态：提案（第二稿，已按 Codex-gpt-6.1 评审意见修订） · 2026-09-29 · 纯文档，不改动代码

## 一、背景：现有的是什么，缺的是什么

本仓库的核心主张是：感知（DOM、无障碍树、截图）是可替换的传感器，真正的内核是证据、因果、验证、信任与恢复。`world_act` 的五态回执 `page_outcome` 就是这个主张的落点，它回答"这次动作到底发生了什么"。

现有基线并非没有测量。`mcp/test_receipt_metrics.py` 已经同时统计"失败判成功"和"成功判失败"，并要求两者均为零。所以缺的不是"有没有数"，而是：

**缺少一个有统一分母、固定测试条件、并受覆盖率约束的可比较比例。**

具体说，现有统计回答不了三件事：一是样本集不固定，数值不能跨版本比较；二是没有覆盖率约束，一个大量回答"不确定"的系统同样能拿到零错误；三是没有区间估计，"零次"不等于"概率为零"。这份文档补的就是这三样。

## 二、先定义"成功"是什么，否则整个指标会算错

这是评审提出的第一个问题，也是本稿改动最大的地方。

`aw_outcome.py` 里的 `progressed` 表示**页面动作有进展**，包含填表、导航、弹窗、视觉变化。它不等于订单已保存或付款已完成。如果一律拿"后端有没有写入业务记录"当真值去评判所有 `progressed`，正常的填表动作会被误算成假成功。

所以成功分两层，每个夹具在跑之前**预先声明**本次动作属于哪一层、以及判定成功的检查点：

| 层级 | 动作类型 | 真值检查点 |
|---|---|---|
| 动作级 | 填表、导航、展开、选择 | 动作声称的直接后果是否成立：输入框的值是否等于目标值，视图是否确实切换 |
| 业务级 | 提交、下单、付款、不可逆操作 | 后端是否产生了与本次动作关联的业务记录 |

对应地，主指标也分开算：

- **FSR-业务**：只在业务级动作上计算，这是主指标。
- **FSR-动作**：只在动作级动作上计算，单独报告。

第七节表中第 7 类"路由变化无状态变化"因此也要结合动作目标判定：如果动作目标就是导航，那么路由变化本身就是动作级成功；只有当动作目标是提交业务时，路由变化而业务记录未产生才算未生效。这条不改变现有导航语义。

## 三、为什么主指标盯假成功，以及假失败在哪些场景必须硬约束

两个方向的错，后果不同：

- **假成功**（未生效却报成功）：用户不再跟进，以为事情办完了，实际订单根本不存在。等发现时往往已过时限。
- **假失败**（已生效却报失败）：用户或上层系统会重试。在付款、下单这类不可逆动作上，重试就是重复扣款。

第一稿把"以为付款没成功而再付一次"写成假成功的后果，与第四节的假失败归因自相矛盾，本稿已更正：**重复付款是假失败的后果**，不是假成功的后果。

结论保持"主指标只有一个"，但假失败不再是"只记录不否决"：

- 全局假失败：记录趋势，不否决。
- **高风险场景（付款、下单、不可逆提交）的假失败：设上限，超过即否决。**
- 并要求被测系统遵守一条行为约束：**在重试任何高风险动作之前，必须先核对原动作的结果**，不得因一次失败判定直接重放。

## 四、指标定义

| 指标 | 定义 | 门槛 |
|---|---|---|
| **FSR-业务@C**（主指标） | 覆盖率校准到 C 时，业务级动作中判定为成功但真值未生效的数量，除以该层全部成功判定数 | 观察到 0 次 |
| **FSR-动作@C** | 同上，在动作级动作上计算 | 观察到 0 次 |
| **FNR@C** | 真值已生效、却被判为 `errored` 或 `unchanged` 的数量，除以**阈值筛选后仍保留判定的真实已生效动作数**（被改判 `uncertain` 的不计入分子也不计入分母，但计入覆盖率损失） | 全局记录趋势；高风险场景设上限 |
| **Coverage**（覆盖率） | 给出确定判定（`progressed` / `errored` / `unchanged` / `challenged`）的动作数除以总动作数，等于 1 减去 `uncertain` 占比 | 固定在 80% 比较 |
| **成功召回率** | 判定为成功且真值已生效的数量，除以全部真值已生效的动作数 | 不低于 0.70，低于即不通过 |

`challenged` 计入覆盖率（它是一个明确结论），但不进入 FSR 分母（它没有声称成功）；若真值显示该动作其实已生效，则计入假失败。

## 五、防刷规则

评审指出，按第一稿的定义，一个全部回答 `unchanged` 的系统仍有 100% 覆盖率，而 FSR 分母为零。以下规则堵住这类退化：

1. **分母为零不可计算，且不通过。** 成功判定数为零时，报告写"不可计算"，门禁按失败处理。
2. **成功召回率下限 0.70。** 这条直接否定"一律报失败"的策略。
3. **取点规则。** 按证据强度阈值从高到低扫描，取第一个覆盖率大于等于 80% 的点；分数相同导致覆盖率跳变时取保守的一侧（覆盖率更低、错误更少的那个点不得被采用，必须取实际达到 80% 的那个点）。
4. **原始确定判定率不足 80% 时报"不可计算"**，不允许用低覆盖率下的零错误代替 FSR@80。
5. **低分判定必须在运行时真的改判 `uncertain`**，而不是只在报告里剔除。报告口径必须与线上行为一致。
6. **阈值标定与最终评估分开。** 证据强度分数必须在不知道真值的情况下产生；阈值在独立的标定集上确定，评估在保留集上进行，不得对同一批错误反复挑选有利阈值。

## 六、真值：由夹具自带，并明确时间与关联

每个夹具由一个本地页面和一个本地后端组成。页面制造各种"看起来成功"的假象，后端如实记录这次动作有没有落库。测试跑完直接读后端即为真值，不需要人工标注，所以这套指标能天天跑。

评审要求明确的三件事：

- **读取期限与超时语义。** 每个夹具声明一个真值读取窗口（默认 15 秒）。窗口内未出现记录即判未生效；窗口外才出现的，单独计为"超期生效"，不计入 FSR 分子，但必须在报告中列出。
- **动作关联标识。** 每次动作携带一个唯一关联标识（幂等键），真值查询按该标识匹配，用于区分"本次提交成功"和"此前已有记录"。
- **接口隔离。** 真值读取接口仅供测量程序使用，被测系统不得访问；被测系统只能使用明确允许的证据渠道。

## 七、证据等级必须记录来源与独立性

- **二级**：页面内观测（DOM 变化、网络响应、控制台、视觉差异）。
- **一级**：带外核对（确认邮件、扣款流水、在另一条路径上重读订单记录）。

评审的更正已采纳：**同一商家的另一个页面不自动等于独立权威来源**。因此证据条目必须同时记录三项：来源、是否与被测动作路径独立、以及关联依据（凭什么认定这条证据说的就是这次动作）。理由是，页面推导出的回执本质上仍是商家用自己的话在自证，页面没有义务说实话。

## 八、夹具：按失败模式分类，不按网站分类

按网站分类会随改版腐烂；按失败模式分类才稳定。

| # | 失败模式 | 正确的判定 |
|---|---|---|
| 1 | 静默拒收：前端看起来填进去了，后端没收到 | 不得判成功 |
| 2 | 遮挡拦截：提交按钮被浮层盖住，点击落在别的元素上 | `errored` 或 `unchanged` |
| 3 | 请求失败无提示：点击后接口返回 500，页面毫无变化 | `errored` |
| 4 | 页面说谎：显示"提交成功"，后端没有记录 | `uncertain` 或 `errored`，绝不能判成功 |
| 5 | 慢落库：超出读取窗口才写入 | `uncertain`，或按第六节计为超期生效 |
| 6 | 重复提交诱导：第一次其实已成功但页面无反馈 | 必须判出已生效，这条专测假失败 |
| 7 | 路由变化无状态变化 | 按第二节的动作目标判定 |
| 8 | 挑战页：验证码或二次验证拦截 | `challenged` |
| 9 | 正常成功（对照组） | 判成功 |
| 10 | 正常失败（对照组） | `errored` |

样本口径（评审指出第一稿自相矛盾，本稿限定适用范围）：

- 6 比 4 的真成功与真失败比例**只适用于第 1 到 8 类**；第 9 类全部为真成功，第 10 类全部为真失败，它们是对照组，用于确认低假成功率不是靠"一律保守"换来的。
- 每类不少于 20 次动作，总量不少于 200 次。
- **必须区分"不同案例"与"同一案例的重复执行"**，两者在报告中分别计数；重复执行不用于夸大样本量。

## 九、报告口径

报告分五块：

1. 主表：原始计数（总动作数、成功判定数、各状态计数）、FSR-业务@80、FSR-动作@80、FNR@80、成功召回率、实测覆盖率。
2. 按失败模式分解的表。
3. 每一个假成功案例的完整证据卡快照。
4. 覆盖率对错误率的整条曲线。
5. 与上一次基线的差异。

**表述约束。** 不写"假成功率为零"，写"在本固定测试集上观察到 0 次假成功，95% 置信上限为 x%"（有限样本下用 Clopper-Pearson 单侧上限）。这份报告不承诺现实世界的错误概率为零，只承诺在这个固定测试集上的观察结果可复算。

第三块才是报告真正的价值：一个数字只告诉你好坏，一张证据卡才告诉你为什么错。

## 十、通过门槛

- FSR-业务@80 与 FSR-动作@80 均观察到 0 次，否则否决。
- 成功召回率不低于 0.70，否则否决。
- 成功判定数为零，或原始确定判定率不足 80%，判"不可计算"，按失败处理。
- 高风险场景的假失败超过上限，否决。
- 覆盖率低于 60% 时即便无错也须在报告中显著标注。

## 十一、落地六步

1. 在回执上新增两个字段：**证据强度分数**（0 到 1，必须在不知真值的前提下产生），以及每条证据的**来源、独立性、关联依据**。
2. 按第八节建十类夹具，每类一个页面加一个记录真值的本地后端；每个夹具预先声明动作目标、成功层级与检查点。
3. 写跑批脚本：执行全部动作，记录判定、证据强度、耗时与关联标识，再按关联标识从后端读回真值。
4. 在标定集上按阈值扫描定阈值，在保留集上计算 FSR-业务@80、FSR-动作@80、FNR@80、成功召回率与置信上限。
5. 输出 `metrics.json`（结构见下），渲染成一页报告，假成功案例逐条附证据卡原文。
6. 挂进 `run_quality.py` 作为新 scope `fsr`，门禁加入第十节的全部否决条件。

## 十二、待标定的参数

以下数值是初始约定值，不是实证结论。第一轮实测后应按实际曲线形状重新标定，并在文档中记录改动理由：

| 参数 | 初始值 | 依据 |
|---|---|---|
| 目标覆盖率 | 80% | 约定，待首轮曲线标定 |
| 覆盖率告警线 | 60% | 约定 |
| 样本量 | 不同案例不少于 120，总动作不少于 200 | 约定，需按置信上限倒推 |
| 成功召回率下限 | 0.70 | 约定 |
| 高风险假失败上限 | 待定 | 需先收集基线 |
| 真值读取窗口 | 15 秒 | 约定，按夹具可覆盖 |

方法学依据：错误率与覆盖率联合评估见 [SelectiveNet](https://proceedings.mlr.press/v97/geifman19a.html)；有限样本比例的区间估计见 [NIST 方法说明](https://www.itl.nist.gov/div898/handbook/prc/section2/prc241.htm)。这两份资料支持"必须联合覆盖率评估"和"必须给区间"的做法，但不能证明 80% 或 200 次适合本项目，所以上表全部标为待标定。

## 十三、一句话总结

把"这个运行时很谨慎"换成一个别人可以复算的数字。只要 FSR-业务@80 在固定测试集上持续观察到 0 次，而覆盖率与成功召回率都不塌，这个方向就不再是理念，而是一条可被引用、可被复现、也可以被别人挑战的结论。

```

python -m pip install -r 依赖锁定-requirements.txt
python -m playwright install chromium
python mcp/run_quality.py --parallel 3
→ 通过 37/37  总耗时 246.3s  (并行 ×3)
```

首两次运行曾出现 31 至 33 项失败，经排查全部为运行环境问题，与仓库代码无关：一是本机预装的浏览器版本与 `依赖锁定-requirements.txt` 锁定的 playwright 1.62.0 所需版本不一致；二是 MCP 的 stdio 客户端只向服务器子进程透传白名单环境变量，导致浏览器路径变量丢失。两次的 31 至 33 项失败均塌在同一处 `pw.chromium.launch()`，耗时与报错形态完全相同。

附带建议（不属于本 PR 范围）：浏览器启动失败时，把 playwright 的原始报错与"期望版本对实际安装版本"直接写进 `world_open` 的后果卡，而不是让异常冒成非 JSON 文本。当前表现容易让人误判为几十个守护面同时失效，实际只是一个环境变量。
