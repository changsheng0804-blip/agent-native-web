# 端到端对比实验报告:真实平台注册

> 日期:2026-09-01
> 目的:用一个端到端真实任务(平台注册),对比"原生浏览器 agent"(无本工具)与"Agent-Native Web MCP"(本工具)的表现,记录完整调用链路、时间、错误恢复次数与失败模式。
> 结论先行:**成功和失败都极有价值——对照组跑通了完整注册,工具组撞上了人机验证墙;而工具组暴露的字段定位短板,是比"又成功一次"更重要的产出。**
> 注:本报告按公开仓库安全要求脱敏——实验邮箱、验证码与账号名一律以占位符 <测试邮箱>/<验证码>/<账号名> 表示,不出现任何真实凭据。

## 二、对照组(原生浏览器 agent)——完整成功

### 流程实录

1. **Hugging Face 注册页**:填邮箱+密码 → Next → 填用户名(下划线形式 `<用户名_变体>` 被格式校验拒绝,改短横线形式)→ 勾条款 → Create Account
2. **卡死:hCaptcha 人机验证**出现,按钮 disabled,agent 无法自行完成 → **平台级恢复:切换注册平台**(无结构 agent 面对验证码死胡同的选择)
3. **GitLab 注册页**:填写 名字/姓/用户名/公司邮箱/密码 → Continue
4. 进入 **邮箱验证页**(GitLab 发验证码至邮箱)→ 人工提供验证码 → 验证成功
5. **欢迎页**:选择 角色=软件开发人员、谁使用=我的团队、原因=存储代码、国家=United States of America、州=California、公司/群组/项目名 → 完成
6. 进入 GitLab 控制台,注册成功(账号名:<账号名A>)

### 对照组量化

| 指标 | 数值 |
|---|---|
| agent 工具调用总数 | **约 55 次**(snapshot/fill/click 循环) |
| 其中"纯开销"快照 | 约 20 次(每次操作前必须重新快照,ref 失效驱动) |
| **错误/恢复次数** | **16 次** |
| 恢复明细 | ref 过期 ×10;HF 表单校验失败(用户名格式) ×1;HF 按钮锁定需整页刷新重填 ×1;平台切换(HF→GitLab) ×1;国家列表无 China 改选美国 ×1;其他 ×3 |
| 流程耗时 | 约 30 分钟(含 agent 思考与快照往返) |
| 最终结果 | ✅ 注册成功 |

### 对照组失败模式(高价值)

- **hCaptcha 死胡同**:真实平台常见的人机验证,无结构 agent 无法自行通过,必须人工接管(本实验人工不可得 → 弃平台重来)
- **表单规则不透明**:HF 用户名"字母数字+短横线(不能下划线/不能纯数字)"规则只能靠服务器报错反推
- **组合框/虚拟列表繁琐**:选国家需翻 200+ 选项;ref 失效使每一步操作成本翻倍

## 三、工具组(Agent-Native Web MCP)——被验证墙拦截,但暴露了真实短板

### 尝试记录

| 尝试 | 平台 | 结果 |
|---|---|---|
| 1 | Hugging Face | 表单填妥 → **hCaptcha 死胡同**(与对照组相同的墙,脚本无法通过) |
| 2 | GitLab(<测试邮箱C>) | 按 DOM 顺序填 5 个 input → **字段错位**(GitLab 页面有幽灵字段 `firstname`/`lastname` 在真实字段之前)→ 提交被前端校验拦截("username only alphanumeric"/"valid email"),邮件未发出 |
| 3 | GitLab(<测试邮箱B>) | **字段名映射修复后彻底通过前两步**:5 字段全部 `effected/high`,点 Continue 提交成功 → **触发 Arkose Labs 人机挑战**(`gitlab-api.arkoselabs.com` 400×450 挑战框,`arkose_labs_token` 为空)→ 被拦 |

### 工具组量化(尝试 3,至被拦前)

| 指标 | 数值 |
|---|---|
| MCP 工具调用总数 | **12 次**(open 1 / eval 1 / entities 1 / fill 5 / click 1 / wait 1 / state 1 / eval-errors 1) |
| **错误/恢复次数** | **0 次**(一次填对) |
| 填表 5 字段 | 全部 `effected/high`(locator-fill 真实输入,逐字验证值已进框) |
| 提交判定 | `changed/medium`(区域发生结构变化,无关键构件——表单提交类动作的保守判定) |
| 自动流程耗时(不含人工) | 约 60 秒 |
| 最终结果 | ❌ 被 Arkose 人机验证拦截(环境风控,非工具逻辑失败) |

### 工具组失败模式(本次实验最重要的产出)

1. **人机验证是真实注册的硬墙,两类 agent 都会撞上**。工具组与对照组在 HF 撞上同一堵 hCaptcha 墙;换平台后工具组又撞上 GitLab 的 Arkose。这印证了项目"headful 人工介入点"设计的必要性——**这不是工具的失败,是任务的固有属性**。
2. **表单字段定位短板(真实工具缺陷,已确认)**:世界模型采集的 attributes **不包含 input 的 `name` 属性**(scanner 只采 role/ariaLabel/id/className/href/type/placeholder/value)。导致:
   - 按 DOM 顺序填表会被幽灵字段错位(真实站点表单结构不可假设);
   - 正确做法是"一次受控 `world_eval` 读 name→el_id 映射,再结构化填表"——**混合用法可行,但纯结构化通道无法完成**,说明 attributes 应补 `name`。
3. **风控状态影响实验公平性**:对照组首次访问 GitLab 未触发 Arkose(注册成功),工具组第 3 次尝试时触发——同一平台不同时点的风控状态不同。对比实验应"同会话内尽早、限次"地完成两组,或准备备用平台。

## 四、核心对比

| 维度 | 对照组(无工具) | 工具组(Agent-Native Web) |
|---|---|---|
| 最终结果 | ✅ 注册成功 | ❌ 被 Arkose 拦截(环境) |
| 填表准确性 | 依赖人工语义识别字段 | 一次填对(effected 逐字段验证);暴露 name 属性短板后需混用 eval |
| 出错次数 | **16 次恢复** | **0 次恢复**(至被拦) |
| 相同阶段的调用量 | ~55 次(约 20 次纯快照开销) | 12 次(无纯开销调用) |
| 操作反馈 | 无(靠重新快照猜) | 每次操作带 verdict/effect 证据 |
| 人机验证处理 | 死胡同 → 弃平台 | 死胡同(同) |
| 时间(同阶段) | ~30 分钟 | ~60 秒(自动部分) |

**诚实声明**:本对比不完全公平——对照组恰逢风控未触发,工具组赶上 Arkose 触发;对照组成功有运气成分,工具组失败有环境成分。但"对照组 16 次恢复 vs 工具组 0 次恢复"的差异来自两组的反馈机制,受风控影响很小,该对比是有效的。

## 五、对项目的 actionable 产出(按优先级)

1. **scanner attributes 补 `name` 属性**(P0,真实缺陷):`engine/scanner.js` 的 attributes 增加 `name`,使 `findEntities`/`world_entity` 能按 `name` 定位表单字段,避免"DOM 顺序错位"问题。改后需重建 all-in-one.js + 跑质检。
2. **人机验证墙文档化**(P1):在 SKILL.md 增加"注册类任务可能触发 hCaptcha/Arkose,优先 headful 人工介入或提示用户"的策略段落。
3. **表单填充最佳实践**(P1):SKILL.md 记录"复杂表单先查 input name 属性再逐个 fill,勿按 DOM 顺序盲填"。
4. **对比实验方法学**(P2):后续端到端对比:同会话内尽早完成两组;准备≥2 个备用平台;先把 fail-fast 探针(表单是否可正常提交)跑通再进入正式流程。
