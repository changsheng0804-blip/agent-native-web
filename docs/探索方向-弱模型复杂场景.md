# 探索方向：弱模型下的复杂网页场景

> 版本：2026-09-02
> 状态：**待讨论方案，未验证**
> 背景：当前 SKILL 和工具集基于"强模型可以自行推理"的假设设计；本文针对弱模型（Flash 级别、廉价高频）+ 复杂场景（SPA 状态机、多步表单、弹窗嵌套、反爬干扰）这一更具挑战性的组合，提出工具层和 SKILL 层的改进方向。

---

## 一、问题定位

### 1.1 浏览器任务为什么普遍用弱模型

浏览器操作任务往往步骤多（10-30 步）、重复率高、等待时间多；用 frontier 模型（Claude 3.7/GPT-o1 级别）做每一步的判断，成本不可接受。实际部署中，**orchestrator 用强模型做任务分解，executor 用弱模型执行每一步工具调用**，是主流模式。

这个项目的 MCP 工具面对的 executor，很可能是：
- GPT-4o-mini / Claude Haiku / Gemini Flash 量级
- 上下文窗口有限（4k-8k 实际可用）
- 工具选择能力弱：倾向选列表中靠前的工具、重名工具易混淆
- 推理深度有限：无法在调用前综合多个工具的语义差异做出最优选择

### 1.2 弱模型失败的具体模式

| 失败模式 | 触发条件 | 当前工具集是否加重 |
|---|---|---|
| 工具选择混乱 | 多个工具语义相近 | **是**——4 条"发生了什么"信道 |
| 不知道什么时候停止 | 操作后缺乏明确的成功/失败判断 | 部分是 |
| 陷入重试循环 | 同一操作失败无恢复策略 | 是，SKILL 未提供退出条件 |
| 忽略弹窗/遮挡 | 多层 UI 同时存在 | 部分解决（obscured_note） |
| 把"我执行了"等同于"已成功" | 缺少强制验证步骤 | SKILL 建议但未强制 |

### 1.3 简单场景 vs 复杂场景的分界

**简单场景**：单页、静态结构、目标元素可见、操作即时生效、无弹窗遮挡。
这类场景当前工具已足够，弱模型也能处理。

**复杂场景**（本文关注对象）：
1. 输入触发联想下拉 → 必须从下拉选择而非直接提交
2. 多步表单 → 每步有验证、有条件跳转
3. 弹窗嵌套 → 点击触发 modal，modal 内再触发 confirm
4. SPA 无 URL 变化导航 → 内容区切换但 URL 不变
5. 页面局部刷新 → 滚动到某处触发懒加载
6. 登录墙中途出现 → 深层操作后跳转到登录页
7. 反爬 / 人机验证 → 结构化工具返回降级内容

## 二、工具层：正交合并提案

### 2.1 当前问题："发生了什么"被回答了四次

```
world_state          ── 当前页面状态（auth/dialogs/forms/page）
world_changes        ── 原始增量变化事件流（游标续读）
world_change_digest  ── 变化的语义摘要（counts + key）
world_evidence       ── 操作前后的证据对比（verdict/confidence）
```

弱模型面对这四个工具时，无法可靠地判断"这次应该用哪一个"——它们覆盖的语义空间高度重叠。实测中弱模型会：随机选一个、全都调一遍、或只用第一个然后停止。

### 2.2 合并方案（待讨论）

保持四个独立工具不一定错，但它们的**调用时机**应该由 SKILL 写死，而不是让 model 自行判断。

**方案 A：工具不变，SKILL 强制时序**（短期，零代码改动）

```
执行任何操作后，固定按此顺序：
  1. 读操作返回值中的 effect.verdict（不需要额外工具调用）
  2. 如果 verdict = no-change，调 world_state 看 dialogs/page
  3. 如果 verdict = effected 且任务需要跟踪后续变化，调 world_change_digest
  4. world_evidence 只在人工核查或 FP=0 验证场景使用，不进入常规流程
```

优点：零改动工具层，立刻可以更新 SKILL 测试效果。

**方案 B：参数化合并**（中期）

```
world_status(scope="page"|"changes"|"evidence", since=None)
```

- scope="page"：等价于当前 world_state
- scope="changes"：等价于 world_change_digest（摘要优先）
- scope="evidence"：等价于 world_evidence（最近一次操作）

三合一，弱模型只需要学一个工具名，用 scope 参数控制需要什么。

### 2.3 其他正交性问题（次优先级）

| 当前工具 | 问题 | 建议 |
|---|---|---|
| `world_entities` + `world_entity` | 单复数容易混淆 | 合并为 `world_query(ids?=[...], filter?={...})` |
| `world_layers` | 与 `world_map` 的用途区别不清晰 | 明确文档或合并进 `world_map(depth=2)` |
| `world_navigate` + `world_open` | 都可以打开新 URL | 明确分工：open=创建新实例，navigate=同实例内跳转 |

## 三、SKILL 层：从原则到决策树

### 3.1 当前 SKILL 的问题

现有 SKILL.md 是**原则性**的，适合强模型：
> "验证变化：查看操作返回值自带的 status 卡与 effect 证据，必要时调用 world_changes..."

"必要时"对弱模型是个无效指令——弱模型不知道什么是"必要"。

### 3.2 弱模型 SKILL 的设计原则

1. **决策由 SKILL 做，model 只负责执行**：把"什么情况下调哪个工具"写成判断树，不依赖 model 推理
2. **每步有明确退出条件**：不让 model 自行判断"应该继续还是停止"
3. **错误恢复路径显式列出**：失败后走哪里，写清楚，不让 model 自由发挥
4. **截图是最后兜底，不是可选项**：当两次重试都失败时，强制截图并停止

### 3.3 复杂场景通用决策树

```
┌─────────────────────────────────────────────────────┐
│ 进入新页面                                           │
│  → world_guide(task_hint)  【强制，不可跳过】        │
│  → 读 candidates，确认目标区域和候选入口             │
└─────────────────────────┬───────────────────────────┘
                          │
┌─────────────────────────▼───────────────────────────┐
│ 定位目标                                             │
│  → world_map(region=候选区域)  【先看局部地图】      │
│  → world_query(filter={name/role/text})              │
│  → 如果返回 0 个结果：扩大范围，再试一次            │
│  → 如果仍然 0 个：world_screenshot → 停止，报告     │
└─────────────────────────┬───────────────────────────┘
                          │
┌─────────────────────────▼───────────────────────────┐
│ 执行操作                                             │
│  → world_click / world_fill / world_press            │
│  → 【立即】读返回值中的 effect.verdict               │
└─────────┬───────────────────────┬───────────────────┘
          │ effected              │ no-change / timeout
          ▼                       ▼
┌─────────────────┐   ┌──────────────────────────────┐
│ 继续下一步      │   │ 第一次失败：                  │
│                 │   │  → world_state 看 dialogs     │
│                 │   │  → 有弹窗：先处理弹窗         │
│                 │   │  → 无弹窗：world_map 重新定位 │
│                 │   │  → 重试一次                   │
│                 │   └──────────────┬───────────────┘
│                 │                  │ 仍然失败
│                 │                  ▼
│                 │   ┌──────────────────────────────┐
│                 │   │ 第二次失败：                  │
│                 │   │  → world_screenshot           │
│                 │   │  → 停止，报告截图 + 失败原因  │
└─────────────────┘   └──────────────────────────────┘
```

## 四、七种典型难场景的处理模式

### 场景 1：输入触发联想下拉（autocomplete）

**典型失败**：fill 后直接 press Enter，联想词没有出现或 Enter 提交了空表单。

```
world_fill(id, text, type_delay_ms=30)
  → 读 effect.verdict
  → 如果 effected：world_state 看 dialogs 或 world_query(role="listbox"|"option")
  → 如果找到 listbox：world_click(正确 option 的 id)
  → 如果没找到 listbox（联想未触发）：world_wait(condition="listbox_appear", timeout_ms=2000)
  → 如果超时：降级为 world_press(id, "ArrowDown") 触发
  → 选中后验证：world_state 的 forms 字段确认输入值已更新
```

**不能做**：fill 完直接进下一步，假设联想已自动选择。

### 场景 2：多步表单（有验证错误）

**典型失败**：提交后出现 validation error，弱模型没有识别出来，继续后续步骤。

```
world_click(submit_button_id)
  → 读 effect.verdict
  → 如果 effected：world_state 检查 dialogs（弹窗错误） + world_query(role="alert"|class~"error")
  → 如果找到 error 元素：
      读 error 文本 → 映射到对应字段 → world_fill 修正该字段 → 重试 submit
  → 如果 no-change：
      说明 submit 没有触发（按钮未 active 或有前置条件未满足）
      → world_query(role="button", name~"submit") 确认按钮状态
      → 如果 disabled：找未填的必填字段 → 补填
```

**关键原则**：提交后必须主动寻找 error 信号，不能只看 verdict=effected 就认为提交成功。

### 场景 3：弹窗嵌套流程

**典型失败**：modal 打开后，弱模型继续对主页面操作，所有操作被 modal 遮挡失败。

```
任何操作返回 effected 后，先检查 world_state.dialogs
  → 如果 dialogs 有新增：
      立即切换上下文到该 dialog
      world_query(bounds=dialog的坐标范围) 获取 dialog 内元素
      完成 dialog 内的操作（confirm/close/select）
      验证 dialog 已消失（world_state.dialogs 变空）
      再继续主流程
  → dialog 关闭后，重新调 world_guide 刷新方向感
```

**不能做**：忽略 dialogs 字段，直接继续主页面操作。

### 场景 4：SPA 无 URL 变化导航

**典型失败**：点击导航项后，URL 没变，弱模型认为"没发生任何事"。

```
world_click(nav_item_id)
  → 读 effect
  → 如果 local_verdict=no-change 但 page.url 未变：
      → world_change_digest：看是否有大量内容区变化（main/article 区域）
      → 如果变化 counts > 10 且主要在 main 区域：认定为 SPA 导航成功
      → world_guide(task_hint) 刷新方向感，用新结构继续任务
  → 不要依赖 URL 变化作为唯一成功标准
```

**关键原则**：SPA 导航的"成功"标准是内容区变化，不是 URL 变化。

### 场景 5：目标在视口外（需要触发懒加载）

**典型失败**：world_query 找不到目标，弱模型报告"页面没有该元素"。

```
world_query(name/text~=目标) → 返回 0 个
  → 不能直接报告"找不到"
  → world_map 检查是否有 scroll/pagination 相关区域
  → 如果有无限滚动区域：
      world_click_at(x=中央, y=页面底部附近) 触发滚动
      world_wait(timeout_ms=1500)
      world_query 再次查找
  → 如果有分页：
      找到下一页按钮 → world_click → 重新查找
  → 重复最多 3 次，超过则截图报告
```

**当前限制**：没有专门的 scroll 工具；`world_click_at` 点底部是变通方法，需验证可靠性。
**待确认**：是否需要新增 `world_scroll(direction, distance)` 工具。

### 场景 6：登录墙中途出现

**典型失败**：深层操作跳转到登录页，弱模型没有识别出来，继续在登录页上按任务目标找元素。

```
每次 world_guide 或 world_state 都检查：
  → status.auth.loggedIn = false 且 page.url 包含 "login"|"signin"|"auth"
  → 立即停止当前任务
  → 报告：已跳转至登录页，需要人工登录后继续
  → 如果是 headful 模式：等待人工操作，再调 world_wait(condition="url_change")
  → 如果是 headless 模式：无法继续，任务终止，报告登录墙
```

**关键原则**：登录中断是任务级异常，不是步骤级错误，不能尝试"自动登录"。

### 场景 7：反爬 / 人机验证

**典型失败**：页面返回了简化内容或 CAPTCHA，弱模型仍然尝试按正常流程操作。

```
world_state.page.state = "anomaly" 或 world_guide 返回 candidates 为空
  → 立即调 world_screenshot
  → 分析截图中是否包含 CAPTCHA、验证码、人机验证区域
  → 如果是 headful 模式：暂停，等待人工通过验证
  → 如果是 headless 模式：任务终止，报告反爬拦截
  → 不尝试自动解决 CAPTCHA
```

## 五、SKILL 版本分层提案

现有 SKILL.md 是单一版本。建议拆分为两个版本：

```
skills/agent-world/
  SKILL.md              ── 通用版（当前，原则性，适合强模型/orchestrator）
  SKILL-executor.md     ── 执行版（新建，决策树，适合弱模型/executor）
```

**SKILL-executor.md** 的核心特征：
- 每步写明"如果 X，则调 Y；如果 Y 返回 Z，则执行 W"
- 不使用"必要时"、"酌情"、"根据情况"等模糊表达
- 失败路径和成功路径权重相同，不以成功为主线
- 明确标出"此步骤不可跳过"的检查点

## 六、需要验证的问题

以下问题目前没有答案，需要实验验证：

**关于工具层**
- 方案 A（SKILL 强制时序，工具不变）vs 方案 B（参数化合并）对弱模型的实际行为差异有多大？
- 弱模型是否真的因为工具名语义相似而混淆，还是只是因为 description 不够精确？

**关于 SKILL-executor**
- 决策树式 SKILL 对 Flash 级别模型的任务完成率提升是否显著？
- SKILL-executor 是否会反过来限制强模型的灵活性（在不该限制的场景里死板执行）？

**关于复杂场景**
- 场景 5（懒加载触发）目前用 world_click_at 变通，是否需要专门的 scroll 工具？
- 场景 3（弹窗嵌套）的 dialog bounds 是否在 world_state 里稳定返回、坐标是否准确？
- 场景 1（autocomplete）的 world_wait 目前是否支持 listbox_appear 条件？

**关于 world_guide 的定位**
- 如果 world_guide 在 SKILL-executor 里变成强制第一步，调用频率上升后性能是否足够？
- world_guide 的 task_hint 参数质量依赖 model 自身能力——弱模型写 hint 本身就是挑战，是否应该让 orchestrator 传入 hint？

## 七、推荐的验证顺序

**Step 0（10 分钟，可 A/B，不改代码）**

给四条"发生了什么"信道工具的 description 各加一句"何时用/何时不用"。来自实测观察：弱模型之所以没有混用四信道，是因为它读了 server.py 全部源码——真实 executor 没有这个前提。description 是工具对 agent 的唯一接口，必须在这里写清楚内部语义，而不是依赖 agent 猜测。

建议措辞（直接加到各工具 description 开头）：

```
world_changes:        原始事件调试用。常规操作请用 world_change_digest。
world_change_digest:  操作后了解变化趋势用。需要完整原始序列才用 world_changes。
world_state:          了解当前页面全局状态（弹窗/表单/登录态）。操作后先读 effect 字段，再按需调此工具。
world_evidence:       调试和人工核查用。常规流程读操作返回值中的 effect 即可，不需要单独调此工具。
```

这个改动完成后，在现有测试脚本里加入"工具调用分布统计"，对比前后弱模型的信道选择分布是否改善。

**Step 1（半天，核心盲区）**

page_outcome 最小实现：只做 `challenged` 检测（特征① + submit 前置条件），把 GitLab 注册页（Arkose 触发场景）做成本地夹具，验证最核心的盲区是否能被预合成判断覆盖。

**Step 2（各 10 分钟，最便宜的假设）**

本地夹具验证：
- 假设 B（Shadow DOM）：Shoelace UI 演示页，world_query 可交互元素数量
- 假设 E（pointer-events:none）：构造 button + pointer-events:none，验证 effected 判定
- 假设 R（CSS 变量 IPI）：CSS 自定义属性同色文字，验证 IPI 过滤

> Shadow DOM（假设 B）优先于 CSS 变量（假设 R）——现代组件库全面采用 shadow root，影响范围更大。CSS 变量因为 `getComputedStyle` 在计算阶段已展开变量，大概率已被现有实现覆盖，但仍值得 10 分钟确认。

**Step 3（半天，SKILL 路线验证）**

SKILL-executor 草稿：只覆盖场景 1（autocomplete）/ 场景 3（弹窗）/ 场景 7（验证码），用 Flash 级别模型跑 3-5 次，记录完成率和具体失败模式。

> SKILL-executor 决策树顶部须加逃生门："本树只覆盖已知模式；遇到未匹配情况一律执行：world_screenshot + 停止上报。"否则强模型会被死板分支拖慢。

**Step 4（根据 Step 0-3 结论决定工具层优先级）**

方案 B（工具合并 world_status）排到最后，在 page_outcome 语义标签和 SKILL-executor 都上线并跑出数据之后再评估。"弱模型有 4 个信道可选"不是根因，缺语义预答案才是；先把答案给到位，再看工具数量是否还是问题。

## 附：工具调用时机速查表（建议作为 SKILL-executor 前言）

| 时机 | 应调工具 | 不应调工具 |
|---|---|---|
| 打开新页面后 | world_guide（强制） | world_entities（太早，结构未定向） |
| 需要找目标元素 | world_map → world_query | world_screenshot（视觉兜底，不是第一选择） |
| 操作后立即 | 读操作返回的 effect | 再次调 world_guide（刷新太重） |

| 结构化工具失败两次后 | world_screenshot | 再次重试相同路径 |
| 任务全部完成 | world_close | （无需验证，直接关闭） |

## 八、page_outcome 合并信道设计（来自实战案例）

> 来源：2026-09-02 DeepSeek v4 flash 在另一 harness 上对 GitLab 注册流程的实测记录。
> 场景：点击"Continue"后 Arkose 人机验证 iframe 出现；四条信道无法给出可靠判断。

### 8.1 实战中的具体失败

| 工具 | 返回内容 | 为何不够 |
|---|---|---|
| `world_state` | auth/dialogs/forms/page 全部"正常" | dialogs 只看主文档 DOM，Arkose 在 iframe 内完全不可见；forms:[] 看起来像"没填过"而非"提交后清空" |
| `world_changes` | 事件流记录了新增、更新 | 如实记录"发生了变化"，但不告诉你变化的性质是错误还是成功 |
| `world_change_digest` | 摘要列出新构件 | 没有"错误提示"分类；Arkose 在 iframe 里，主文档摘要是盲区 |
| `world_evidence` | verdict = `changed/medium` | `changed` 是三义词：成功/验证失败/加载验证码，无法区分 |

最终靠 `world_eval` 读页面错误文字才确诊——这是事后调试，不是可靠流程。

### 8.2 根本问题：合并位置错了

四条信道提供的信息已经足够——不够的是**谁来合并**。弱模型在执行过程中无法可靠地跨四条信道做实时合并，但事后反思时能清楚表达盲区（DeepSeek 的分析证明了这一点）。

合并工作应该在 server 端（MCP 工具层）完成，agent 收到的应该是一个预合成的情景判断，不是四条独立信号。

### 8.3 page_outcome 字段提案

在所有操作工具（`world_click` / `world_fill` / `world_press`）的返回值中，新增 `page_outcome` 字段。

**结构：主标签 + 次要信号列表**（不是单值枚举）

真实场景经常同时满足多个状态（例如"跳转到登录墙"= URL 变化 + 阻断态同时成立），单值枚举会逼 server 做"二选一"的错判。改为：agent 读主标签做决策，`secondary` 列表保留次要信号供人工调试或强模型参考。

```json
{
  "local_verdict": "effected",
  "page_outcome": "challenged",
  "situation": {
    "type": "modal_iframe_challenge",
    "confidence": "medium",
    "evidence": [
      "new sandboxed iframe appeared in fixed overlay",
      "form cleared without URL change",
      "no new page-level semantic content"
    ],
    "recommended_next": "surface_to_human_or_wait_for_challenge"
  },
  "secondary": ["form_cleared"]
}
```

`page_outcome` 主标签的五个值（agent 只读这一个做决策）：

| 值 | 含义 | agent 应对 |
|---|---|---|
| `progressed` | 主要信号是前进（URL 变化或内容区重建） | 继续下一步 |
| `challenged` | 出现阻断性中间态（CAPTCHA / 二次验证） | 停止，截图，上报人工 |
| `errored` | 出现错误提示信号（表单验证失败） | 读错误内容，修正后重试 |
| `uncertain` | 变化发生但主要信号性质不明 | 调 world_state 补充判断，最多一次 |
| `unchanged` | 没有有效变化 | 按失败路径处理 |

`secondary` 可包含的次要信号（不影响主决策，供参考）：`url_changed` / `form_cleared` / `dialog_appeared` / `dialog_closed` / `aria_state_changed`。

### 8.4 iframe 的结构性检测（不依赖 URL 白名单）

检测"认识的"CAPTCHA 提供商 URL（arkoselabs / hcaptcha / recaptcha）是脆弱的——提供商会换 CDN、走代理、用第一方域名。

### 8.4 iframe 的结构性检测（不依赖 URL 白名单）

检测"认识的"CAPTCHA 提供商 URL（arkoselabs / hcaptcha / recaptcha）是脆弱的——提供商会换 CDN、走代理、用第一方域名。

改为检测**结构特征**，但须防止假阳性（Stripe、Google Maps、广告 iframe 大量满足 sandbox 特征）：

```
【必要前置条件】：本次操作的目标元素是 submit 类触发器
  （type=submit，或元素有 form 属性关联，或 role=button + 在 form 内）

满足前置条件后，再检测以下特征：

  ① 新出现的 iframe 父元素是 position:fixed 的全屏遮罩（viewport 宽高 ≥ 90%）
     → page_outcome = "challenged"，type = "modal_iframe_challenge"（充分条件）

  ② iframe 持有当前焦点（focus trap 特征）
     + iframe 有 sandbox 且包含 allow-forms allow-scripts
     → page_outcome = "uncertain"，secondary 加 "iframe_focus_trap"（辅助证据，需结合其他信号）
```

**不满足前置条件时**（普通点击后出现 iframe）：只记录 `secondary: ["new_iframe_appeared"]`，不升级为 `challenged`，避免误判 Stripe 等支付组件。

### 8.5 错误状态的语义 HTML 检测（不依赖 CSS 类名）

`.error` / `.gl-field-error` 等类名是网站私有约定，不稳定。改用标准语义属性：

```
操作后新出现的元素，满足以下任意一条：
  ① role="alert" 或 aria-live="polite|assertive"
  ② 某个 input 的 aria-invalid 从 false 变为 true
  ③ aria-describedby 指向的目标元素是新出现的
→ page_outcome = "errored"
→ errors = [采集上述元素的文本内容]
```

### 8.6 forms:[] 的时机歧义修正

表单提交后清空（forms:[]）既可能是"成功"也可能是"验证失败后重置"，当前无法区分。

解法：在 before 快照里记录 forms 状态，action 后对比：

```
action.before.forms = [{id:"email", value:"x@x.com"}, {id:"password", value:"***"}]
action.after.forms  = []
→ form_cleared = true, had_content = true
→ 结合 page_outcome 解释语义：
    page_outcome = progressed  → 提交成功后清空
    page_outcome = challenged  → 验证中断，表单重置，意义不明
    page_outcome = errored     → 验证失败后重置，需修正重填
```

## 九、其他工具待实测假设清单

> 本节为开放假设，尚未验证。目的是给其他 agent 提供实测议题。
> 每条假设标注：触发条件 / 预期失败现象 / 建议实测方式 / 当前是否有部分应对。

### 9.1 world_map

**假设 A：粘性元素（sticky header/footer）被误计入主内容区**
- 触发：页面有 `position:sticky` 的导航栏，world_map 区域识别时将其归入 main 或 content 区域
- 预期失败：agent 认为"导航栏是主内容"，从导航区开始操作而非正文区
- 实测建议：使用 GitHub 仓库页面（有 sticky header），检查 world_map 是否把顶栏归入独立 header 区域
- 当前应对：无专门处理

**假设 B：Shadow DOM 组件（Web Components）在地图中缺失**
- 触发：页面使用 Custom Elements（如 `<sl-button>`、`<ion-input>`）
- 预期失败：world_map 区域存在但区域内可交互元素为 0（构件在 shadow root 内，扫描不到）
- 实测建议：使用 Shoelace UI 或 Ionic 框架的演示页面测试
- 当前应对：未知，需确认注入内核是否穿透 shadow DOM

**假设 C：地图结构在内容刷新后过时**
- 触发：world_map 已调用，之后页面局部刷新（如 Ajax 替换了主内容区）
- 预期失败：agent 按旧地图的区域坐标定位，命中的是新内容的错误位置
- 实测建议：Google Flights 搜索航班后（结果区替换），检查之前的地图区域坐标是否还有效
- 当前应对：需确认 world_map 是否每次调用都重新扫描

### 9.2 world_query / world_entities

**假设 D：虚拟化列表（Virtualized List）只返回当前渲染的子集**
- 触发：大型列表使用 React Virtuoso / TanStack Virtual 等库，只渲染视口内元素
- 预期失败：world_query 找不到"第 50 个"列表项，因为它根本没有在 DOM 里
- 实测建议：GitHub Issues 列表（超过 25 项时）或大型表格，查询底部附近的元素
- 当前应对：场景 5 中有 scroll 变通方案，但非针对虚拟化的解法

**假设 E：pointer-events:none 的元素被当成可交互目标**
- 触发：某些元素有 aria 属性（role=button）但有 `pointer-events:none` 样式，点击不会触发
- 预期失败：world_query 返回该元素为可交互，world_click 执行后 verdict=effected（DOM 坐标点击了），但实际功能没有触发
- 实测建议：构造本地夹具，包含 `pointer-events:none` 的 button，验证 world_click 的 effected 判定
- 当前应对：无

**假设 F：React Portal 元素的父子关系误导区域归属**
- 触发：Modal / Tooltip 使用 React Portal 渲染到 document.body，视觉上在某个组件内部但 DOM 上是 body 的直接子元素
- 预期失败：world_map 把这些元素归入错误区域（body 根层而非逻辑父组件）
- 实测建议：MUI / Ant Design 的 Modal 演示页面
- 当前应对：world_state.dialogs 有一定覆盖，但区域归属不确定

### 9.3 world_fill

**假设 G：富文本编辑器无法用 world_fill 可靠填充**
- 触发：目标是 CodeMirror / Monaco / Quill / TipTap 等编辑器（不是标准 input/textarea）
- 预期失败：world_fill 注入文本后，效果/焦点状态依赖编辑器内部事件，可能无效或部分生效
- 实测建议：GitHub Issue 新建页（有 Markdown 编辑器）或 CodeSandbox
- 当前应对：行动层有 JS Setter 降级，但富文本编辑器往往连 value 属性都没有

**假设 H：掩码输入框（masked input）填充格式不符**
- 触发：电话号码输入框格式为 `(xxx) xxx-xxxx`，world_fill 填入纯数字 `1234567890`
- 预期失败：掩码格式化逻辑可能拒绝输入或截断，forms 里显示的值与实际提交值不一致
- 实测建议：美国地区的注册表单（含电话号码字段）
- 当前应对：无

**假设 I：React 受控输入（controlled input）的 state 未同步**
- 触发：React `onChange` 驱动的输入框，world_fill 改变了 DOM value 但没有触发 React 的合成事件
- 预期失败：表单提交时，React state 里仍是旧值（或空），实际提交内容与 forms 字段显示不符
- 实测建议：Next.js / Create React App 的注册表单，填充后检查提交内容
- 当前应对：行动层有 `type_delay_ms` 模拟真实键盘，理论上能触发 onChange，但未专门验证

### 9.4 world_click

**假设 J：hover-triggered 菜单点击失败**
- 触发：导航菜单需要先 hover 才显示子项，直接 click 子项时子项 DOM 还不存在
- 预期失败：world_query 找不到子菜单项（元素还没渲染），或 world_click 点击时元素已隐藏
- 实测建议：有 hover 下拉菜单的传统网站（非 SPA）
- 当前应对：无 hover 工具，只有 click

**假设 K：双击（double-click）场景被单击替代**
- 触发：某些 UI 元素需要双击才能激活（如：表格内联编辑、文件重命名）
- 预期失败：world_click 执行单击，元素进入 selected 状态而非 edit 状态
- 实测建议：Google Drive 文件列表（点击=选中，双击=打开/重命名）
- 当前应对：无 dblclick 工具

**假设 L：页面滚动后元素坐标失效**
- 触发：world_entity 获取了元素坐标，然后页面发生了滚动（sticky 元素位置改变，非 sticky 元素的视口坐标改变），再用坐标兜底点击
- 预期失败：world_click_at 按旧坐标点击，命中了错误元素
- 实测建议：长页面上使用坐标兜底点击，中间触发页面滚动
- 当前应对：world_click 主路径用 Locator（应对滚动），坐标兜底路径有此风险

### 9.5 world_wait

**假设 M：文本条件跨语言/动态文本失效**
- 触发：world_wait 等待包含"验证码"的文本，但页面实际显示英文 "verification" 或动态拼接的文本
- 预期失败：等待超时，任务中断（DeepSeek 实战中已出现此情况）
- 实测建议：对同一场景用中文和英文文本条件分别测试
- 当前应对：无跨语言匹配；建议改用结构条件（等待 role="dialog" 出现）而非文本条件

**假设 N：页面持续微小更新导致"稳定"条件永不满足**
- 触发：股票行情、实时聊天等页面有持续的后台更新，page.state 始终是 loading 或 unstable
- 预期失败：world_wait 一直等待稳定，直到超时
- 实测建议：实时行情页面或带 WebSocket 推送的页面
- 当前应对：未知，需确认 page.state 的稳定判定对持续更新页面的行为

### 9.6 world_guide

**假设 O：弱模型提供的 task_hint 质量太差，导致 candidates 与任务无关**
- 触发：弱模型将 task_hint 写成非常通用或错误的描述（如"找到按钮"而非"找到提交注册的按钮"）
- 预期失败：world_guide 返回的 candidates 是页面上所有按钮，没有实质过滤
- 实测建议：对同一页面用高质量 hint（"找到注册表单的提交按钮"）和低质量 hint（"点击"）分别调用，对比 candidates 的精准度
- **当前应对：无；这是 SKILL-executor 架构里必须 upfront 决策的问题，不能留给"以后验证"**

> **循环依赖的具体解法**：SKILL-executor 的决策树第一步强制调 world_guide(task_hint)，但弱模型写 hint 本身就是挑战。解法不是"让弱模型写更好的 hint"，而是**把 hint 改为从有限模板中选择，不允许自由填写**：
>
> ```
> task_hint 只能从以下四类中选一个关键词：
>   find_and_click  → 找一个元素并点击它
>   fill_form       → 填写表单并提交
>   navigate_to     → 进入某个页面或区域
>   read_content    → 只读取内容，不操作
> ```
>
> 四个任务类型覆盖浏览器任务的绝大多数场景；弱模型从列表选一个远比自由填写可靠。orchestrator（强模型）负责把复杂任务分解后，为每个子任务指定对应的 hint 类型传给 executor。这把"弱模型写 hint"变成"弱模型从已知列表选 hint"，完全在弱模型的能力范围内。

**假设 P：world_guide 在单一巨型区域页面上没有导向作用**
- 触发：页面整个 main 区域是一个大容器（无语义子区域），world_guide 返回的区域只有"main"，没有更细的候选
- 预期失败：agent 收到 world_guide 结果后仍需要对整个 main 区域做全量扫描
- 实测建议：结构扁平的营销落地页或单屏 Dashboard
- 当前应对：world_map 的 region 参数可以钻取，但 world_guide 是否能利用这个能力未知

### 9.7 跨工具的系统性假设

**假设 Q：A/B 测试导致稳定指纹失效（fingerprint stability）**
- 触发：网站对不同用户或不同会话展示不同版本的 UI（A/B 测试），同一 URL 两次进入结构不同
- 预期失败：上次记录的稳定指纹（fingerprint）在新会话中匹配不到，或匹配到错误元素
- 实测建议：在支持 A/B 测试的平台（如 Optimizely 测试页）多次进入，比较指纹一致性
- 当前应对：文档提到真站指纹命中率 80-92%，但 A/B 测试场景未单独验证

**假设 R：IPI 过滤的新变体——CSS 自定义属性隐藏**
- 触发：页面通过 CSS 变量（`--color: var(--bg-color)`）使文字与背景同色，而非直接 `color: white; background: white`
- 预期失败：当前 IPI 过滤的"同色文字"检测基于计算样式，CSS 变量是否能正确展开取决于实现
- 实测建议：构造本地夹具，用 CSS 自定义属性实现同色文字，验证 IPI 过滤是否拦截
- 当前应对：未知，需代码层确认
