## 二、验证体系如何运作(复盘要点)

### 2.1 质检流水线证明了自己的价值(3 次)

1. **收编 validate 即抓到 bug**:百度提交后页面导航中 `world_eval` 崩溃导致整个矩阵中断——脚本原无保护,收编后第一次现形。修复:truth 查询失败 → SKIP(不污染 FP 一票否决)。
2. **PR #2 的 POC 测试全是"假绿"**:0 断言、不走 MCP 链路、失败也退出 0——如果没有流水线纪律,这些"测试"会被当成已守护。降级到 mcp/poc/ 并补正式测试。
3. **合并 PR #2 后立即全量回归**:offline 从 5 项扩到 9 项,一次跑通,说明合并无回归(含视觉 diff 正负例)。

### 2.2 流水线的设计原则(验证有效)

- **分组分层**:offline(快/稳/必跑) vs real(慢/环境敏感) vs special(需特殊环境)——把"环境失败"和"代码失败"分开,避免误伤。
- **退出码契约**:0 全过/1 失败/2 前置检查失败——可被任何后续工具消费。
- **FP=0 一票否决**:validate 的通过线设计直接约束了视觉判定等新能力,防"判定过激"。
- **前置检查**:all-in-one.js 与分文件一致性(内核改动的同步点)。

### 2.3 教训:测试的"真"比"多"重要

- 3 个 POC 脚本(50+ 行断言缺失)的价值 **低于** 1 个正式测试(4 项断言正负例)。
- "跑通"不等于"守护":无断言、无退出码的脚本无法进入 CI/流水线语义。
- 后续新测试必须满足:走 MCP 链路(真实协议)、有断言、有退出码、本地夹具优先。

## 三、端到端实验复盘(重点)

### 3.1 实验设计的教训(3 条)

1. **风控状态是最大不可控变量**:对照组首次访问 GitLab 未触发 Arkose,工具组第 3 次尝试触发——同一平台不同时点结果不同。"对照组成功"有运气成分,"工具组失败"有环境成分。**教训:对比实验应同会话内尽早完成两组,或备≥2 个平台,先跑 fail-fast 探针确认风控未触发再开始。**
2. **真实注册任务本身带验证墙**:hCaptcha(2 次)、Arkose(1 次)——无论工具多好,注册类任务在自动化下大概率触发人机验证。**教训:此类任务更适合"headful + 人工介入点"或明确标记为人工辅助任务。**
3. **邮箱别名技巧有效但引入混淆**:Gmail + 别名(tooling/baseline)让同一收件箱收多封验证码,但调试中容易混淆"哪封是哪组"。**教训:每组用独立清晰标记,或顺序执行。**

### 3.2 工具的真实短板(这次实验最大的产出)

**世界模型不采集 input 的 `name` 属性** → 无法精确定位表单字段:
- GitLab 表单有幽灵字段(`firstname`/`lastname` 在 `new_user[xxx]` 之前),按 DOM 顺序盲填 → 全部错位,邮箱进用户名、密码进邮箱。
- 对照组靠"人工语义识别"绕过了;工具组纯结构化通道做不到。
- 缓解:一次受控 `world_eval` 读 name→el_id 映射(12 次调用、0 恢复完成填表)。
- **结论:attributes 应补 `name`(P0),这是实验发现的第一真实缺陷。**

### 3.3 实验结果解读(诚实版)

| 结论 | 可信度 |
|---|---|
| 对照组 16 次恢复 vs 工具组 0 次恢复 | 高(反馈机制差异,受风控影响小) |
| 工具组 12 次调用 vs 对照组 ~55 次 | 高(结构化查询确实省调用) |
| 对照组"注册成功" vs 工具组"被拦" | 低(风控状态不同,不能归结为工具差异) |
| 工具组 60s vs 对照组 30min | 中(对照组含大量人工 agent 思考时间,非纯工具差异) |

**核心洞见:工具的价值不在"能不能完成",而在"完成时消耗多少探索成本"——16 vs 0 次恢复、55 vs 12 次调用,这才是结构化世界的真实优势,且不受风控影响。**

## 四、过程问题分析(本次会话的失败模式)

| 问题 | 根因 | 教训 |
|---|---|---|
| cmd/PowerShell 引号反复出错 | Windows shell 对中文引号/括号拆分参数,多次 commit/pip 失败 | 用 `-F message 文件` 提交;复杂命令写脚本文件执行 |
| `import mcp` 假成功 | 脚本放在项目目录内时命中了项目自己的 mcp/ 目录(namespace package) | 探针脚本放仓库外;检查 `__file__` 非空 |
| 工具组验证码邮件收不到 | 表单字段错位(幽灵字段)→ 提交被前端校验拦截,邮件从未发出 | 先诊断"是否真的提交成功"(URL/错误文本),再等邮件 |
| 实验中途换平台/换邮箱 | 验证墙死胡同 + 风控 | 开始前多平台预案;fail-fast 探针 |
| 后台脚本 stdout 为空 | Python 缓冲未 flush | `python -u` + PYTHONUNBUFFERED |
| git rebase 交互编辑器卡死 | PowerShell 无 `--no-edit` | GIT_SEQUENCE_EDITOR 自动化 |
| 敏感数据入提交 | 真实凭据写进文档后直接 commit+push,未先脱敏 | **纪律:涉及真实账号/邮箱/验证码的文档,提交前必须脱敏检查**(本次教训的直接来源) |
