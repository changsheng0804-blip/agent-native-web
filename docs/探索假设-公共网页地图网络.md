# 探索假设：公共网页地图网络

## 文档状态

**状态：待验证的产品假设，不是已确定的发展路线。**

本文件只记录一个可能的方向：把不同智能体在公开网站上产生的结构化探索结果，沉淀为可复用的站点级网页地图。是否值得做，必须经过需求、效果和维护成本验证。

本方向暂不进入主分支的正式产品承诺，也不要求立即建设远程服务。

## 一、核心想法

普通网页通常没有为智能体准备 API、结构化入口或页面导览图。每个新的智能体进入网站时，都可能需要重新理解页面结构、寻找入口和试探操作结果。

假设：一次智能体使用过程可以只留下**脱离用户身份的公开结构证据**，后来的智能体进入同一网站时先读取这些证据，再用当前网页进行实时确认。

```text
第一次探索：从零理解网页
       ↓
提取公开结构、入口和操作结果
       ↓
合并为站点级公共网页地图
       ↓
后来者先读取地图，再用当前网页校准
       ↓
新的探索继续补充和修正地图
```

这个方向类似协作制图，但共享的不是用户浏览历史，而是：

> 网站公开结构、页面导航关系、可操作入口和经过验证的动作结果。

## 二、它可能解决的问题

### 1. 降低陌生网站的冷启动成本

智能体第一次进入一个复杂网站时，真正困难的往往不是执行一次点击，而是判断：

- 页面有哪些主要区域。
- 哪个区域与任务有关。
- 目标入口可能在哪里。
- 点击后通常会产生什么结果。

公共地图可以提供一个候选方向，减少每次从零开始。

### 2. 让低频网站也能积累价值

个人用户低频访问某个网站时，单独建立个人网页记忆可能没有意义。但如果公共网站被很多智能体偶尔使用，每次只贡献一点公开结构，长期可能形成有价值的站点地图。

### 3. 把一次性探索变成公共基础设施

单次操作产生的最有价值的结果，不一定是操作轨迹，而可能是：

```text
这个入口存在
它属于哪个区域
它可以执行什么动作
这个动作通常会产生什么页面变化
```

这些结果可以被后来的智能体复用。

## 三、共享边界

### 允许共享

- 公开网站域名和公开页面路径。
- 页面区域及相对空间关系。
- 公开按钮、链接、输入框、菜单等元素的角色。
- 短的公开界面标签或其脱敏索引。
- 元素稳定定位特征。
- 公开页面之间的导航关系。
- 可执行动作类型。
- 动作结果类型，例如 URL 变化、弹窗出现、菜单展开。
- 地图版本、验证时间、验证次数、完整度和失效标记。

### 默认不共享

- Cookie、登录状态和浏览器 profile。
- API Key、密码、令牌和账户信息。
- 用户输入的搜索词、表单内容和任务内容。
- 私人后台页面和带权限页面。
- 完整页面正文、完整 DOM 和截图。
- 用户身份、浏览时间、浏览历史和原始轨迹。
- URL 中可能包含的用户参数。

### 核心原则

公共地图描述的是“网站如何工作”，而不是“某个用户做过什么”。

## 四、地图不是事实数据库

网页具有动态性、个性化和版本差异，因此公共地图不能被视为绝对真相。

地图条目至少需要关联：

```text
网站
页面路径
语言/地区
登录或公开状态
设备类型
页面结构版本
最近验证时间
验证次数
可信度
```

正确使用方式是：

```text
公共地图提供候选位置
→ 当前网页实时确认
→ 当前网页执行动作
→ 当前网页反馈结果
→ 用新证据更新地图
```

地图负责降低冷启动成本，当前网页负责最终裁决。

## 五、为什么它可能是伪需求

这个方向不能因为有网络效应想象空间，就直接认定有产品价值。至少存在以下可能：

### 1. 地图维护成本可能高于重新探索

如果智能体本身已经能在几秒内完成页面探索，那么下载、匹配和验证地图反而增加复杂度。

### 2. 页面变化可能让公共地图很快失效

按钮文案、页面布局、登录状态、地区和 A/B 测试都可能改变地图。若地图更新不及时，错误先验可能比没有地图更糟。

### 3. 网站结构可能无法稳定合并

不同用户看到的页面可能不是同一个页面变体。元素的临时编号不能直接作为公共身份，稳定指纹也不能保证跨版本永久有效。

### 4. 使用者未必有贡献动机

用户可能愿意使用公共地图，却不愿意贡献；这样会出现“公共地图需要贡献才能有价值，但没有价值就没人贡献”的冷启动问题。

### 5. 只共享结构可能不够完成任务

结构地图可以帮助智能体找到入口，但任务本身仍然需要当前页面内容。若智能体真正困难的是理解业务语义，而不是找到按钮，地图带来的收益可能有限。

### 6. 站点级地图未必适合所有网站

公共网站、文档站、产品首页和开发者控制台可能有价值；高度个性化、登录强依赖、频繁变化的系统可能不适合公开共享。

## 六、可验证的价值假设

### H1：公共地图能缩短陌生网站首次正确定位时间

验证方法：同一网站、同一任务，比较有地图和无地图时到达第一个正确目标的时间与步骤数。

### H2：公共地图能减少无关页面读取

验证方法：比较两种方式发送给智能体的结构数据量、元素数量和无关区域比例。

### H3：动作证据比原始操作轨迹更有复用价值

验证方法：比较“只有页面结构”“结构 + 操作结果证据”“原始轨迹”三种数据对后续任务成功率和恢复时间的影响。

### H4：地图可以通过实时校准抵抗页面变化

验证方法：对页面改版、按钮移动、文案变化和区域重排进行测试，记录地图命中率、校准时间和错误操作率。

### H5：公开结构地图在隐私边界内具有可持续贡献可能

验证方法：只允许公开页面、结构和脱敏证据，观察贡献数据是否足以提升后续任务效果；不以收集用户轨迹作为前提。

## 七、最小验证方案

在建设公共服务之前，先做一个本地可验证的最小版本：

### 第一步：生成标准地图文件

从现有 `world_map`、`world_entities`、`fingerprint`、`world_changes` 和 `effect` 中提取一个脱敏 JSON 文件。

只包含公开页面结构、入口、导航关系和动作结果，不包含用户内容。

### 第二步：个人本地模拟多用户合并

用同一网站的多次独立探索生成多份地图文件，模拟：

- 不同时间进入。
- 不同页面加载顺序。
- 不同元素编号。
- 局部区域新增或失效。
- 页面结构小幅变化。

验证能否合并为一份稳定的站点地图。

### 第三步：做有地图/无地图对照

至少选择以下类型的公开网站：

- 内容结构清晰的网站。
- 内容和区域较深的官网。
- 重型 SPA 页面。
- 文档或开发者网站。

每个网站准备多个无破坏性任务，记录：

- 首次正确定位时间。
- 首次正确操作时间。
- 读取元素数量和数据量。
- 定位歧义率。
- 假成功率和假失败率。
- 地图校准次数。
- 页面变化后的恢复时间。

### 第四步：设置停止条件

出现以下情况之一，应暂停公共地图方向：

- 有地图不能稳定降低首次正确定位时间。
- 地图命中后仍需要重新完整理解页面。
- 地图维护和校准成本高于重新探索。
- 页面变化导致错误先验频繁产生误操作。
- 公开结构不足以产生后续任务收益。
- 没有清晰的贡献来源和质量控制方式。

## 八、可能的最小产品形态

如果验证通过，第一版也不应直接做复杂的“智能体网络世界”。更适合先做：

```text
Atlas Lookup
查询某网站/页面是否存在公共结构地图

Atlas Match
根据当前页面特征匹配地图版本

Atlas Get
读取区域、入口和动作证据

Live Verify
用当前网页确认地图是否仍然有效

Atlas Report
提交结构失效或页面变化报告
```

公共贡献可以后置，先证明“读取公共地图”本身能带来明确收益。

## 九、与 WebMCP 的关系

```text
网站主动提供 WebMCP
    → 直接调用网站工具

网站没有 WebMCP
    → 使用 Agent-Native Web MCP
        → 查询公共地图
        → 当前页面校准
        → 结构化操作
        → 真实结果验证
```

公共网页地图不是 WebMCP 的替代品，而是网站没有适配时的智能体侧基础设施。

## 十、当前判断

目前可以确认的是：

- 技术上可以从现有 MCP 结果中提取脱敏的页面结构和操作证据。
- 公共地图有机会减少陌生网站的冷启动成本。
- 地图、实时反馈和操作证据可以形成互补闭环。

目前不能确认的是：

- 这种收益是否足以覆盖地图生成、合并和维护成本。
- 网站结构是否具有足够长期的稳定性。
- 用户是否会在没有直接收益的情况下贡献公共结构。
- 公共地图是否能显著提升真实任务成功率。

因此当前结论是：

> 这是一个值得做小规模验证的方向，但还不是应该立即建设的确定需求。

## 十一、后续关键问题：真实网页任务中的“地形信息”

公共网页地图是否有价值，最终不能只看网页世界的机器重建成本，还要看真实任务中智能体是否因为缺少“地形信息”而反复盲目摸索。

### 1. 哪些真实任务会使用浏览器智能体

比较有代表性的场景包括：

- 网站没有 CLI 或 API，只能通过网页完成任务。
- 人类不熟悉该网站，智能体能够代替人理解专业后台。
- 页面结构复杂、步骤多、需要跨多个页面或功能区。
- 内容发布、资料整理、表单录入等重复性工作可以交给智能体执行。
- 人类知道目标，但不熟悉实现路径，例如云平台控制台、开发者平台和专业 SaaS 后台。
- 网站本身存在大量隐藏菜单、弹窗、状态切换和逐步加载内容。

典型例子包括：

```text
在内容平台发布一篇笔记
在云服务控制台创建或配置某项资源
在陌生专业后台找到某个设置
在没有 API 的网站完成多步骤资料整理
```

这些任务的共同点不是“人类不会点击”，而是：

> 智能体必须先理解一个陌生、复杂、状态不断变化的网页环境。

### 2. 当前智能体的真实困难

把“摸索”称为探索并不完全准确。对大型语言模型来说，很多时候更接近：

```text
看到局部页面
→ 猜测页面整体结构
→ 猜测某个按钮的作用
→ 点击后等待
→ 根据不完整反馈猜测结果
→ 再继续猜下一步
```

它缺少的不是单个元素，而是以下环境信息：

- 页面有哪些区域和功能。
- 当前区域在整个网站中的位置。
- 当前页面有哪些可执行动作。
- 每个动作的前置条件是什么。
- 点击后是跳转、弹窗、展开、筛选还是状态翻转。
- 下一页面有哪些结构和可用功能。
- 哪些内容可以直接读取，哪些必须经过动作才会出现。
- 当前动作是否真的完成了预期目标。

### 3. 智能体需要的可能不是“地图”，而是“网页地形信息”

“地图”只是一个容易理解的比喻。对智能体真正有用的地形信息，至少包含五层：

```text
空间层：页面有哪些区域、区域如何排列
结构层：页面和页面之间如何连接
能力层：每个区域可以执行什么动作
状态层：动作会造成什么状态变化
证据层：如何判断动作是否真的生效
```

例如“进入火山方舟”这个入口，不只是一个链接，还应当知道：

```text
它位于模型服务区域
它是一个公开链接
点击后进入火山方舟概览页
可能需要登录
进入后会出现模型、推理或应用相关区域
当前页面可以先读取入口地址和相关公开结构
```

这比“元素 el_89 在坐标 x,y”更接近智能体真正需要的环境知识。

### 4. 页面全量结构是否应该提供给智能体

这里需要区分“提供能力”和“默认发送”：

- **提供完整结构查询能力**：可能非常有价值，智能体可以在需要时穿透整个网站或页面。
- **每次把完整结构全部塞进上下文**：未必合适，可能造成新的信息洪水。

因此更合理的设计是：

```text
默认：返回页面总览和任务相关入口
需要时：查询某个区域的完整结构
继续需要时：查询页面之间的关系和动作结果
```

也就是说，智能体应该拥有“查看全图的能力”，但不一定每次都被迫阅读全图。

这与人类的使用方式不同：人类通常需要视觉上的整体控制，而智能体可能更适合拥有一份可检索的完整结构数据库，再按任务提取相关部分。

### 5. Skill 引导和网页地形信息的区别

Skill 可以告诉智能体：

```text
遇到网页任务时先看地图，再查目标，操作后验证
```

但 Skill 不知道某一个具体网站的实际地形。

网页地形信息需要告诉智能体：

```text
这个网站有哪些区域
这个页面有哪些入口
这个入口通常通往哪里
这个功能需要什么前置状态
点击后会出现什么
下一页面还有什么结构
```

所以两者关系是：

```text
Skill：告诉智能体如何探索和使用网页世界
网页地形：告诉智能体这个具体网页世界是什么样
```

二者不能互相替代。

### 6. 这是否重新提高了公共地图的必要性

这会把公共地图的价值从“避免重复重建”转移到“避免重复盲目摸索”：

```text
机器重建成本：当前通常是秒级，未必值得共享
智能体理解成本：复杂网站可能需要多轮查询和试错，可能值得共享
```

因此公共地图是否成立，应该用真实任务验证：

```text
没有网页地形先验的智能体
vs
拥有网页地形先验的智能体
```

比较：

- 是否更快找到正确功能。
- 是否更少走错页面。
- 是否更少重复读取页面。
- 是否更少产生歧义定位。
- 是否更少把动作结果猜错。
- 是否更容易从失败中恢复。

### 7. 新增的待验证假设

#### H6：复杂网页任务的主要成本是环境理解，而不是网页扫描

如果同一页面的结构扫描只需要几秒，但智能体需要多轮读取和试错才能找到目标，则公共网页地形信息可能有价值。

#### H7：页面地图和动作结果证据能够显著降低任务试错

如果地图只帮助找到按钮，却不能告诉智能体动作前置条件和动作后果，则它的价值可能很有限。

#### H8：完整结构应作为可查询能力，而不是默认上下文

如果完整结构直接发送给智能体导致上下文负担增加，而按需查询能保持任务效果，则应采用分层查询。

### 8. 下一步最小实验

暂不建设公共网络，先做一个本地“网页地形先验”实验：

1. 选择火山引擎官网、一个内容发布平台和一个开发者控制台。
2. 为每个网站准备 3～5 个无破坏性真实任务。
3. 记录没有先验地图时智能体的完整探索过程。
4. 手工整理一份最小网页地形信息，只包含区域、入口、动作和结果。
5. 让智能体使用这份先验完成同类任务。
6. 对比时间、工具调用次数、错误定位、重复读取和结果判断错误。

如果没有明显改善，公共地图方向暂时停止；如果改善明显，再继续验证自动生成、多人合并和页面版本更新。

## 十二、当前阶段结论

目前更准确的问题不是：

> 要不要为每个页面提前建立一份公共地图？

而是：

> 在复杂网页真实任务中，智能体是否因为缺少网站级地形信息而付出了显著的理解和试错成本？

只有这个问题得到肯定回答，公共网页地图才从“有趣的基础设施设想”变成“值得建设的需求”。
