# 业务逻辑图工程（点-边-图）架构设计方案

> **状态**：专项前沿架构设计与论证基准（v1.0 · 2026-09-04）  
> **核心定位**：将 Web Agent 从“单步物理交互（DOM/截图猜测）”升维到“业务因果拓扑驱动（Harness-like Graph Engineering）”。让 Agent 具备跨层级穿透、业务逻辑推导与最短路径规划能力。  
> **配套文档**：`探索方向-网站导航图与路径规划.md` · `小票标准-page_receipt-v0.1.md` · `探索方向-弱模型复杂场景.md`

## 一、 为什么必须转向“业务逻辑图工程”？

### 1.1 当前 Web Agent 的认知盲区与瓶颈

当前主流的浏览器自动化 Agent（包括本项目现有的 `world_*` 工具链路），本质上依然是 **“局域感知驱动的单步 Markov 链”**：
1. 每次站在当前视口，花费大量算力与 Token 扫描当前 DOM、Accessibility Tree 或视觉多模态截图；
2. 由 LLM 猜想“下一步应该点哪个”；
3. 执行操作，等待反馈；
4. 如果任务需要跨越 5 个页面/状态才能完成，Agent 必须重复 5 轮“盲人摸象”，任何一轮出现歧义就会导致任务走偏、陷入循环或因上下文膨胀而崩溃。

```text
传统单步交互模式：
[用户目标] ──> (当前页面盲猜) ──> [动作1] ──> (新页面盲猜) ──> [动作2] ──> ... ──> (累积误差爆炸)
```

### 1.2 图工程的核心主张：业务因果转移拓扑

人类专家和成熟的 Harness 系统操作复杂业务系统时，大脑里运行的是一张 **业务状态因果转移图（Business State Transition Graph）**。  
Agent 操作网页的真正优势，不在于“每次都能在成百上千个 DOM 里找到按钮”，而在于**在执行前就能把完成业务任务的因果逻辑串联成图**，直接进行路径寻优与确定性状态推进。

```text
业务图工程模式：
[用户目标]
    │
    ▼ 启发式路径规划 (Graph Pathfinding)
┌────────────────────────────────────────────────────────────────────────┐
│ 业务逻辑图 (State-Transition Graph):                                   │
│ (业务状态 A: 未登录) ──[边 E1: SSO凭证]──> (业务状态 B: 控制台首页)   │
│                                                │                       │
│                                           [边 E2: 路由穿透]            │
│                                                ▼                       │
│ (业务状态 D: 任务成功) <──[边 E3: 提交]── (业务状态 C: 配置表单填写态) │
└────────────────────────────────────────────────────────────────────────┘
    │
    ▼ 批流/确定性执行 (Deterministic Step Execution + 小票对账)
[快速达成业务结果，Token 消耗降低一个数量级]
```

## 二、 核心实体抽象：点、边、图的形式化定义

不同于传统网络爬虫以 URL 为节点，业务逻辑图面向的是**语义与业务状态**。

### 2.1 业务状态点（Node / State）

一个“点”不是一段 Raw HTML，也不是一张截图，而是一个**经过哈希收敛的业务状态签名（Business State Signature）**：

$$Node = \text{Hash}(URL\_Pattern, \text{Surface\_Type}, \text{Active\_Modals}, \text{Form\_Schema\_Hash}, \text{Role\_Capabilities})$$

* **URL Pattern**：参数泛化后的路由模板（如 `/:owner/:repo/settings` 而非具体某次 URL）。
* **Surface Type**：主视窗类别（`page` | `embedded_drawer` | `fullscreen_modal` | `stepper_wizard_step_N`）。
* **Active Modals**：当前激活的模态框/遮罩层语义签名（区分同一页面在弹窗前后两个完全不同的业务状态）。
* **Form Schema**：当前状态所暴露的核心表单输入能力集（输入项、必填校验项）。
* **业务状态分类标签**：
  * `ENTRY`：入口态（主页、列表页）
  * `INTERMEDIATE`：中间过程态（表单录入、配置调整）
  * `CHALLENGE`：挑战阻断态（人机验证、二要素认证、登录拦截）
  * `TERMINAL`：业务完备态（成功提交结果页、成功提示 Toast、空状态）

### 2.2 因果转移边（Edge / Transition）

“边”代表将页面从一个业务状态推演至下一个业务状态的**最小因果交互包**：

* **边标识符**：`Edge_ID = (Source_Node) -> (Target_Node) via (Action_Intent)`
* **前置约束（Pre-conditions）**：
  * 必须满足的状态（例如：`auth.loggedIn == true`，`form.field_count >= 3`，必填项校验全部通过）。
* **触发载荷（Action Payload）**：
  * 目标构件的稳定指纹序列（`fingerprint` / `name` / 语义选择器）。
  * 交互动词集合（`click`、`fill(schema)`、`press(Enter)`、`batch_steps`）。
* **后验小票契约（Outcome Contract）**：
  * 判定该边是否通行成功的凭证，完全对接项目的 `page_outcome` 标准：
    * 期望的 outcome 主标签（`progressed`）。
    * 证据要求：URL 变更、特定 DOM 消失（Modal 关闭）、或出现预期业务 Toast。
* **边的置信度与耗时权重（Weight & Confidence）**：
  * `weight = f(平均步骤耗时, 历史成功率, 失败重试代价)`。

### 2.3 业务图空间（Graph / Topology）

* 维护网站/业务域维度的全局或局部拓扑。
* 支持正向查询：`Given (Current_State, Target_Goal) -> Return [Edge_1, Edge_2, ...]`。
* 支持逆向推导：`Given (Target_State) -> Trace Back (Pre-requisite States)`。

## 三、 两级构建流水线：预先透视与运行时结晶

针对“如何构建图”的问题，采用**“静态预先透视（能穿透先穿透）”**与**“运行时被动结晶（无法透视的深水区运行时沉淀）”**相融合的流水线架构。

```
┌────────────────────────────────────────────────────────────────────────┐
│                        业务逻辑图两级构建流水线                         │
├──────────────────────────────────┬─────────────────────────────────────┤
│ Level 1: 预先透视 (Ahead-of-Time) │ Level 2: 运行时结晶 (Just-in-Time) │
│ (零交互/低成本/启动前 100ms 内完成)│ (真实任务交互中逐步硬化因果边)       │
├──────────────────────────────────┼─────────────────────────────────────┤
│ • 前端路由表嗅探 (Router Table)   │ • 真实动作触发 (world_act)          │
│ • 导航结构与菜单树反编译          │ • 小票对账与状态转移捕获 (outcome)  │
│ • 表单 Schema 与提交意图解析     │ • 因果边固化 (Edge Confirmed)       │
│ • 预热构建“毛坯路网骨架”         │ • 动态补全分支、异常态与挑战态     │
└──────────────────────────────────┴─────────────────────────────────────┘
```

### 3.1 阶段一：前置轻量静态透视（Frontier Scanner）

在 `world_open` 建立世界的初始阶段（控制在 50~150ms 注入执行），不产生破坏性操作，透视网页的前端架构：

1. **SPA 内存路由表透视**：
   * 现代前端框架（React Router、Vue Router、Next.js、Nuxt）大多在 `window` 或框架根实例中保留路由注册树。
   * 内核尝试挂钩嗅探路由配置（Pathname 模式、元数据、路由守卫、页面标题），直接获得应用的全量子页面路径树。
2. **静态语义路网抽取**：
   * 抽取全量 `<nav>`、`<aside>`、菜单栏中的链接集与 ARIA 树，映射“一级菜单 -> 二级模块 -> 功能页面”的骨架树。
3. **表单动作意图透视**：
   * 扫描处于可见态但尚未提交的表单容器，提取 `form[action]`、关联 Submit 按钮及字段 Schema。
4. **产物**：输出一张 **置信度为 `speculative`（推测性）的毛坯拓扑骨架**。

### 3.2 阶段二：运行时因果沉淀与结晶（Runtime Crystallization）

对于任何涉及复杂权限、深层交互、弹窗、动态异步加载等前端路由无法覆盖的场景，由 Agent 在任务驱动下进行结晶：

1. **状态跃迁侦听**：
   * 记录动作前状态卡 $S_{before}$ 与动作后状态卡 $S_{after}$。
2. **小票背书检验**：
   * 依据 `mcp/server.py` 返回的 `page_outcome` 小票。
   * 若小票为 `progressed`，计算两态哈希；若产生新状态点 $S_{new}$，则在拓扑中原子化写入一条有向实线边：
     $$Edge(S_{before} \to S_{after}) \text{ with Contract}$$
3. **加权强化**：
   * 多次走通同一条边，提升边的 `confidence`（`low` -> `medium` -> `verified`），并平滑更新平均耗时与 Token 代价。

## 四、 图工程驱动的 Agent 执行闭环（Run-Loop）

有了业务图，Agent 的工作方式彻底改变，执行闭环如下：

```
[Agent 接收业务任务] (例如: "关闭账户的双重认证")
       │
       ▼
1. 状态定位 (Localize Current Node)
   • 采集当前状态卡，匹配图中最接近的 State Node (当前是否在设置页？是否已登录？)
       │
       ▼
2. 拓扑寻路 (Pathfinding on Business Graph)
   • 图引擎搜索从 Current_Node 到 Target_Node 的最优边路径
       │
       ├─► [找到高置信度路径] ──> 3. 规划式快轨批执行 (Fast-Track Batch Execution)
       │                         • 按边定义直接打包动作步骤流 (steps=[...])
       │                         • 每步仅校验小票契约，无须重新全量推理
       │
       └─► [图谱缺失/断裂/未命中] ──> 4. 探索式慢轨 (Exploration Fallback)
                                  • 降级调用现有 world_guide / world_find
                                  • 走通后触发结晶机制，修补/新增图谱边
```

## 五、 自愈、防毒化与颗粒度收敛机制

实战中最严峻的问题不是“怎么建图”，而是**“怎么防止过期的死图把 Agent 带进死胡同”**。

### 5.1 铁律：实时小票与探针永远拥有一票否决权

图中的先验知识**永远只能作为规划建议，绝不能覆盖实时事实**：
1. **轻量预检探针（Pre-flight Probe）**：
   * 沿着图中的边准备执行动作前，内核花费 <20ms 嗅探目标构件的稳定指纹是否在场、是否被遮挡。
   * 若指纹不在场，判定该边**“瞬间熔断”**，不进行硬点盲操。
2. **小票不匹配立即降级（Contract Violation Fallback）**：
   * 边执行后，小票返回 `unchanged`、`errored` 或 `challenged`，与边预期不符。
   * 立即降级为探索模式，并自动降低该边的权重；连续 2 次失败则将该边标记为 `stale_deprecated`。

### 5.2 业务状态颗粒度的实测收敛法则

状态切得太细（每个 DOM 变化都算新状态），会导致图爆炸，丧失路径规划意义；切得太粗（整个网站算一个页面），退化回现状。  
**收敛标准由以下三个客观指标决定**：

1. **因果稳定性指标**：沿着边 $E$ 触发动作，产生预期后验结果的概率是否 $\ge 90\%$？如果低于该值，说明当前状态节点存在隐式未分离的子状态（需要细化）。
2. **决策剪枝比率**：拥有该状态点后，是否能帮弱模型剪掉 $\ge 50\%$ 的无用分支探索？
3. **合并同类项规则**：
   * 纯展示类滚动、列表微更新、时间戳更新：**强制合并为同一状态点**。
   * 出现拦截弹窗、表单校验错误呈现、主路由跳转、DOM 关键操作能力翻转：**必须分裂为独立状态点**。

## 六、 推进实施建议与验证里程碑

### 里程碑 1：数据结构契约与 Mock 图寻路（Day 1）
* 在 `agent-native-web/docs/` 归档图工程规格与 JSON Schema（`business_graph_schema.json`）。
* 在本地构建一个 3 步业务跳转的受控夹具（如：未登录 -> 登录页 -> 账户中心 -> 修改邮箱）。

### 里程碑 2：前置静态路由透视探针（Level 1 透视实测）
* 编写浏览器端轻量注入脚本，实测主流 SPA 站点（GitHub、Vue 文档站、常见后台框架）的前端 Router 内存挂钩成功率。
* 评估能否在 100ms 内提取出合法的二级路由路网。

### 里程碑 3：运行时结晶与对照消融实验（真实检验价值）
* 对照组：Agent 纯靠现有的 `world_guide` + `world_act` 盲走多步向导任务。
* 实验组：Agent 在业务图工程驱动下按边索骥推进。
* **核心验收指标**：
  * **决策往返轮数（Turn Count）**：是否实现从 15+ 轮缩减至 3~5 轮？
  * **Token 消耗与成本**：是否实现 60% 以上的下降？
  * **容错恢复率**：在边人为失效时，自愈回退耗时是否可控？
