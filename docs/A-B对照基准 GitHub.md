# A/B 对照基准：GitHub 任务图复用

## 验证日期

2026-09-04

## 目的

比较两种完成同一个真实网站流程的方式：

- A 组“页面优先”：每次打开 GitHub 后，重新查找入口和输入框，不读取历史任务图。
- B 组“任务图复用”：先读取历史任务图并规划目标路径，再查找当前页面构件并执行。

两组均执行同一个只读流程：进入 `git/git` 仓库的 Pull requests 页面，筛选确定不存在的作者。每组独立运行 3 次。

安全范围：不登录、不评论、不创建、不修改仓库内容。

## 原始结果

| 指标 | A 组：页面优先 | B 组：任务图复用 |
|---|---:|---:|
| 独立运行次数 | 3 | 3 |
| 成功次数 | 3 | 3 |
| 平均耗时 | 66.883 秒 | 69.958 秒 |
| 中位数耗时 | 66.221 秒 | 70.539 秒 |
| 平均工具调用次数 | 10 | 10 |
| 平均 `world_find`（目标发现）次数 | 2 | 2 |
| 平均 `world_act`（页面动作）次数 | 3 | 3 |
| 平均 `world_task_plan`（任务规划）次数 | 0 | 1 |
| 平均业务状态读取次数 | 3 | 2 |

补充结果：

- 严格安全规划：`blocked`（阻断）；
- 任务图状态：`replayed`（已达到回放阈值，但还未达到完整验证）；
- 任务图轨迹：9 条；
- B 组 3 次均使用候选路径完成执行；
- 每次的目标发现次数减少量：0；
- 每次的页面动作次数减少量：0；
- B 组平均耗时比 A 组高 3.075 秒，约 4.6%。

## 结论

### 已确认

1. 任务图没有让当前实现减少实际页面动作。两组都需要 2 次目标发现和 3 次页面动作。
2. 任务图规划本身可以在新会话中复用历史路径，并完成 3/3 次真实执行。
3. 对未达到安全验证级别的目标，严格模式会阻断，而不是猜测执行。
4. 任务图复用增加了一次规划调用，但减少了一次显式业务状态读取；总工具调用数相同。

### 推断

当前任务图更像“业务流程安全层”和“可审计的路线层”，还不是“网站原生接口层”。它的主要价值是降低误操作、避免重新猜路径、保留失败分支和支持跨会话复用。

### 不确定

本次样本只有每组 3 次，且真实网站加载受网络影响；不能据此判断长期平均速度。工具调用次数也不能直接等同于模型令牌、模型费用或模型思考时间。

## 下一步

如果要验证速度和成本收益，下一步必须让任务图中的操作节点携带可复用的目标解析策略或网站原生执行入口。否则每次执行仍要重新 `world_find`，任务图只能提供规划和安全收益。

这不要求新增一套用户可见工具，优先在现有适配器和 `world_act` 执行链中复用“操作名 → 目标解析 → 动作参数”的绑定，然后重新跑同一套 A/B。
