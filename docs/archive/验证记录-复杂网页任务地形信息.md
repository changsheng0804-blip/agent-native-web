# 验证记录：复杂网页任务的地形信息

## 文档状态

**状态：第一轮最小对照已完成，结论仍是探索性结论，不代表产品路线已经成立。**

本记录只验证“站点专属地形先验是否能帮助智能体完成复杂网页任务”。它不验证公共网页地图网络，也不把本地实时地图能力是否存在作为变量。

## 一、验证问题

在同一个公开网站、同一个只读任务和同一个 MCP 能力下：

- A 组：没有预先编写的站点专属地形卡，只能用通用 MCP 能力现场理解页面。
- B 组：额外提供一张简短的站点专属地形卡，只描述区域、入口和页面关系，不提供网页元素编号或坐标。

本轮希望观察：

```text
地形先验
→ 是否更快定位目标
→ 是否减少错误探索和歧义
→ 是否减少 MCP 调用和返回信息量
→ 是否更准确地判断入口所属区域和后续去向
```

## 二、实验控制

【已确认】

- 使用 4 个相互独立的子代理，全部指定为 `gpt-5.6-luna`，推理强度为中等。
- 每个子代理只负责一个条件和一个网站，并在网站内完成两个任务。
- 每个任务都启动独立的本地 MCP 进程和全新的浏览器上下文。
- 没有使用登录状态、私有数据、控制台、发布、提交、编辑或其他写入操作。
- 主要信息源是本地 MCP 的结构化查询和 `world_map`，没有把截图作为主要信息源。
- 本轮 `world_map` 在 A、B 两组均可使用，因此验证的是“外部站点地形先验”的增益，而不是验证地图工具本身有没有价值。
- 所有耗时、调用次数和字符数都是近似测量，不是模型 token 精确计费。

## 五、初步分析

### 1. 本轮没有证明“地形卡必然显著提速”

火山官网的两个任务中，B 组平均首次定位时间约 7.96 秒，A 组约 10.27 秒；主要改善来自 V2，V1 几乎没有变化。样本太小，不能把这个约 22% 的平均差异视为稳定效果。

GitHub 的 G1 中，B 组反而更慢，而且两组都遇到“预期结构与实际页面不一致”的问题。G2 两组接近，B 组只表现出轻微的定位优势。

### 2. 地形卡的价值更像“减少理解歧义”，还不是“减少底层扫描”

本轮 B 组没有减少 `world_map` 调用、MCP 调用或返回字符数。原因可能是：

- 两组都需要先打开页面并获得当前真实结构。
- B 组虽然知道功能区域，但仍要用实时结构确认当前页面事实。
- 本轮任务主要是找入口和判断区域，步骤短，还没有充分测试跨页面、多动作和状态变化。

但在火山官网 V1 中，A 组出现了父容器误命中，B 组没有出现这一歧义；这说明地形先验可能首先改善“我正在找的到底是什么”和“它应该位于哪里”的判断。

### 3. 实际页面事实必须优先于地形先验

GitHub 的结果非常重要：B 组地形卡认为 Issues 是仓库导航中的常见入口，但本次实际首页没有暴露它。地形信息如果被当成事实硬套，会产生误导；它只能作为路径提示，不能替代实时页面证据。

合理的优先级应是：

```text
站点地形先验：缩小搜索空间、提供预期结构
实时页面事实：确认当前页面实际存在什么
动作证据：确认操作后是否真的产生预期结果
```

### 4. 本轮暴露了 MCP 自身还需要改进的地方

- GitHub 首页宽泛查询返回量过大，说明页面地图和实体查询还需要更好的分层、摘要和按区域展开。
- 部分中文返回存在编码显示异常，虽然没有阻断本轮目标判断，但会影响实际使用体验。
- GitHub Issues 的搜索表单被识别，但输入框没有稳定地作为独立输入控件暴露，说明复杂控件的语义抽取仍不完整。
- “加载中”状态与已经可用的结构同时存在，智能体需要更清楚地区分“页面未稳定”和“目标区域已可验证”。

## 六、第一轮结论

【已确认】

- 采用独立同模型子代理进行 A/B 隔离是可执行的。
- 在公开网站、无登录、只读任务中，MCP 可以让子代理通过结构化查询和地图定位真实网页入口，并读取公开链接关系。
- 站点专属地形先验在部分任务上能减少歧义、缩短定位时间，但本轮没有证明它稳定提升整体任务效率。
- 地形信息不能取代实时页面事实；实际页面结构与先验不一致时，实时证据必须优先。

【推断】

复杂网页地形信息更可能在以下任务中体现价值：跨多个页面的路径规划、多个动作连续执行、弹窗/展开/筛选等状态变化、需要根据动作结果继续决策的任务。短平快的入口识别任务不足以证明它的完整价值。

【不确定】

目前还不能判断：

- 地形信息的维护成本是否低于每次现场探索。
- 地形信息是否能稳定减少真实任务的总调用次数和总返回量。
- 它相对于更好的提示词、Skill（工作方法说明）、更强模型或视觉兜底的独立增益有多大。
- GitHub 本次的导航差异属于长期结构还是临时渲染状态。

## 七、下一轮最小验证建议

下一轮不再只测“找到入口”，而是使用两个公开、多步骤、可验证结果的只读任务：

1. GitHub：从仓库首页进入 Issues，定位筛选区域，读取一个公开问题的标题和状态，再返回确认路径。
2. 火山引擎官网：从首页定位“进入火山方舟”和“模型广场”的关系，沿公开链接进入其中一个页面，只读确认页面标题、主区域和返回路径。

每个条件至少做 3 次独立重复，并固定记录：

- 首次定位目标时间。
- 首次正确操作时间。
- 完成任务总时间。
- MCP 调用数和各工具分布。
- 返回字符数。
- 错误探索、错误操作和恢复次数。
- 页面事实与地形先验冲突次数。
- 最终结果判断是否正确。

只有当 B 组在至少两个网站、多个重复任务中同时降低总任务时间或错误恢复成本，才可以继续把“复杂网页地形信息”列为优先产品方向；否则应暂停独立地形资产建设，优先改进实时结构抽取和证据反馈。
