# 探索方向：实时页面信道与操作反馈

## 文档状态

**状态：独立探索方向，已进入最小验证；不是已经确定的完整架构。**

本方向只讨论一个问题：智能体执行网页操作后，能否通过独立、轻量、及时的页面信息信道，准确知道页面发生了什么，而不必重新读取整页结构。

本方向与“实时任务导览”并行但分工不同：

```text
实时任务导览：告诉智能体接下来应该往哪里走
实时页面信道：告诉智能体刚才页面到底发生了什么
```

本方向也与“复杂网页任务的地形信息”独立。复杂网页地形信息关注长期、复杂的环境理解；实时页面信道关注当前页面的即时事实和操作反馈。

## 一、问题背景

网页操作的关键困难不只是找到按钮，还包括确认动作结果：

- 点击后是否真的跳转了页面；
- 是否只是页面局部刷新；
- 是否弹出了菜单、弹窗或确认框；
- 是否出现了错误提示；
- 是否需要等待页面继续加载；
- 页面结构变化后，原来的任务导览是否已经失效。

传统浏览器操作经常通过延时轮询、重新读取 DOM（网页结构）或再次截图来判断结果。这会带来延迟、重复信息和误判。

当前项目的一次真实验证已经发现：GitHub 页面实际从仓库首页跳转到了 `/pulls`，但 `world_click` 仍然因为点击目标附近没有明显变化而判断“无变化”。

这说明“页面局部变化”和“页面整体事实变化”之间还没有被统一处理。

## 二、核心设想

同一个实时网页世界作为唯一事实来源，再按用途提供不同的小型信息信道：

```text
实时网页事实源
├─ 页面状态信道：当前网址、加载状态、弹窗、登录状态
├─ 页面变化信道：新增、消失、更新、可见性变化
├─ 操作证据信道：某次动作前后发生了什么
├─ 任务导览信道：当前任务相关的区域和下一步
├─ 结构目录缓存：当前页面已确认的区域和入口
└─ 内容读取信道：按需读取文本、表格和页面内容
```

这里的“信道”不要求一开始就实现成多个网络连接。第一版可以理解为：同一个网页世界里的不同数据视图，各自只返回自己负责的信息，并且可以有自己的读取位置。

## 三、三条优先信道

第一阶段只优先验证三条，不建设完整的多信道系统。

### 1. 页面状态信道

只保留最新的页面状态：

```text
当前网址
页面标题
页面是否稳定
页面是否发生跳转
是否出现或消失弹窗
是否出现菜单或对话框
页面版本或变化序号
```

它回答的是：

```text
页面还在原处吗？
页面是不是换了？
现在有没有需要优先处理的弹窗？
```

### 2. 页面变化信道

只读取自上次以来的新变化，而不是重新发送整个页面：

```text
新增了什么
消失了什么
哪些区域发生更新
哪些元素变得可见
```

它更像网页的“变化流水”，而不是网页快照。

### 3. 操作证据信道

把一次具体动作和页面变化绑定起来：

```text
动作：点击某个链接
动作前：页面网址和目标区域状态
动作后：网址、弹窗、页面版本和相关区域状态
结论：已跳转、已弹出、已改变、无变化或无法确认
```

操作证据必须优先使用整体页面事实，例如网址变化；不能只看点击元素附近的局部区域。

## 四、与实时任务导览的关系

两者应当分离：

```text
智能体提出任务
        ↓
任务导览信道：当前应该看哪里、下一步做什么
        ↓
执行动作
        ↓
页面状态 / 变化 / 操作证据信道：刚才发生了什么
        ↓
任务导览失效或更新
        ↓
生成下一步导览
```

任务导览不应该自己猜测动作结果。它应该等待页面信道提供事实，再决定是否继续。

## 五、信息缓存的边界

不同信道可以采用不同的保存方式：

| 信息 | 建议保存方式 | 原因 |
|---|---|---|
| 当前页面状态 | 只保留最新值 | 变化快，旧状态很快失效 |
| 页面变化 | 按顺序保存事件 | 需要知道发生过什么，可用读取位置继续读取 |
| 操作证据 | 按动作保存前后对照 | 需要追溯某次操作是否成功 |
| 任务导览 | 按任务和页面版本缓存 | 页面变化后自动失效 |
| 结构目录 | 按页面版本短暂缓存 | 避免重复扫描，但不能使用过期结构 |
| 页面内容 | 按需读取，默认不缓存 | 内容量大，也可能涉及隐私 |

关键原则是：

> 多个信道保存不同的信息摘要，不保存多份完整网页。

否则只是把“整页信息洪水”复制成多个版本，并没有真正降低负担。

## 六、当前 MCP 能力的对应关系

当前项目已经有部分可复用基础：

- `world_changes`：页面变化信道的基础；
- `world_wait`：等待变化出现或消失的基础；
- `world_click`：操作证据信道的基础，但整体跳转判断仍需加强；
- `world_open`：提供页面状态和变化序号；
- `world_map`：任务导览和结构目录的基础；
- `world_entity`：读取具体构件和区域关系的基础。

因此第一步不应重新设计网页运行时，而应优先把整体页面状态、变化事件和操作结果组合起来。

## 七、最小验证问题

先验证三个简单事实：

1. 点击一个明确的公开链接后，是否能及时识别网址变化；
2. 点击一个会打开菜单或弹窗的控件后，是否能及时识别新状态；
3. 对于目标区域没有局部变化但页面已经跳转的情况，是否能避免误报“无变化”。

验证只使用公开网站和只读动作，不涉及登录、提交、发布或删除。

## 八、验证成功的直观标准

不追求一开始测很多数字，只看智能体能否得到正确的实时反馈：

```text
点击后发生页面跳转 → 明确告诉智能体“已跳转到哪里”
出现弹窗 → 明确告诉智能体“出现了什么弹窗、可做什么”
没有变化 → 确认页面整体也没有变化后，才报告“无变化”
无法确认 → 明确报告“无法确认”，不强行猜测
```

## 九、风险与边界

- 页面变化太多时，不能把所有变化都原样交给智能体，需要摘要和重要性排序。
- 页面整体重新渲染可能制造大量假变化，需要区分真实导航、弹窗和普通重绘。
- 页面信道只能报告事实，不能自动把网页文本中的指令当成可信命令。
- 登录、验证码和高风险操作仍需要清晰的人工介入边界。
- 页面变化信道不能替代任务导览；它只负责报告发生了什么。

## 十、当前阶段判断

【已确认】当前 MCP 已有页面变化、等待和操作效果的基础能力，但整体跳转反馈与局部变化判断还没有完全统一。

【推断】独立的页面状态、变化和操作证据信道，可能比不断扩大单次页面快照更能提升实时性和鲁棒性。

【不确定】多信道是否能稳定降低任务总耗时、减少重复读取，以及是否需要真正的主动推送机制，目前尚未验证。

【建议】先完成页面跳转、弹窗出现和操作证据的最小 Demo；验证有效后，再考虑结构目录缓存、任务导览失效机制和更多信息信道。

## 十一、第一轮最小验证结果

【已确认】

- 弹窗反馈有效：在公开 Google Flights 页面点击乘客按钮，`world_click` 返回 `effected/high`，并明确给出出现 `dialog`（弹窗）的证据。
- 事件驱动等待有效：本地动态测试页中，已存在的目标约 0.02 秒返回，动态出现约 0.04 秒命中，动态消失约 0.18 秒命中；不存在目标则按约 2 秒超时。说明 `world_wait` 已经可以作为低延迟事件信道的基础。
- 页面跳转可以从整体页面状态中识别：GitHub 仓库首页点击 Pull requests 后，页面网址变为 `https://github.com/git/git/pulls`，新页面也能继续查询到筛选区域和搜索输入框。
- 当前页面变化流能够捕获跳转期间的大量结构变化，但一次跳转可能产生约 2,000 条以移除和重绘为主的事件，不能原样全部交给智能体。

【已确认】页面跳转的操作结果判断还不稳定：一次运行中网址已经变为 `/pulls`，但局部效果判断返回“无变化”；另一次运行中返回 `effected/high`。这说明整体网址状态比点击目标附近的局部差异更适合作为导航证据。

【推断】第一版最有价值的信道组合是：

```text
页面状态：网址、页面稳定状态、弹窗
    +
变化摘要：只保留重要区域和重要构件变化
    +
操作证据：把动作前后整体状态绑定起来
```

【不确定】页面变化事件中的大量重绘，究竟能否通过当前重要性分级稳定压缩，仍需要在更多动态网站上观察；暂时不能把完整事件流称为可直接使用的实时反馈。

【建议】下一步先修正一个最小闭环：动作后优先检查网址、页面状态和弹窗，再结合局部区域变化判断结果；只有在这个闭环稳定后，才增加独立结构缓存和更多信道。

## 十二、最小闭环实现结果

【已确认】当前 `world_click` 已加入页面整体反馈：

- `feedback.page`：动作前后网址、标题和页面稳定状态；
- `feedback.overlays`：动作前后新增或消失的弹窗/菜单；
- `feedback.changes_seq`：页面变化序号前后值；
- `effect.global`：网址变化、新覆盖层和标题变化的强信号。

当网址发生变化或页面整体出现新的弹窗/菜单时，服务器会优先用整体事实修正局部效果判断，保留原来的局部判断作为 `local_verdict` 和 `local_why`，方便诊断。

【已确认】最小回归验证通过：

- 本地无副作用标题：仍返回 `no-change`，且全局状态没有变化；
- 本地 URL 跳转：返回 `effected/high`，捕获整体网址变化；
- 本地远处弹窗：返回 `effected/high`，捕获整体覆盖层变化；
- 公开 Google Flights：乘客按钮弹窗反馈仍返回 `effected/high`；
- 公开 GitHub：从仓库首页进入 Pull requests 后，返回 `effected/high`，并明确报告 URL 从仓库首页变为 `/pulls`；
- 事件驱动等待和官方 MCP 初始化回归测试均通过。

【推断】这个最小闭环已经证明：页面整体状态可以作为操作反馈的独立基础，不必每次重新读取整页；但目前它仍是动作返回中的整体反馈，还不是主动推送的独立网络信道。

【建议】下一步先观察这个闭环在更多公开动态页面上的稳定性，再决定是否把页面状态、变化摘要和操作证据拆成独立的可读取信道；暂不扩展更多缓存类型。

## 十三、三条独立可读取信道的实现结果

【已确认】当前 MCP 已新增三条独立工具：

- `world_state`：只返回当前最新页面状态，不附加全量 `status`；
- `world_change_digest`：只返回变化数量、重要性统计、关键构件和变化游标，不返回原始事件列表；
- `world_evidence`：按独立证据序号读取动作前后页面状态和结果，不保存填表的具体文本。

原有 `world_changes` 继续保留，作为需要深入诊断时的原始变化流。这样形成了“平时读摘要、需要时查原始变化”的两级读取方式。

【已确认】本地信道回归验证已通过：

```text
页面状态信道：只返回当前状态
变化摘要信道：不返回原始事件
操作证据信道：独立记录无变化、URL 跳转和弹窗
```

官方 MCP 初始化验证显示工具总数从 18 个变为 21 个，原有真实弹窗测试仍然通过。

【推断】当前实现已经验证了“多个小信道共享同一个网页世界”的可行性，而且没有复制多份完整页面；但证据信道目前只在当前 world 内存中保存，网页世界关闭后记录即消失，也还没有主动推送。

【建议】下一步先在真实动态网站上观察三条信道的输出是否足够稳定，再考虑：

1. 让任务导览根据页面状态和变化摘要自动失效/刷新；
2. 为变化摘要增加更明确的导航、弹窗和内容区域分类；
3. 再评估是否需要持久化或主动推送，而不是现在就扩展缓存体系。

## 十四、实时任务导览接入结果

【已确认】当前新增 `world_guide`，会组合三条页面信道和当前实时结构，返回：

- 当前页面状态；
- 自指定游标以来的变化摘要；
- 最近动作的短证据；
- 与任务词匹配的页面区域；
- 少量候选入口和公开链接关系；
- 下一步建议和新的读取游标。

导览不会返回完整 `world_map`，而是先搜索地图区域，再用当前页面可交互元素做轻量语义兜底。地图中没有列出的目标，也有机会被任务词找到。

【已确认】公开 GitHub 分段试跑通过：

```text
仓库首页
→ world_guide 找到 Pull requests 入口
→ world_click 可进入 /pulls

/pulls 页面
→ world_guide 找到搜索区域和筛选控件
```

中文“拉取请求”“筛选”等任务词可以通过别名匹配页面中的英文结构。动作后的第二次导览能够读取新的页面状态和最近操作证据。

【已确认】一次试跑中点击因为动态页面重绘没有立即跳转，`world_evidence` 正确保留了 `no-change`；这说明导览提供的路径不能替代动作证据，只有整体页面状态确认网址变化后，才能把路线标记为已完成。

【推断】当前最小架构已经形成：

```text
world_guide：任务相关路径
world_state：当前页面事实
world_change_digest：页面变化摘要
world_evidence：动作结果证据
```

【不确定】当前任务词匹配仍然是轻量规则，不是完整语义理解；复杂任务可能需要智能体先提供更明确的目标词。多页面连续路径和更复杂控件仍需继续验证。

【建议】下一步优先验证弹窗出现、标签切换、筛选展开和导航失败恢复四类场景；暂不建设持久化网站地图或主动推送系统。
