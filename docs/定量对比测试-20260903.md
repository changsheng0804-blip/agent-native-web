# 定量对比测试（2026-09-03）

## 测试口径

- 原生浏览器：同一个浏览器标签页重复打开并用页面语义定位、点击。
- MCP：每次新建独立网页世界，执行 `world_open → world_find → world_act`。
- 本地页面：`tests/fixtures/far_modal.html`，5 次/方案。
- GitHub 页面：`https://github.com/git/git`，2 次，仅用于观察复杂页面趋势。
- 时间包含工具调用和浏览器等待，不包含模型思考时间。

## 本地静态弹窗页（5 次平均，毫秒）

| 路径 | 打开 | 定位 | 动作确认 | 总耗时 |
| --- | ---: | ---: | ---: | ---: |
| 原生浏览器（复用标签） | 155 | 30 | 298 | 482 |
| MCP `action`（独立） | 525 | 50 | 728 | 1303 |
| MCP `terrain`（独立） | 394 | 21 | 696 | 1110 |
| MCP `stable`（独立） | 915 | 22 | 697 | 1634 |
| MCP `action`（复用浏览器进程） | 241 | 22 | 688 | 951 |
| MCP `receipt`（独立） | 374 | 23 | **10 首回执** | 1112（最终确认约 704） |

所有动作均得到 `page_outcome=progressed`，没有错误成功判定。

## GitHub 复杂页面（2 次平均，毫秒）

| 路径 | 打开 | 定位“Pull requests” | 备注 |
| --- | ---: | ---: | --- |
| 原生浏览器 | 2950 | 1905 | 页面已完成常规加载 |
| MCP `action` | 7550 | 486 | 返回时 `full_scan=pending`，后台扫描继续 |

## 结论边界

1. MCP 当前最大成本仍是“启动/注入网页世界”，不是定位本身。
2. `action` 比 `stable` 明显更快；`terrain` 在本地页上最快，但复杂页面仍需更多样本。
3. `receipt` 只缩短“动作已发出”的等待，不会让最终页面后果凭空消失；适合动作后可以并行处理其他工作的场景。
4. GitHub 样本显示 MCP 可以在完整扫描结束前定位部分目标，但本轮 MCP 的总耗时仍高于原生浏览器。
5. 原生浏览器复用现有标签，MCP 独立模式包含浏览器进程和网页世界初始化成本，因此不能把绝对总耗时直接当成纯算法差距。

## 重复任务（4 次）

先清空本次测试产生的路线记忆，再执行 4 次相同任务；对照组通过环境开关关闭历史提示。历史组第 3、4 次命中已验证指纹路线 2 次，4 次动作全部成功。

| 组别 | 历史命中 | 指纹定位 | 成功次数 | 平均单次耗时 |
| --- | ---: | ---: | ---: | ---: |
| 历史路线 | 2/4 | 2/4 | 4/4 | 1334ms |
| 无历史对照 | 0/4 | 0/4 | 4/4 | 1384ms |

本轮只减少约 3.6% 总耗时，未达到 30% 的验收目标。原因已经定位：路线提示虽跳过了完整候选构建，但每次仍要重新打开网页世界；启动成本和动作确认成本占据大头。历史路线当前更明显减少的是“探索内容”，不是“总墙钟时间”。

补充测试：复用浏览器进程后，历史组平均 1193ms、无历史组 1182ms，差异在本轮噪声范围内，说明仅靠路线提示还不能解决启动成本。

## 两个网页世界并行调用

同一时间打开一个持续变化页和一个静态页，再同时发起两个点击：

| 路径 | 打开墙钟时间 | 定位墙钟时间 | 两个动作墙钟时间 |
| --- | ---: | ---: | ---: |
| 原生浏览器（两个标签） | 544ms | 124ms | 301ms |
| MCP（当前单一 Playwright 线程） | 1490ms | 47ms | 1851ms |

MCP 两个动作都正确返回，但动作阶段仍然互相等待。这确认了第二阶段“按网页世界拆分执行器”是高优先级优化；在迁移前不能把当前 MCP 称为真正的跨世界并行。
