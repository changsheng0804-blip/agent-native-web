# 真实网站操作对比记录

## 测试目的

比较 Agent-Native Web MCP 与 Codex 原生浏览器在真实网页上的操作方式，重点观察复杂页面的进入速度、定位歧义、反馈方式和失败可解释性。

测试只使用公开页面和无破坏性动作，不登录、不提交敏感信息、不购买、不修改账户数据。

## MCP 实测

| 网站 | 操作 | 结果 | 反馈 |
| --- | --- | --- | --- |
| Wikipedia | 打开主页并扫描页面 | 成功 | 858 个结构元素、343 个可交互元素、19 类语义角色；状态稳定 |
| GitHub Explore | 打开页面并点击 Platform | 成功 | 930 个结构元素；按钮通过语义名称定位，产生 138 条变化事件 |
| Hacker News | 打开首页并读取结构 | 成功 | 761 个结构元素、285 个可交互元素；无需截图即可读取链接结构 |
| Google Flights | 点击乘客控件 | 成功 | 返回 `effected/high`，确认弹窗出现；负例点击返回 `no-change/high` |
| Google Flights | 填入 Tokyo | 成功 | 返回填表生效报告，并找到 Tokyo 机场选项和弹窗 |
| 火山引擎官网 | 查找“进入火山方舟” | 成功 | 570 个结构元素中精确找到 1 个 link，返回名称、稳定指纹、坐标和目标地址 |
| 火山引擎官网 | 查找“模型广场” | 成功 | 精确找到 1 个 link，可直接得到对应模型页面地址 |

MCP 测试中的时间包含启动浏览器、注入内核和页面加载，不等同于单次点击耗时：Wikipedia 约 9 秒、GitHub 约 13 秒、Hacker News 约 7 秒。启动后的优势主要体现在按需查询和操作后反馈，而不是消除网络加载时间。

## Codex 原生浏览器对照

| 网站 | 操作 | 结果 | 观察 |
| --- | --- | --- | --- |
| Wikipedia | 用可访问名称定位搜索框并填入关键词 | 初次失败 | 页面同时存在可见搜索框和隐藏副本，直接按键时匹配歧义；加可见性过滤后可定位 |
| GitHub Explore | 用按钮名称定位 Platform 并点击 | 定位成功，点击未完成 | 原生浏览器已找到唯一可见按钮，但浏览器控制通道在点击派发前超时；这是对照通道问题，不能归因于网页模型 |
| Wikipedia/GitHub | 读取页面 DOM 快照 | 成功 | 能读取页面，但需要在原始 DOM 或可访问性树中继续判断目标和页面变化 |
| 火山引擎官网 | 读取页面结构并定位 AI 入口 | 部分成功 | DOM 快照直接显示主标题、模型与场景切换、火山方舟入口和 API KEY 入口；仍需要继续处理页面层级与可见性 |

## 结论

1. MCP 的核心优势不是“也能点击”，而是把网页预先整理成带编号、语义、空间和状态的可查询世界。
2. `world_map` 适合先看全局，再按需深入目标区域，避免智能体一开始读取所有元素。
3. `effect`、`world_changes` 和 `world_wait` 把操作后的真实页面变化直接反馈给智能体，减少延时轮询和“没有反馈所以猜测成功”的空间。
4. 原生浏览器仍然更通用，适合最后的视觉确认和兜底操作；但在复杂页面上，定位歧义和反馈判断需要由调用方额外处理。
5. 本轮没有测量严格 Token 节省比例，因此“降低 Token 消耗”应作为设计动机和潜在收益，不应写成未经基准测试的固定数字。
6. 火山引擎官网属于结构较深、内容较多的典型页面；MCP 的“先导览、再按角色和文本精确查询”明显比从原始 DOM 快照中人工判断页面关系更适合智能体。

## 当前限制

- MCP 启动阶段仍受网页网络速度、动态渲染和反爬机制影响。
- 普通网页的结构是由注入内核推断出来的，不等同于网站已经原生实现 Agent-Native 标记。
- Codex 原生浏览器本轮一次点击受控制通道超时影响，不能据此得出所有原生浏览器操作都会失败的结论。
