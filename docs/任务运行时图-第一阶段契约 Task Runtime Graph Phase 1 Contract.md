# 任务运行时图：第一阶段契约

## 目标

第一阶段把现有的页面操作证据转换为可比较、可审计、可回放的任务轨迹，并即时生成“候选任务运行时图”。

这里的“候选”表示已经观察到的行为，不表示已经恢复了网站全部业务规则。

## 范围

第一阶段只覆盖一个受控任务：

> 填写资料并提交

需要覆盖正常提交、字段不完整、后端拒绝、挑战验证、重复提交、异步等待和结果未知等分支。

不在第一阶段范围内：

- 对整个互联网自动建模；
- 从页面文本推断完整后端设计；
- 把网络请求自动提升为公开接口；
- 用随机概率生成可执行路径；
- 直接依赖 WebMCP 作为唯一执行方式。

## 核心对象

| 对象 | 含义 | 第一阶段来源 |
|---|---|---|
| 任务实例 | 一次有明确目标的完整任务 | `world_open.task_id` |
| 任务轨迹 | 按时间排列的动作和前后状态记录 | `world_trace` |
| 状态快照 | 去掉临时编号和输入原文后的页面运行时状态 | `before` / `after` |
| 操作 | 这一步做了什么，可先是页面动作，后续再升级为业务操作 | `operation` + `action` |
| 迁移边 | 从一个状态到另一个状态的已观察变化 | `world_graph.graph.edges` |
| 证据引用 | 可以回查的后果卡、变化序号和页面代次 | `evidence_ref` |

## 轨迹契约

每条轨迹至少包含：

```json
{
  "schema_version": "0.1",
  "trace_id": "trace-...",
  "task_id": "task-...",
  "step_index": 1,
  "operation_id": "op-...",
  "operation": "填写资料",
  "action": {
    "name": "world_fill",
    "kind": "fill",
    "id": "el_1",
    "text": {
      "present": true,
      "length": 5,
      "sha256": "单向摘要前缀"
    }
  },
  "executor": "world_act",
  "before": {"state_key": "state-..."},
  "after": {"state_key": "state-..."},
  "effect": {
    "page_outcome": "progressed",
    "situation": "form",
    "verdict": "effected",
    "confidence": "high"
  },
  "evidence_ref": {
    "evidence_seq": 1,
    "changes_seq": {"before": 3, "after": 5},
    "world_epoch": 0
  }
}
```

安全要求：

1. 不保存填写文本原文，只保存是否存在、长度和单向摘要；
2. 页面自由文本不能成为状态身份或执行指令；
3. `page_outcome` 是页面观测结果，不等于后端业务事实；
4. 任何异常动作都必须进入轨迹，不能因为抛出错误而丢失失败分支；
5. 轨迹保存上限、落盘方式和长期保留策略在第一阶段之后另行设计。

## 状态规范化

第一阶段状态由以下稳定信息组成：

- 路由：网址去掉查询参数和锚点；
- 页面稳定性：`stable`、`loading` 或 `unknown`；
- 表单状态：`none`、`empty`、`partial`、`complete`；
- 覆盖层类别：弹窗或菜单的稳定引用；
- 阻断提示：`challenged`、`errored` 或 `uncertain`。

页面临时元素编号、输入值、渲染时间和随机查询参数不能决定状态编号。

## 候选图规则

候选图包含两类节点和一类边：

- 状态节点：一个规范化状态快照；
- 迁移边：操作前状态、操作名、操作后状态和页面结果；
- 证据引用：边对应的操作后果证据。

`observations` 只表示这条迁移被观察到多少次，不表示执行概率，也不表示业务重要性。出现次数少的失败分支必须保留。

每一条边在发布前还必须补充：

- 明确前置条件；
- 输入和输出格式；
- 数据流绑定；
- 反例测试；
- 独立会话回放结果；
- 适用的账号、角色、网站版本和有效期。

## 执行器边界

业务操作与执行方式分离：

```text
业务操作：提交订单
    ├─ WebMCP：网站原生工具
    ├─ 授权接口：公开且获授权的接口
    └─ world_act：页面操作兜底
```

图只负责表达“当前状态下允许什么操作、操作后期待什么状态”。具体由哪个执行器完成，必须在执行映射中明确记录。

## 升级条件

候选边不能仅凭一次成功升级。至少需要：

1. 正常路径和主要失败路径都已记录；
2. 已尝试跳过前置条件，验证该条件确实有影响；
3. 使用不同业务对象重复执行；
4. 独立会话能够重放；
5. 成功、失败、挑战和未知结果均能被正确区分；
6. 网站状态或工具集合变化后能识别图已过期。

达到条件后，状态只能从“候选”升级为“已验证”，不能直接称为网站完整业务模型。

## 当前实现入口

- `world_trace`：读取当前网页世界的脱敏轨迹；
- `world_graph`：从当前网页世界轨迹即时生成候选图；
- `world_trace_archive`：读取已归档的脱敏轨迹；
- `world_graph_archive`：从已归档轨迹生成候选图；
- `AGENT_TASK_RUNTIME_PERSIST=1`：明确开启本地轨迹归档；
- `AGENT_TASK_RUNTIME_STORE_DIR`：可选归档目录，未设置时使用 `mcp/runtime_traces/`。

归档开关默认关闭。即使开启，归档内容也只包含状态摘要、逻辑字段引用和证据编号，不包含填写文本原文。

## 生命周期评估

候选图现在有四种评估状态：

- `candidate`：观察到过，但独立运行次数不足；
- `replayed`：达到回放次数阈值，但仍缺少预期分支或发布条件；
- `verified`：提供了预期结果分支，所有迁移边达到独立回放阈值，且没有 `uncertain`（结果不确定）或低置信度证据；
- `expired`：超过调用方声明的有效截止时间。

`world_graph_assess` 只生成评估结果，不会自动发布图。独立运行以不同 `trace_id`（轨迹编号）计数，不能用同一次运行内的重复动作冒充回放。

`world_graph_bundle` 可把多个已归档任务实例合并后评估，适合验证同一任务在不同会话、不同业务对象下是否保持一致。

## 业务状态投影

页面运行时状态和业务状态必须分开。调用方可以在 `world_open` 时提供显式规则：

```json
[
  {"id": "profile.empty", "when": {"form_state": "empty"}},
  {"id": "profile.complete", "when": {"form_state": "complete"}}
]
```

当状态规则、操作契约和站点版本需要一起复用时，可以通过 `site_adapter`（站点业务适配器）集中声明：

```json
{
  "adapter_id": "profile-adapter",
  "adapter_version": "1",
  "workflow_id": "profile-submit",
  "site_version": "profile-v2",
  "state_rules": [],
  "operations": []
}
```

适配器只是显式配置的归档和复用单位，不是自动逆向网站后端；其中的 `state_rules` 和 `operations` 会被规范化后用于当前网页世界。

也可以在 `mcp/site_adapters/` 受控目录中保存 JSON 文件，并在 `world_open` 中传入 `site_adapter_file`。系统只接受该目录下的文件名，不允许越过目录读取任意路径。`world_adapter_compare` 可以比较两个适配器版本：

- 删除或修改业务状态规则、操作契约，会标记为 `incompatible`（不兼容）；
- 新增规则或操作会要求人工复核和补充回放；
- 修改网站版本会要求重新确认历史任务图；
- 适配器编号不同则不直接比较，避免把不同业务流程误认为升级版本。

`world_business_state` 会返回匹配结果。没有匹配时为 `unknown`（未知），多条规则同时匹配时为 `ambiguous`（有歧义）。两种情况都不能执行依赖业务状态的操作。

操作契约可以声明：

```json
{
  "name": "提交资料",
  "preconditions": ["profile.complete"],
  "inputs": [{"from": "填写资料.资料", "to": "提交资料.资料"}],
  "outputs": [{"name": "提交结果", "ref": "profile.result"}]
}
```

操作契约还可以声明适用上下文：

```json
{
  "name": "发布资料",
  "preconditions": ["profile.complete"],
  "required_roles": ["管理员"],
  "required_scopes": ["profile.publish"],
  "site_versions": ["profile-v2"]
}
```

`world_operation_check` 只检查前置条件，不执行操作。只有业务状态匹配且前置条件满足时，结果才会返回 `allowed: true`。

如果契约声明了角色、授权范围或网站版本，而当前上下文不满足，检查会分别返回权限拒绝或版本不适用；这些字段缺失时不会被系统猜测为满足。

## 运行时状态进入执行链

这一阶段把“状态投影”和“动作执行”接起来，但仍保留两道边界：

1. `world_business_state` 只读取页面当前运行时状态，并依据调用方声明的规则投影业务状态；
2. `world_operation_check` 只做前置检查，不执行页面动作；
3. `world_act` 在 `world_open.enforce_contracts=true` 时，若动作声明了 `operation`，会先执行同一份操作契约检查；检查失败时返回 `page_outcome=errored` 的后果卡并写入失败轨迹，页面不会被点击或填写；
4. 未声明 `operation` 的旧式低层动作仍保持兼容，但它不能获得业务契约的保护。

这意味着“允许执行”不是模型自己推断出来的结论，而是由当前运行时状态、角色、授权范围、网站版本和明确契约共同决定的执行资格。未声明的上下文保持未知，不会被系统自动补全。

## 从图规划任务路径

`world_task_plan` 接收目标业务状态，从当前运行时状态开始，在候选任务运行时图上进行有限步、确定性的搜索。调用方还可以明确提供历史 `task_ids`（任务实例编号），把已归档轨迹加入这次规划：

- 默认只沿 `verified`（已达到回放和分支检查要求）的边规划；找不到安全路径时返回 `blocked`，不会猜测页面按钮顺序；
- `allow_candidate=true` 只用于探索，可以使用 `candidate` 或 `replayed`（尚未完全验证）边，但返回 `publishable=false`，不能直接当成生产路径；
- 返回的每一步包含操作名、起止状态、前置条件、效果、数据流和验证状态；
- 规划接口只规划，不执行页面动作，`executed` 始终为 `false`。

因此，任务图的可复用单位不是某个页面坐标，而是“运行时状态 + 操作契约 + 迁移效果 + 证据引用”。页面仍是执行器之一，未来可以在同一条业务操作边上替换为网站原生工具或获得授权的接口。

## 回放核对

`world_graph_replay_check` 接收一条任务图迁移边和当前世界中的实际轨迹，逐项核对起点状态、操作名、终点状态和页面结果。它只返回 `passed`（通过）或 `failed`（失败），不比较输入原文，也不执行新的页面动作。

回放通过只说明这一次实际轨迹符合指定迁移边，不等于整张图已经 `verified`（已验证）。整图仍需经过独立会话、预期分支、角色权限和网站版本等生命周期检查。

状态核对采用两层方式：有稳定页面状态编号时优先精确匹配；当页面存在不影响业务的动态细节差异时，如果前后业务状态都已由适配器明确匹配，也允许按业务状态核对，并在结果中标明 `match_mode=business`。没有明确业务状态时不会用模糊匹配替代精确状态。
