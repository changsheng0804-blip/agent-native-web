# 探索方向 A：复杂网页任务的地形信息

## 文档状态

**状态：独立的前置探索方向，待验证，不是已确定的产品路线。**

本文件只讨论一个问题：当智能体执行真实网页任务时，是否需要一份比当前页面快照、DOM（网页结构）或截图更适合它理解的“网页地形信息”。

本方向与“公共网页地图网络”完全独立，不以多人共享、远程服务或跨用户复用为前提。

## 一、问题背景

真实浏览器智能体通常被用于：

- 网站没有 CLI 或 API，只能通过网页完成任务。
- 人类不熟悉目标网站，需要智能体理解专业后台。
- 页面结构复杂、步骤多，需要跨多个页面或功能区。
- 内容发布、资料整理和表单录入等重复工作可以交给智能体。
- 云平台控制台、开发者平台和专业 SaaS 后台功能多、层级深、状态变化复杂。

典型任务包括：

```text
在内容平台发布一篇内容
在云服务控制台配置某项资源
在陌生专业后台找到一个设置
在没有 API 的网站完成多步骤资料整理
```

这些任务的困难不只是点击，而是智能体必须先理解一个陌生、复杂、不断变化的网页环境。

## 二、当前智能体的核心困难

很多时候，智能体所谓的“探索”更接近盲人摸象：

```text
看到局部页面
→ 猜测页面整体结构
→ 猜测按钮的作用
→ 点击并等待
→ 根据不完整反馈猜测结果
→ 再猜下一步
```

它需要知道的不是单个元素，而是：

- 页面有哪些区域和功能。
- 当前区域在整个网站中的位置。
- 当前页面有哪些可执行动作。
- 动作需要什么前置条件。
- 点击后是跳转、弹窗、展开、筛选还是状态翻转。
- 下一页面有哪些结构和可用功能。
- 哪些内容可以直接读取，哪些必须经过动作才会出现。
- 当前动作是否真正完成了预期目标。

## 三、什么是网页地形信息

“地图”只是比喻。智能体真正需要的是一份可查询的网页环境结构：

```text
空间层：页面有哪些区域、区域如何排列
结构层：页面和页面之间如何连接
能力层：每个区域可以执行什么动作
状态层：动作会造成什么状态变化
证据层：如何判断动作是否真的生效
```

例如“进入火山方舟”不只是一个链接，还应当知道：

```text
它位于模型服务区域
它是一个公开链接
点击后进入火山方舟概览页
可能需要登录
进入后会出现模型、推理或应用相关区域
当前页面可以先读取入口地址和相关公开结构
```

这比“元素在某个坐标”更接近智能体真正需要的环境知识。

## 四、完整结构与按需读取

需要区分两件事：

- **提供完整结构查询能力**：智能体可以在需要时查看整个页面或网站的结构。
- **每次默认发送完整结构**：可能造成上下文负担和新的信息洪水。

合理方向可能是：

```text
默认：返回页面总览和任务相关入口
需要时：查询某个区域的完整结构
继续需要时：查询页面之间的关系、前置条件和动作结果
```

智能体应该拥有“查看全图的能力”，但不一定每次都被迫阅读全图。

## 五、Skill 与网页地形信息的区别

Skill 可以告诉智能体：

```text
先看页面总览，再查目标，操作后验证
```

但 Skill 不知道具体网站的实际结构。

网页地形信息需要告诉智能体：

```text
这个网站有哪些区域
这个页面有哪些入口
这个入口通常通往哪里
这个功能需要什么前置状态
点击后会出现什么
下一页面还有什么结构
```

二者关系是：

```text
Skill：告诉智能体如何探索网页世界
网页地形：告诉智能体这个具体网页世界是什么样
```

## 六、与当前 Agent-Native Web MCP 的关系

当前项目已经有部分基础能力：

- `world_map`：页面区域和入口。
- `world_entities`：语义构件和位置。
- `fingerprint`：元素的候选稳定身份。
- `world_changes`：页面增量变化。
- `effect`：动作结果证据。
- `world_wait`：等待页面状态变化。

本方向不是立即增加一个公共地图服务，而是先判断这些本地能力是否足以构成对复杂网页任务真正有帮助的“地形信息”。

## 七、待验证假设

### H1：复杂网页任务的主要成本是环境理解，而不是网页扫描

如果网页结构扫描只需要几秒，但智能体需要多轮读取和试错才能找到目标，则地形信息可能有价值。

### H2：页面地图和动作结果证据能够显著降低任务试错

如果地图只帮助找到按钮，却不能告诉智能体动作前置条件和动作后果，则价值可能有限。

### H3：完整结构应作为可查询能力，而不是默认上下文

如果完整结构直接发送导致上下文负担增加，而按需查询能保持任务效果，则应采用分层查询。

### H4：地形信息能帮助智能体处理陌生专业网站

在火山引擎、内容发布平台、开发者控制台等任务中，有地形信息的智能体应该比没有地形信息的智能体更少走错页面和错误定位。

## 八、最小验证方案

1. 选择火山引擎官网、一个内容发布平台和一个开发者控制台。
2. 为每个网站准备 3～5 个无破坏性真实任务。
3. 记录没有地形先验时智能体的完整探索过程。
4. 手工整理一份最小地形信息，只包含区域、入口、动作和结果。
5. 让智能体使用这份先验完成同类任务。
6. 比较两组任务的时间、工具调用次数、错误定位、重复读取和结果判断错误。

## 九、验收指标

- 首次正确定位时间。
- 首次正确操作时间。
- 页面读取量和工具调用次数。
- 定位歧义次数。
- 错误操作次数。
- 把成功误判为失败的次数。
- 把失败误判为成功的次数。
- 从错误状态恢复所需时间。

## 十、停止条件

出现以下情况之一，应暂停本方向：

- 有地形信息不能稳定降低首次正确定位时间。
- 使用地形信息后仍需要重新完整理解页面。
- 地形信息维护成本高于重新探索。
- 页面变化导致错误先验频繁产生误操作。
- 地形信息只增加上下文，却没有提升真实任务成功率。

## 十一、与公共网页地图方向的关系

本方向可以独立推进，也可以与公共网页地图并行讨论，但二者不是前后依赖关系：

```text
方向 A：复杂网页任务的地形信息
验证智能体到底需要什么网页环境结构

方向 B：公共网页地图网络
验证这些结构是否值得跨用户共享和持续合并
```

方向 A 即使最终不做公共共享，仍然可以直接改善本地 MCP；方向 B 即使最终成立，也必须先明确它共享的究竟是哪一种结构资产。

## 十二、当前结论

当前只能确认：复杂网页任务中，智能体确实存在页面理解、路径判断、动作前置条件和结果确认困难。

当前不能确认：这些困难是否必须通过一份独立的“网页地形信息”来解决，也不能确认地形信息是否比更好的模型提示、Skill、搜索或视觉兜底更有效。

因此本方向的下一步不是建设公共网络，而是先完成有无地形先验的真实任务对照实验。
